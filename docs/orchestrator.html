Methodology

Orchestrator, budgets and failure types

The orchestrator is an LLM agent that works on one description at a time. At each step it receives a short description of the situation and the list of actions that are allowed now, chooses one, and the matching tool runs. It never sees the reference model or a similarity score; after the comparison it sees how many errors remain, per type. This page explains the actions, the budgets, when the work on a description stops, how failures are detected, and how bonuses and penalties are counted.

The actions and when each one is allowed

The loop is always the same: decide → run the tool → decide again. The code computes the allowed actions from the state of the description; the agent chooses among them and gives its reason, which is saved in decisions.json.

ActionWhat the tool doesAllowed when
generateThe generator writes the first draftNo draft exists yet
validateThe Structural validator checks the latest draft at levels L1 to L4The latest draft is not validated
evaluateThe Similarity evaluator compares the draft with the referenceThe draft is validated
detect_failuresThe Failure detector turns the validator and similarity results into failure types T1 to T7After evaluate
learnRuns the two tool-using guideline agents (Retriever and Expert, each in its own ReAct loop with its tools and a budget of tool calls); they propose guidelines, or abstain, and the Guideline catalogue is updated Learning is on and a failure type was detected; not after the last next iteration (nothing could test it)
reviseStarts a next iteration: the guidelines learned for this description are sent back to the generator Guidelines to send exist and the 3 next iterations are not reached
stop_success / stop_failureEnds the description Success when the kept draft is valid, failure when it is not or when a budget is used up

In the Revised runs and the Reuse training, the iterations are forced: while a failure type is detected and fewer than 3 next iterations were made, the only allowed action is learn, then revise. So every description gets i1, i2 and i3 unless no failure is left. In First and in the Reuse tests, there is no learning: the description ends after the first pass.

The budgets of one description

Three numbers limit the work on one description. They are saved with the run in models.json under limits.

BudgetValueWhat it limitsCommand line
Next iterations3 (0 in First and Reuse tests)How many times the error-driven guidelines are sent back to the generator for the same description--next-iterations

Orchestrator decisions48Total number of decisions of the agent, plus the final stop--max-decisions
first pass = generate + validate + evaluate + detect = 4 (+ learn = 5 when learning is on)
one next iteration = revise + validate + evaluate + detect = 4
learning between two next iterations = 1 learn, so N − 1 in total
maximum tool calls = 5 + 4N + (N − 1) maximum decisions = maximum tool calls + 1

With N = 3: 5 + 12 + 2 = 19 tool calls and 20 decisions, inside the budgets of 40 and 48.

When the work stops and which model is kept

Next iterations stop at the first of these:

  1. the 3 next iterations are done;
  2. no failure type is detected on the current model, so there is nothing to learn from;
  3. the agents learned nothing to send (they abstained, or only repeated guidelines already sent);
  4. the tool-call or decision budget is used up.

Which model is kept. After a next iteration, the new model replaces the previous one only if it is not less valid and has not more errors:

the new model is kept when errors of T1 to T7 after the iteration ≤ errors before it, and it is not less valid

Otherwise the previous model is kept and carried forward: the next iteration starts again from it, and the reported value of that iteration is the kept model. An empty draft (for example a truncated answer) is never kept. Example: 40 errors before, 44 after: the new model is not kept.

Confirmation of a guideline. A guideline sent in a next iteration is confirmed when the errors of its own type (T1 to T7) decrease. Only confirmed generic guidelines are reused on unseen descriptions in the Reuse tests.

In the first pass, the comparison with the reference is never used to choose a draft. In a next iteration the number of errors is used as stated above; this is why Revised i1, i2 and Learned are reported apart from First, and why Reuse is measured on descriptions never seen in training.
Failure types T1 to T7

The Failure detector is a rule, not a model, and it uses no threshold. T1 to T4 come from the Structural validator. T5 to T7 are detected as soon as the Similarity evaluator finds at least one difference of that kind between the kept draft and the reference.

TypeMeaningDetected whenOne error of this type is
T1Invalid XML or schemaValidator level L1 (syntax & schema) failsone incorrect element at L1
T2Incorrect gateway useValidator level L2 (gateways) failsone incorrect gateway
T3Incorrect control flowValidator level L3 (sequence flows) failsone incorrect flow node, or one problem of a whole process
T4Malformed pools, lanes or message flowsValidator level L4 (collaboration) failsone incorrect lane or message flow
T5Connections or flow order differ from the referenceA sequence flow, or an order relation, is missing or additionalone sequence flow missing or additional
T6Label meaning differs from the referenceAn activity of the reference or of the generated model has no partnerone activity without a partner
T7Participants differ from the referenceA pool, lane, membership or message flow is missing or additionalone such relation missing or additional
errors of T5 = sequence flows missing (FN) + sequence flows additional (FP)
errors of T6 = reference activities + generated activities − 2 × paired activities
errors of T7 = participant relations (pools, lanes, memberships, message flows) missing (FN) + additional (FP)

Two activities worded differently but with the same meaning (cosine similarity of at least 0.75, BAAI/bge-base-en-v1.5) are paired, so a different wording alone is not an error. Example: the reference has 10 activities, the generated model 8, and 6 are paired: T6 has 10 + 8 − 2 × 6 = 6 errors.

A failure type only opens the door to learning: T1 to T7 are passed, with their evidence, to the guideline agents (the Retriever and the Expert). They do not change the scores that are reported.

Bonuses and penalties

This is a record of the orchestrator's work, error by error: three incorrect elements at L3 are three errors of type T3.

  • Penalty: −1 for each error, at the step that finds it.
  • Bonus: +1 for each error that is gone, at the step that shows it.
penalty of a step = sum over the types of max(0, errors now − errors before)
bonus of a step = sum over the types of max(0, errors before − errors now)
score of a description = total bonuses − total penalties = − (errors still open at the end)

Example: the first draft has 3 incorrect elements at L3 (−3). The comparison then finds 4 flow errors and 2 activities without a partner (−6). After the next iteration, 1 L3 error and 1 flow error remain (+2 for T3, +3 for T5, +2 for T6). Bonuses 7, penalties 9, score −2: two errors are still open.
