Methodology

Structural validator

The Structural validator (step 3 of the pipeline) judges every model at four independent levels and records, for each level, a verdict, a message and the offending elements with their line numbers. In a next iteration, these messages are sent back to the generator with the previous model. The red boxes below show example messages in the validator's format. How the results are counted, with the equation of the precision, is in How the validator's results are measured.

L1
Syntax & schema

The document parses and conforms to the official BPMN 2.0 XSD (OMG). Child elements are first reordered, in memory, to the schema's canonical order, so element order alone is not penalized; the stored model is the generator's output, unchanged.

L1: does not conform to the BPMN20.xsd schema → Element 'conditionalEventDefinition': Missing child element(s). Expected is ( condition ).
L2
Gateways

Only the five standard gateway types are used, including in nested elements. An event-based gateway has at least two unconditioned outgoing flows, each leading directly to an intermediate catch event (message, timer, signal, conditional) or a receive task.

L2: event-based gateway leads directly to task 'Call_guest'; each branch must first reach an intermediate catch event (message, timer, signal, conditional) or a receive task
L3
Sequence flows: the control flow of each process, and recursively of each expanded sub-process
  • C1 start and end events exist (a rule of our modeling profile; BPMN allows implicit ones in some cases)
  • C2 sequence flows connect existing nodes of the same scope
  • C3 incoming and outgoing flows, with the exceptions of start, end, boundary and link events; boundary events attached to an activity
  • C4 every gateway splits or merges
  • C5 every node is reachable from a start event and can reach an end event
  • C6 the same rules inside sub-processes; event and ad-hoc sub-processes exempt where rules do not apply
  • C7 the flow of a scope forms one connected block
  • C8 behavior: no deadlock, and the process can always complete (token game)
L3: cannot reach an endEvent → ['StartEvent_Monitoring (line 18)'] (process 'Process_1')
L4
Collaboration: pools, lanes and message flows

Each lane, including nested lanes, lists only flow nodes of the process or sub-process it partitions, and a node belongs to at most one lane of a lane set (nodes outside every lane are only reported). With a collaboration, message flows connect different pools, never attach to gateways or lanes, and respect event direction. L4 is not applicable when a model has neither pools nor lanes.

How the validator's results are measured

Each level gives one verdict per model: pass, fail, or not applicable (L4, when the model has neither pools nor lanes). On top of this verdict, the validator marks every element it inspects at that level as correct or incorrect, with the reason. This gives a finer measure than pass or fail.

LevelElements inspectedAn element is incorrect when
L1Every XML element that has an idThe schema reports an error on its line, or on one of its children that has no id
L2Every gateway, nested ones includedIts type is not one of the five standard types, or an event-based gateway breaks its rules
L3Every flow node (activities, events, gateways, also inside sub-processes), plus one entry for each problem of a whole process, such as a missing start eventIt breaks one of the rules C1 to C8
L4Every lane and every message flowA lane lists an element of another process; a message flow stays inside one pool, touches a gateway or a lane, or goes against the direction of an event
precision of a level = correct elements (TP)correct elements (TP) + incorrect elements (FP)

For one model, the elements are those of that model. For a run, the correct and incorrect elements of all the models where the level applies are added first, then divided. A model where the level is not applicable is kept apart: it counts neither as correct nor as incorrect.

Why precision only, and no recall or F1. An element is correct (TP) when it satisfies the BPMN 2.0.2 rules the level checks, and incorrect (FP) when it breaks one; the reference model is not used. Recall would need the elements that are missing from the model (FN), and the validator cannot see what a model omits. Precision is therefore the only measure it supports. The average of a model is the mean precision of the levels that apply to it.

Where to see it. On the Run page, the tables “Structural validator, element by element” (first draft and kept draft) and, for each draft, the list of incorrect elements with their reason. In the run folder: validator_performance.json.

C8: the deadlock check

When C1–C7 hold, the validator plays the BPMN token game over all reachable states of the scope (soundness.py): exclusive gateways follow one branch, parallel gateways wait for all branches, inclusive joins wait while a token can still arrive, boundary events replace or extend their host's completion, and a terminate end event stops the instance.

L3: deadlock: parallelGateway 'Join_Payment' waits for flow(s) Flow_Cash_Join that can no longer receive a token (e.g. an exclusive split joined by a parallel gateway, or a parallel gateway used to merge a loop)

A flow that can carry two tokens at once (lack of synchronization) is reported as a warning only, since it can be intended, e.g. a non-interrupting timer inside a loop.

What the generator receives in a next iteration

A next iteration sends exactly:

  • the process description and the guidelines of the setting, as for the first draft;
  • the model kept so far (previous_generated_bpmn_xml);
  • the Structural validator's report of that model (validation_profile): for each level, the verdict, the message and the offending elements;
  • the guidelines sent back for this example (guidelines_to_apply).
The reference model and the similarity scores never enter what the generator receives.

Which model is kept. The new model replaces the previous one unless it is less valid or has more errors (T1 to T7). So a next iteration cannot hand back a model less valid than the one it started from.

What “valid” means, and what it does not

Conformance to every implemented check (L1–L4, C1–C8).

Checked on the 55 reference models: all of them pass every level.

Not full BPMN compliance (e.g., data or message semantics).

Not fidelity to the description: a valid model can still miss an activity.
