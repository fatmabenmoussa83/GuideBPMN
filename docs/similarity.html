Methodology

Similarity evaluator

The Similarity evaluator (step 4 of the pipeline) compares a generated model with its reference model (the gold BPMN). It runs once drafting is finished and it is the only step that reads the reference. Every score is between 0 and 1, higher is better, and each score is reported on its own: there is no total score. The five measures of the pipeline figure are flow order, participants, connections, label meaning and element coverage; this page gives the equation of every score, in the order the evaluator computes them.

Step 1 · Pair the elements of the two models

Before the structure is scored, the evaluator decides which reference element corresponds to which generated element. This pairing is used by element coverage, connections, flow order and participants. The label scores of step 2 pair the labels by meaning only (same category, cosine of at least 0.75, one-to-one), without the position in the flow. The identifiers written in the XML are never used.

  1. Compare the labels. Each label is turned into a vector by the embedding model BAAI/bge-base-en-v1.5. Two labels are compared by cosine similarity: 1 means the same meaning, 0 means unrelated.
  2. Same category only. An activity can only be paired with an activity (task, user task, service task… all count as activities), an event with an event, and a gateway with a gateway of exactly the same type.
  3. Named activities: the label decides. A pair is possible only if the cosine is at least 0.75. The position in the flow can rank the candidates but cannot rescue a pair below 0.75.
  4. Gateways and unnamed start or end events: the position decides. They usually have no label, so they are paired from their type and their neighbours, and accepted from a score of 0.50.
  5. One-to-one assignment. The Hungarian algorithm picks, inside each category, the pairing with the highest total score. An element with no acceptable partner stays unpaired.
  6. Refine. The score of each candidate pair is updated with the neighbours that are now paired, and the assignment is repeated until it no longer changes, at most 3 times.
cosine(a, b) = vector(a) · vector(b)length of vector(a) × length of vector(b)
first score = 0.90 × cosine of the labels + 0.10 × local context
refined score = 0.90 × first score + 0.05 × predecessors already paired + 0.05 × successors already paired

Local context is the mean of five comparisons between the two elements: number of incoming flows, number of outgoing flows, categories of the predecessors, categories of the successors, and same kind of scope (process or sub-process). Predecessors already paired is the share of the predecessors of the two elements that are paired with each other; the same for successors.

element coverage = paired elementsmax(reference elements, generated elements)

Example: the reference has 10 elements, the generated model 6, and 6 are paired. Coverage = 6 ÷ max(10, 6) = 0.60.

Step 2 · Label meaning: does the model describe the same work?

Activities score (the main label score). Sum of the similarities of the accepted activity pairs, divided by the larger number of activities. A missing activity and an additional activity both lower it.

activities score = sum of cosine of the accepted activity pairsmax(reference activities, generated activities)

Activity precision, recall and F1 count the pairs instead of summing their similarities.

precision = paired activitiesgenerated activities recall = paired activitiesreference activities F1 = 2 × precision × recallprecision + recall

Example: the reference has 10 activities, the generated model 8, and 6 pairs are accepted with similarities that sum to 5.4. Activities score = 5.4 ÷ 10 = 0.54. Precision = 6 ÷ 8 = 0.75. Recall = 6 ÷ 10 = 0.60. F1 = 0.67.

All labels. The same idea on every labelled element. Each category is paired separately: activities (task, user task, service task, send task…), each event type (start, end, intermediate catch, intermediate throw, boundary), each gateway type, sub-processes, pools, lanes and message flows. An element without a label is not counted on either side. Labels of sequence flows (such as “yes” and “no”) are not counted. When the reference has no pool, the pools, lanes and message flows added by the generator are set aside first.

all labels = sum of cosine of all accepted pairssum over the categories of max(labelled reference elements, labelled generated elements)
Why the activities score is the main one. The reference models label only 99 of their 464 gateways. A generated model that labels its gateways was penalised by the all-labels score for labels the reference never had. Activities are labelled in both models, so the activities score does not have this problem. Both are shown.
Step 3 · Connections: are the same sequence flows present?

A sequence flow A → B of the reference is correct when the generated model has a flow between the partners of A and B, in the same direction. Labels are not scored a second time here: the pairing of step 1 already used them.

CaseMeaningCounted as
correctthe flow exists in both modelsTP
missinga reference flow with no counterpart, including a flow whose source or target could not be pairedFN
additionala generated flow with no counterpartFP
reversedthe reference has A → B and the generated model has B → Aone FN and one FP
precision = TPTP + FP recall = TPTP + FN connection F1 = 2 × TP2 × TP + FP + FN

Example: the reference has 10 flows, the generated model 8, and 5 are the same. TP = 5, FN = 5, FP = 3. Precision = 5 ÷ 8 = 0.63. Recall = 5 ÷ 10 = 0.50. F1 = 10 ÷ 18 = 0.56.

Step 4 · Flow order: do things happen in the same order?

This score also counts indirect order. In A → B → C the order relations are: A before B, B before C, and A before C, because a path leads from A to C through B.

  1. Use the paired elements. Only elements paired in step 1 can be compared.
  2. Build the order relations. For every two paired elements, the evaluator asks in both models: does a path of sequence flows lead from the first to the second? Each relation is then classified.
StatusMeaningCounted as
correctthe relation exists in both modelsTP
missingthe relation exists in the reference onlyFN
additionalthe relation exists in the generated model onlyFP
reversedthe reference has A before B, the generated model has B before Aone FN and one FP
order consistency = TPTP + FP + FN

Example: the reference is A → B → C and the generated model is A → C → B. “A before B” and “A before C” exist in both (TP = 2). “B before C” is missing (FN = 1). “C before B” is additional (FP = 1). Order consistency = 2 ÷ (2 + 1 + 1) = 0.50.

Element coverage is taken into account. Two correctly ordered elements out of ten must not give a high score, so consistency is multiplied by the element coverage of step 1.

flow order = order consistency × element coverage

Example: consistency 0.50 and coverage 0.60 give 0.50 × 0.60 = 0.30.

  • Processes and sub-processes. The comparison is done inside each process and each sub-process. Each reference process is compared with the generated process that shares the most paired elements with it; the TP, FP and FN of all of them are added before the division.
  • Parallel branches. Two activities on parallel branches are not ordered, because no path leads from one to the other.
  • Not used: the order of the elements in the XML file, the positions in the drawing, and the labels.
Step 5 · Participants: same pools, lanes and message flows?

Five kinds of relations are compared: a pool exists, a lane exists, a lane belongs to a pool, an element belongs to a lane, and a message flow goes from one participant to another. Pools and lanes are paired from the paired elements they contain; a pool with no element inside (for example an external “Customer”) is paired by its name.

participants = TPTP + FP + FN
  • If neither model has a pool, a lane or a message flow, the score does not apply (shown as —).
  • If the reference has them and the generated model has none, the score is 0.
  • Rule of the pipeline. If the reference has no pool, lane or message flow (49 of the 55 examples), the score does not apply, and the pools added by the generator are set aside before the other scores are computed. The participants score is therefore an average over 6 descriptions. The scores on the model exactly as generated are also saved, with the suffix _strict.
Type counts (diagnostic only)

This check only counts elements; it does not use the pairing. Task subtypes are grouped as “activity”; gateway types stay separate. For each category:

TP = min(reference count, generated count) FN = max(0, reference count − generated count) FP = max(0, generated count − reference count)
precision = TPTP + FP recall = TPTP + FN F1 = 2 × precision × recallprecision + recall

It is saved with every result but decides nothing, because it counts elements without checking which ones they are.

Known limits
  • Everything depends on the pairing. A correct activity worded very differently (cosine below 0.75) stays unpaired and lowers the activities, element coverage, connections and flow order scores together.
  • One reference per description. A different but acceptable model is scored as different.
  • Participants is measured on 6 descriptions only.
