Methodology

Guideline learning: the Retriever and Expert agents

Steps 6 and 7 of the pipeline. When the orchestrator calls its learn tool, two LLM agents turn each failure type detected by the Failure detector (step 5) into an error-driven guideline, and the Guideline catalogue is updated. This page describes exactly what runs in the code: what is decided by an agent, what is computed by code, and what is kept in the trace. Every run on the Run page shows, for each description, every tool call of both agents, and the files of a description, traces included, can be downloaded there as a zip. The figure on the Overview page names the tools of each agent; this page says what each one does.

The sequence inside the orchestrator's learn tool
#WhoWhat
1CodeBuilds the evidence records, numbered so that the agents can cite them: the sentences of the process description (S1, S2…), the elements the Structural validator marked as incorrect at the failed level with the reason (V-L3-1…), and the differences found by the Similarity evaluator: reference elements without counterpart (M), generated elements without counterpart (X), label pairs (P), missing and extra flows (F, G), participant differences (C). For each failure type, a fixed table says which kinds of records it may use (T1–T4: the description and that level's validator records; T5: flows and elements; T6: labels; T7: swimlanes and messages).
2Retriever agentSelects, with its tools, the records that explain the failure (at most 12), and explains the error in one sentence.
3Expert agentReads the description and the selected records with its tools, consults the closest documentation guidelines and error-driven guidelines, checks its wording, and answers with one guideline and its relation to the existing guidelines, or abstains.
4CodeGuards the answer (citations, no reference-only label, near-copies), then updates the catalogue: stores, consolidates, or rejects.

The agents never open the gold BPMN file: they work on the Similarity evaluator's results. The orchestrator sees only the outcome of the step (which guidelines were learned), never a score.

How each agent runs: a ReAct loop with tools and a budget

Both agents follow the reason-and-act pattern of ReAct (Yao et al., ICLR 2023): the LLM alternates between reasoning and actions, and each action is a tool call whose result is fed back to it. The same single-agent, tool-using pattern is used by CP-Agent (Szeider, AGENT@ICSE 2026) with LangGraph. In GuideBPMN:

  1. Observe. At each step the agent receives its task, the list of its tools (name, description, arguments), the steps it has already made with their results, and the number of tool calls left.
  2. Decide. It answers with one JSON object: either a tool call {"action": "tool", "tool": <name>, "args": {…}, "reason": …} or its final answer {"action": "final", …}. The reason it gives for each call is kept in the trace.
  3. Act. The code runs the tool and returns the result; the loop continues until the agent gives its final answer or the budget is reached.
Rule of the loopWhat happens
BudgetRetriever: 4 tool calls; Expert: 6. When no call is left, the agent is told so and must answer.
Unknown tool or wrong argumentsThe agent gets an error message as the result and continues; nothing crashes.
Expert proposes without having consulted the documentation guidelinesIts answer is sent back: “call find_closest_documented_guidelines first and classify your guideline against what it returns”. So the relation is always the Expert's own decision.
Answer cut at the output limitThe agent is asked once more, briefly (the JSON object only); if it is cut again, a last time with the tool results shortened. Each event is recorded in the trace.
TraceEvery step (tool, arguments, result, reason), every send-back and the final answer are saved in guideline_learning_history.json, for every learn call of every description.

The loop is the same for both LLMs (GPT-6 Luna and Claude Haiku 5.5): it uses the plain chat call of each provider, not a provider-specific tool API.

The Retriever agent — selects the evidence and explains the error

Receives: the failure type (T1–T7) with its meaning, the summary of the Failure detector, and how many records of each kind exist. It does not see the records at first: it has to look for them.

ToolArgumentsReturns
list_evidencekind: description, validator_L1…L4, missing_element, extra_element, missing_flow, extra_flow, label_pair, collaboration, counts, metricsThe records of that kind (id and text), at most 40
search_evidencewordsThe records whose text contains one of the words
find_counterpartsrecord_id of a missing reference elementThe generated elements without counterpart whose wording overlaps it: the same element may have been modeled differently (another type, another pool)

Final answer: {"selected": [ids], "reason": …}: at most 12 records, and the reason is its explanation of the error, which the Expert receives.

Code after it: ids that do not exist are dropped; the generated counterparts of the selected missing elements are added when the agent did not select them (completeness, logged as added by code).

The Expert agent — reviews the evidence, proposes the guideline and decides its relation

Receives: the failure type, the records selected by the Retriever with its explanation, and the list of categories of the documentation guidelines.

ToolArgumentsReturnsComputed by
read_descriptionnoneThe full process descriptioncode (reads the text)
find_closest_documented_guidelinestextThe 6 documentation guidelines closest to the text (id, category, rule) code: sentence embeddings with BAAI/bge-base-en-v1.5, the same model the Similarity evaluator uses to compare labels, then cosine similarity; a word-overlap score (Jaccard index of the words longer than 3 letters) is computed too and the higher of the two ranks. No threshold: the Expert decides.
find_closest_learned_guidelinestextThe 4 error-driven guidelines of the run's catalogue closest to the textsame
check_wordingtextWhether the text is tied to this one process, and by which words code: a word is tied when it appears in this description and in fewer than 3 of the descriptions in scope, and is not generic or BPMN vocabulary

Final answer: decision (propose or abstain), trigger (the situation: what the description states, written in general terms, starting with “the description…”), instruction (what to model), category, cited (the records it relies on), relation and rule_id, reason.

Relation decided by the ExpertMeaningEffect on the catalogue
contradicts (checked first)The guideline asks for a model that a documentation guideline forbids or advises againstReturned once to the Expert to be rewritten so that it respects that guideline; if it still contradicts it, rejected. No stored guideline goes against the BPMN specification.
not_applied (restates)A documentation guideline already says the same thing; the generator did not apply itNothing stored; that documentation guideline is sent back to the generator in the next iteration
refinesA documentation guideline covers the topic; this one adds when or how to apply itStored, with a link to the refined guideline
newNo guideline covers itStored
same_as_learnedAn error-driven guideline already says essentially the same thingConsolidated: not duplicated; the description is added to the descriptions that guideline was learned from (its support)

When the Expert is asked again. Once if it abstains while the failure is still detected on the model; once if its wording is still tied to the process (with the words to avoid); once if its guideline contradicts a documentation guideline.

Generic or example-specific. A guideline still worded in terms of its own process after the rewrite is kept as example-specific: it is sent back to its own description only and never given to another description. Otherwise it is generic. A confirmed example-specific guideline is given to the Expert once more to be written in general terms (promotion).

The code guards, and what they never do

After the Expert's final answer, the code checks it. These checks are guards, like the orchestrator's allowed actions: they can reject or correct an answer, they never write a guideline.

GuardRuleOutcome
CitationsEvery cited record must be one the Expert was given; trigger and instruction must not be emptyrejected (bad citation / incomplete)
No reference labelThe guideline must not contain a label that exists only in the reference model (the agents never see that file; this catches a leak through the evidence)rejected (reference label)
Named guidelineThe id the Expert names must be one its tools returnedotherwise the relation is not used
Near-copyA proposal nearly identical to an existing guideline (cosine ≥ 0.88 or word overlap ≥ 0.60) is treated as that guideline, even if the Expert said “new”not applied (documentation) or consolidated (error-driven)
FallbackOnly if the Expert gave no usable relation (it spent its whole budget without consulting the documentation guidelines): the similarity thresholds decide (cosine ≥ 0.72 = refines the closest, otherwise new)logged as judged by similarity instead of judged by the Expert
confirmed = after the guideline was sent back, the errors of its own type (T1–T7) decreased and the new model was kept

Only confirmed generic guidelines are reused on unseen descriptions in the Reuse setting.

A real trace (GPT-6 Luna, Revised run 1 of the study, description 04, failure T5, first learn call)

Copied from id_04/guideline_learning_history.json of the run; the wording of the agents is theirs. The same view, for every description of every run, is on the Run page.

Retriever agent (4 tool calls, its whole budget)

  1. list_evidence(kind: description) → 5 records S1–S5. Why: “Read the reference description sentences that specify what the process should contain.”
  2. list_evidence(kind: missing_element) → 7 records M1–M7. Why: “Identify absent reference elements and then check for generated counterparts that may represent them differently.”
  3. list_evidence(kind: missing_flow) → 20 records F1–F20. Why: “Inspect the missing connections to identify the main structural divergences and relevant description points.”
  4. find_counterparts(record_id: M1) → X1, a generated intermediate catch event. Why: “Check whether the missing campaign-period-end task is represented by a differently named or modeled generated element before selecting evidence.”
  5. Final: selected S1–S5, M1–M5, M7, X1 (12 records). Explanation: “The descriptions establish the intended campaign stages, while the selected missing elements show structural differences at campaign setup, lead handling, and performance analysis. X1 is included as the generated event that may correspond to the missing campaign-period-ending task.”

Expert agent (4 of its 6 tool calls)

  1. read_description(). Why: “Verify the process sequence and whether campaign completion and the parallel activities are stated in the description.”
  2. find_closest_documented_guidelines(text: “When a process description says a period ends or an activity waits until a specified time, model the wait as a timer intermediate catch event rather than as a task…”) → EVT-13, PROC-04, EVT-03, EVT-02, ACT-07, ACT-04. Why: “Check documented guidance most relevant to the event-type mismatch and gateway differences before proposing a guideline.”
  3. find_closest_learned_guidelines(text: “When a description identifies multiple required activities as independent work that may proceed concurrently, model them as parallel branches…”) → LRN-010, LRN-013, LRN-009, LRN-011. Why: “Check whether an error-driven guideline already covers the missing parallel gateways.”
  4. check_wording(text: “the description lists multiple distinct activities as required parts of a phase before subsequent work…”) → not tied to this process, no word to avoid. Why: “Verify that the proposed guideline is general and does not rely on wording specific to this process.”
  5. Final: propose — when the description lists multiple distinct activities as required components of the same phase before later work: model the activities as parallel branches and synchronize all branches with a parallel gateway before the later work. Category: gateways, branches and joins. Cites S2, M5. Relation: same_as_learned LRN-010. Reason: “The description lists several activities in one phase, and the reference includes a parallel gateway before them. This matches learned guideline LRN-010. The campaign-period end is represented by a generated intermediate catch event (X1), so that item is a difference in element choice, not a missing element.”

Code guards: S2 and M5 exist among the records it was given, no reference-only label, LRN-010 is among the guidelines its tool returned → consolidated with LRN-010 (judged by the Expert); description 04 is added to the support of LRN-010. Nothing new is stored, and LRN-010 is sent back to the generator in the next iteration.
