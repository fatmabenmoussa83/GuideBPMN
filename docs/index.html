Overview

GuideBPMN — BPMN generation that learns modeling guidelines

GuideBPMN turns a textual process description into a BPMN 2.0 model and learns modeling guidelines from the mistakes it verifies. An orchestrator agent (LLM + LangGraph) calls the components as tools. The generator starts from the documentation guidelines, paraphrased from the official OMG BPMN 2.0.2 specification; what the pipeline learns is given back to it in next iterations and reused on unseen descriptions. This site lets you run the study on a 55-example dataset and see every result.

Architecture of GuideBPMN

The orchestrator coordinates executions, decisions and iterations: it feeds the generator, has the model checked by the structural validator and the similarity evaluator, feeds the failure types to the guideline agents (the Retriever and the Expert, each with its own tools and an LLM that decides), which update the guideline catalogue. The seven steps
  1. Inputs. The task prompt, the process description, and the 82 documentation guidelines.
  2. Generator. An LLM model writes the BPMN 2.0 XML.
  3. Structural validator. Four deterministic checks: L1 syntax & schema, L2 gateways, L3 sequence flows, L4 collaboration (pools, lanes and message flows).
  4. Similarity evaluator. The BPMN XML is checked against the gold BPMN: flow order, participants, connections, label meaning and element coverage. It is the only step that reads the gold model.
  5. Failure detector. A rule-based tool turns the results of steps 3 and 4 into failure types: T1–T4 types of validator errors, T5–T7 types of similarity errors.
  6. Guideline agents. Two tool-using LLM agents, each in a ReAct loop. The Retriever agent selects the evidence and explains the error with list_evidence(kind), search_evidence(words) and find_counterparts(record_id). The Expert agent reviews the evidence and proposes a guideline of the form “when the description states …, model …”, or abstains, with read_description(), find_closest_documented_guidelines(text), find_closest_learned_guidelines(text) and check_wording(text). Details: Guideline learning.
  7. Guideline catalogue. Documentation guidelines (read-only), generic error-driven guidelines, and example-specific error-driven guidelines. The Expert decides whether its proposal restates a documentation guideline, refines one, is new, contradicts one, or is the same as an error-driven guideline already learned.

Next iteration. The guidelines learned for a description are sent back to the generator for that same description, and the new model is validated and compared again. In the study the iterations are forced: 3 next iterations for every description while a failure is left. A guideline is marked confirmed when the errors of its own type (T1–T7) decrease after it was sent back.

The three settings of the study
SettingWhat it doesWhat the generator receives, besides the description and the documentation guidelines
FirstFirst pass only, no learning; 3 separate runsNothing
RevisedLearns from an empty catalogue, 3 forced next iterations on every description; 3 separate runs. Reported after iteration 1, 2 and 3 (Learned) In each next iteration, the guidelines learned for this description
ReuseStratified 5-fold cross-validation: learns on 44 descriptions (as Revised), then a first pass on the 11 unseen ones; 1 run The confirmed generic guidelines learned in the training of the round

Each setting is compared with First: mean over the runs, with the sample SD between the runs in parentheses, and a paired Wilcoxon signed-rank test (p < 0.05) on the per-description means.

How the comparison is kept fair

The reference stays behind step 4

The generator never receives the reference model. The orchestrator never sees the reference or a similarity score; after the comparison it only sees how many errors remain, per type. The guideline agents work on the evaluator's results, never on the reference file.

No example helps itself

In Reuse, the test descriptions of a round are never in its training set: a guideline is never reused on a description it was learned from.

Evidence before use

A guideline is reused only once it is confirmed: the errors of its own type decreased when it was sent back.

Scores kept separate

The measurements are reported one by one, on the first pass, and are never merged into a single weighted score. The next iteration is reported apart, because it uses the example's own reference.

Where things are
  • Run GuideBPMN: test one description from zero and download everything the tool did for it; launch First, Revised or Reuse runs, follow them description by description, reopen past runs.
  • Guidelines: the documentation guidelines and the catalogues of error-driven guidelines.
  • Guideline learning: the Retriever and Expert agents, their tools, the code guards and a real trace.
  • Orchestrator & budgets: the actions, the budgets of one example, the stop rules, the failure types, the bonuses and penalties.
  • Structural validator L1–L4: what each level checks and how its results are measured.
  • Similarity evaluator: every score with its equation.
  • Documentation: installation, command line and output files.
