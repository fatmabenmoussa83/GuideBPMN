# Learned guidelines: Claude Haiku 5.5, Reuse training, round 2 (44 descriptions)

119 generic and 38 example-specific error-driven guidelines; 62 generic guidelines confirmed. Full records (evidence, confirmation tests, provenance): `learned_guidelines.json`.

## Generic guidelines

**LRN-008** (T5; refines EVT-01; 7 description(s); confirmed: yes)  
When the description says the process begins when a participant performs an action (an activity it names), rather than when an external message, signal, time or condition occurs: Model a start event for the process beginning, with no incoming flow, followed by a task labeled with that participant's action in the description's own wording. Do not label the start event with the action, and do not replace the action with the start event.

**LRN-055** (T5; refines GW-05; 6 description(s); confirmed: yes)  
When the description lists several activities that are carried out concurrently or in no stated order, and a later step starts only after all of them have completed: Model these activities as parallel branches: place a parallel gateway (split) before them, with one outgoing branch per activity and no conditions on the branches. Merge the branches with a matching parallel gateway (join) placed before the later step, so that step starts only after every branch has completed. Do not order the activities arbitrarily, do not use an exclusive gateway for the split or join, and do not let the later step follow any single branch.

**LRN-006** (T6; refines GW-04; 5 description(s); confirmed: yes)  
When the description lists several distinct actions that all follow one point, joined by commas and 'and', with no order stated between them (for example, 'X, Y, and Z' after an event): Model each listed action as its own task. Place a parallel (AND) split after the common point so that all branches start, and join them with a parallel gateway before the shared continuation. Do not add decision conditions to these branches and do not serialize them in an arbitrary order.

**LRN-001** (T5; refines ACT-07; 4 description(s); confirmed: yes)  
When the description lists several activities that follow the same point with no stated order between them, and the following step waits until all of them are finished: Model each such activity as a parallel branch. Route the incoming flow from the preceding point into a parallel gateway that fans out with one unconditional outgoing flow to each listed activity. Route each activity's outgoing flow into a second parallel gateway that joins the branches before the next step. Do not connect the preceding point to only one of the activities, and do not use an exclusive gateway for branches that must all be finished.

**LRN-017** (T6; refines FID-03; 4 description(s); confirmed: no)  
When the description states that a participant outside the company performs an action, such as choosing or supplying information, and the process then depends on that action: Model a task for the participant's own action, labeled with the verb and object the description uses for what the participant does (for example, 'provide ...' or 'select ...'). Do not label the task with the organization's receipt or processing of that input, and do not merge a separately described participant action into a task for the organization's follow-up communication.

**LRN-019** (T5; refines ACT-07; 4 description(s); confirmed: yes)  
When the description states that one activity is followed by two or more separate actions that all must happen, with no order stated between them, and the process continues only after all of them are done: Model a parallel gateway that splits the flow after the preceding activity into one branch per action, with each action as its own task. Close the branches with a parallel gateway before the next activity that needs all of them. Also place a parallel gateway around any activity the description lists as a separate, unordered step within such a group, so that each stated step keeps its own position in the flow. Do not use an exclusive gateway for branches that must all complete.

**LRN-051** (T5; refines ACT-04; 4 description(s); confirmed: yes)  
When the description says a participant personally carries out an action, such as a request, a review, an evaluation, or a delivery step, and does not say that a message is sent to another participant as the unit of work: Model that action as a user task performed by the responsible participant, not as a send task. Reserve a send task for cases where transmitting a message is itself the modeled work. Make sure each such action appears as its own task in the sequence where the description places it.

**LRN-002** (T6; refines PROC-04; 3 description(s); confirmed: no)  
When the description states that a later phase of the same process begins only after an earlier decision or acceptance point has been reached, and that phase is a continuation of the same process rather than an independently triggered one: Model that later phase as an activity (task) placed after the decision or acceptance point in the existing sequence flow. Do not give it a new start event, and do not give the phase's completion a new end event unless the description states a separate outcome.

**LRN-004** (T6; new; 3 description(s); confirmed: yes)  
When the description states that a signal or need may be raised by one of two alternative activities joined by 'or', where each alternative is a distinct activity, and the process then continues with a decision that depends on the outcome: Model each alternative as its own task. Place an exclusive (XOR) split before the alternatives, with one outgoing flow to each task. Route both tasks into one exclusive merge gateway, and place the decision gateway after that merge. Do not drop either alternative, and do not connect the preceding point directly to the decision.

**LRN-007** (T6; refines FID-02; 3 description(s); confirmed: yes)  
When the description lists several distinct actions performed by the same participant in one sentence, joined by 'and' or commas (for example, one action for producing something and another for preparing its presentation): Model each listed action as its own task, in the order the description gives, and label each task with that action's own wording from the description. Do not combine the actions into one task whose label joins them.

**LRN-022** (T5; new; 3 description(s); confirmed: no)  
When the description states that a later step continues only if an assessment result is positive (for example, "if approved, ...") and gives no alternative handling for the negative result, so the process must end on that branch: Place an exclusive gateway directly after the assessment activity. Label one outgoing flow with the positive condition, leading to the continuing activities. Label the other outgoing flow with the negative condition, leading to its own end event. Keep a dedicated decision gateway with the stated condition on the flow, and do not leave the negative outcome as an unlabeled or unconnected path.

**LRN-027** (T5; refines FID-02; 3 description(s); confirmed: yes)  
When the description says the process ends with an activity that a participant carries out after the last described step (for example, the start of work or distribution), so the final sentence names an action rather than a terminal state: Model that described action as a task placed on the flow immediately before the end event, and give the end event a label that names the outcome only. Do not fold the action into the end event's label.

**LRN-062** (T6; refines FID-01; 3 description(s); confirmed: yes)  
When the description says a participant first checks whether they already have something, and a later exclusive decision branches on the result of that check: Model the check as its own activity performed by that participant, labeled with the description's own wording for the check, placed after the preceding step and before the exclusive gateway that branches on the result. Do not drop the check or fold it into the gateway's label or condition, and do not model it as a gateway.

**LRN-070** (T5; refines ACT-05; 3 description(s); confirmed: yes)  
When The description says the process sends a request or places an order with an outside party, and the next step can only happen after that party's reply or confirmation arrives, without describing a decision based on that reply: Model the wait for the reply or confirmation as an intermediate message catch event placed after the request activity and before the step that depends on it, connected by sequence flows in that order. Do not model the wait as a task, and do not leave it out so that the next step follows the request directly.

**LRN-094** (T5; refines PROC-05; 3 description(s); confirmed: yes)  
When the description states that the flow begins with an actor's own action, with no separate triggering event or message described before it, and a later check of that action follows: Model exactly one start event at the process entry. Connect it by a sequence flow to a bpmn:task for the actor's stated action, and never model that action as a start event. Do not add further start events for later checks or later phases, and do not connect the start event directly to a check the description places after the action. A later phase begins from the outgoing flow of the preceding step to a task for its first activity.

**LRN-114** (T5; refines GW-03; 3 description(s); confirmed: yes)  
When the description presents two or more mutually exclusive alternative activities, each of which by itself leads to the same next step or end event, so that either alternative is sufficient: Model an exclusive (XOR) gateway that routes the flow into one of the alternative activities, if the preceding point chooses between them. Connect each alternative activity to a single exclusive merge gateway, and connect that merge gateway to the shared next step or end event. Do not connect alternatives directly to the shared step or end event, and do not use a parallel gateway for alternatives that exclude each other.

**LRN-012** (T1; refines XML-05; 2 description(s); confirmed: yes)  
When the description asks for a complete BPMN XML model and does not request a diagram layout, but the output would otherwise include a diagram interchange (BPMN-DI) section: Omit the BPMN-DI section entirely unless the description asks for layout. If any BPMN-DI section is emitted, its diagram element must contain a plane element that references the process or collaboration, and the diagram must not be left empty. A diagram element with no plane child is schema-invalid.

**LRN-020** (T5; refines FID-02; 2 description(s); confirmed: yes)  
When the description states that one activity covers two or more independent checks or evaluations joined by 'and', and a later decision or step depends on all of them being completed: Model each stated check or evaluation as its own task, not as one combined task. Place a parallel (AND) split before these tasks so that all of them start, and close them with a parallel join before the decision or step that depends on their results. Label each task with that check's own wording from the description. Do not use an exclusive gateway for checks that must all complete.

**LRN-025** (T6; refines ACT-05; 2 description(s); confirmed: yes)  
When the description says a party performs a named action (for example filing, submitting or giving something) and does not say that a message is sent to or awaited from another party: Model that action as a plain task labeled with the description's own wording for the action. Do not model it as a send task or an intermediate message catch event. Use a send task or a message catch event only when the description states a message being sent or awaited.

**LRN-029** (T5; refines ACT-07; 2 description(s); confirmed: yes)  
When the description states that each activity is followed by a specific next activity, and that a decision after an activity may send the flow back to repeat an earlier activity before continuing: Connect each stated activity to the activity that the description places immediately after it with a sequence flow. Where a decision may repeat an earlier activity, add an exclusive gateway after that decision with one flow looping back to the repeated activity and one flow continuing to the next stated activity. Do not leave any stated step without an incoming flow from its predecessor or an outgoing flow to its successor, except for the start and end events.

**LRN-031** (T5; refines PROC-04; 2 description(s); confirmed: yes)  
When the description states a decision whose negative outcome ends the process separately, while its positive outcome leads to a final step that concludes the process: Model an exclusive gateway at the point where the decision is taken, after the checks it depends on. Route the negative outcome to its own end event. Route the positive outcome through the final step and let that step connect to the single end event for the positive path. Do not add a second concluding end event after the final step, and do not place the decision after the final step unless the description says the decision follows it.

**LRN-033** (T5; new; 2 description(s); confirmed: yes)  
When the description lists a step of waiting for an outcome as one ordered step in a sequence and names no message, signal, timer or condition for that wait: Model that waiting step as a task placed in the sequence at its stated position. Use an intermediate catch event only where the description names a message, signal, timer or condition that the process waits for.

**LRN-042** (T5; refines GW-07; 2 description(s); confirmed: yes)  
When The description says that a time limit (a deadline) is reached after a request or notice has been made, and that a further action is then taken, such as forwarding the case to another party, if the expected response or payment has not arrived by then: Model the time limit as an intermediate timer catch event placed in the flow right after the step that starts the waiting period, and connect that timer event to the next action the description attaches to the deadline. Do not omit the time limit, and do not model it as an ordinary task. When the time limit is one branch of an event-based gateway, the timer event must be the target of that gateway branch.

**LRN-044** (T7; refines COL-07; 2 description(s); confirmed: yes)  
When the description says the process sends a request to an external party and later receives a reply from that party, and it describes nothing that party does on its own beyond the request and the reply: Model the request as a send task and the reply as a message catch event in the process's own pool, without creating a separate pool for that party and without message flows to or from it. Create a separate pool only when the description gives that party its own behavior or process.

**LRN-048** (T6; refines EVT-03; 2 description(s); confirmed: yes)  
When the description says that a participant pauses at some point until a condition is reached, and that later steps follow once the condition holds: Model the pause as an intermediate catch event within the flow of the pausing participant, at the position where the pause occurs, labeled with the condition as the description states it. Connect it with sequence flow so that subsequent steps continue from it. Do not model the pause as a task, since that implies work being performed, and do not model it as an end event, since the flow continues after the condition is reached.

**LRN-050** (T5; new; 2 description(s); confirmed: yes)  
When the description states that when an outcome is reached, the process either ends or continues depending on whether a recorded value is at or below a stated threshold, and the continuing branch also removes an obligation that applied before: Place an exclusive gateway at the point where the outcome is reached, after the activities that establish the recorded value. Label one outgoing flow with the at-or-below-threshold condition and the other with the above-threshold condition. Route the at-or-below branch to the continuing activities, and do not route it back into the activity whose obligation was dropped. Route the other branch to its own end event, as the description states. Do not collapse the two branches into one unconditioned path.

**LRN-054** (T6; refines FID-02; 2 description(s); confirmed: no)  
When the description lists several steps that the process itself performs for the person, such as fetching or collecting information, checking that gathered material is complete, preparing documents, or applying for a benefit, placed between choices, notifications, or waits: Model each such described step as its own activity in the order the description gives, and do not omit it or fold it into a neighboring activity. Use a serviceTask when the description attributes the step to a system, and a manualTask when it attributes the step to a person. Keep the dependency the description states, so that a later choice or notification follows the step it depends on.

**LRN-059** (T5; refines EVT-03; 2 description(s); confirmed: yes)  
When the description says that a later decision depends on answers that other people must give, so the process has to wait until those answers have been collected: Model the wait for those answers as an intermediate catch event, placed after the task that requests the answers and before the exclusive gateway that decides on them. Do not replace the wait with a task, and do not route the decision before the wait.

**LRN-066** (T5; refines GW-04; 2 description(s); confirmed: yes)  
When the description states that a set of items (up to a stated number) is handled in parallel, with each item in its own branch that must finish before the process continues: Model a parallel gateway that forks into one branch per item being processed in parallel, and a parallel gateway that joins those branches before the shared continuation. Do not use an exclusive gateway for the fork or the join, and do not put decision conditions on the parallel branches. A stated limit on how many items run at once can be shown in the task or the description, not as a gateway condition.

**LRN-077** (T6; refines FID-03; 2 description(s); confirmed: yes)  
When the description states a step as an action verb with an object, possibly with a direction or recipient, and the generated task label would swap that verb for a synonym or another activity type, or drop a qualifier stated for the object: Name the task with the action verb the description uses and keep every stated qualifier of its object, including any direction or recipient, so the label preserves the described action. Do not substitute a near-synonym or change the activity type, and do not shorten the object by dropping stated qualifiers.

**LRN-079** (T6; refines ACT-04; 2 description(s); confirmed: yes)  
When the description says the process itself sends information or instructions to one or more outside parties so that they carry out work, and does not say the process waits for anything from those parties at that point: Model the step as a bpmn:sendTask, labeled with a send verb and the recipient as the description names it, placed before the outside work it triggers and connected by sequence flow. Do not model an outbound send as a bpmn:receiveTask or as a manual task, because the message direction and the task semantics would then be wrong.

**LRN-082** (T5; refines EVT-03; 2 description(s); confirmed: no)  
When the description says an activity is repeated once for each external occurrence (something arriving, or a response to something that was sent out) and the process keeps repeating until a completion or satisfaction condition holds, looping back when that condition is not yet met: Model the repeated activity as a task. Wait for each occurrence with an intermediate catch event placed before the decision. After the wait, use a decision gateway that tests the completion condition. Place an exclusive merge gateway before the repeated task so that the first entry and the loop-back both enter through it. Connect the 'not yet met' outgoing flow of the decision back to that merge gateway, and leave the 'met' flow to continue the process. Do not omit the wait before the decision, and do not connect the decision directly back to the task without the merge.

**LRN-091** (T5; new; 2 description(s); confirmed: no)  
When the description says a participant must request information from one or more external parties, and the content of the response determines which one of several alternative activities follows: Model the information request as a user task performed by the responsible participant, placed directly before an exclusive gateway. Give that gateway one labelled outgoing sequence flow per possible response, each leading to the activity that response selects. If several parties are queried, model the querying as one user task by the participant before the gateway, not as receive tasks. Do not connect the request task directly to one alternative activity, and do not use a parallel gateway, since only one response branch applies.

**LRN-097** (T5; refines GW-03; 2 description(s); confirmed: yes)  
When the description has an exclusive decision with two or more alternative branches that later continue to the same shared step, and at least one alternative branch ends in a request that awaits a reply before the shared step: Model the decision with an exclusive gateway. Give each alternative branch its own path. Join the alternative branches with an exclusive merge gateway placed before the shared step, so the shared step is entered once from whichever branch was taken. Do not connect the alternative branches directly to the shared step, and do not use a parallel join for them.

**LRN-108** (T5; new; 2 description(s); confirmed: no)  
When the description states that one participant sends a document or request to a different participant, and that the receiving participant then reviews it and makes a decision with named outcomes: Model the sending as a send task in the sender's pool, connected by a message flow to the receiver's pool. Model the receiver's review as a task in the receiver's pool, placed after the message is received. Model the decision as an exclusive gateway with one conditional outgoing flow per named outcome, and give each outcome its own task in the receiver's pool. Do not replace the sending or the review with an unrelated user task in the sender's pool.

**LRN-115** (T6; refines ACT-05; 2 description(s); confirmed: no)  
When the description states that one participant sends a decision or document to another participant, and a later activity of the receiving participant acts on it: Model the sending as an explicit task in the sender's pool or lane, placed before the receiver's activity. If the receiver belongs to a different participant, connect the sending task to the receiving side with a message flow. Do not omit the sending step or reduce it to an implicit message flow.

**LRN-003** (T5; refines GW-03; 1 description(s); confirmed: yes)  
When the description states that an activity may or may not occur after another activity (for example, 'X may happen'), so it is not guaranteed to run in every execution: Model the optional activity behind an exclusive (XOR) split positioned right after the preceding activity. One outgoing flow leads into the optional activity, and a second, unconditional bypass flow skips it. Route both paths into a second exclusive merge gateway before the next activity, so the flow continues whether or not the optional activity ran. Do not connect the preceding activity directly to the next activity, and do not use a parallel gateway for an optional path.

**LRN-005** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description enumerates attributes that qualify how an activity is performed, without presenting them as a separate step or decision: Do not model the enumerated attributes as their own task. Keep them within the activity they qualify, for example by naming them in that task's label or documentation. Create a separate task only when the description states a distinct action to be performed.

**LRN-009** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description names two or more alternative activities joined by 'or' (for example, 'A or B' as the options the team may perform), and a decision follows that leads to one of them: Model each alternative activity as its own task on its own outgoing branch of the decision gateway, labeled with that alternative's own wording from the description. Do not merge the alternatives into one task whose label joins them with 'or'.

**LRN-010** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description's final sentence says the process ends when one action is completed and a further named action is also carried out, the two joined by 'and' (for example, 'the X is done and the Y is executed'): Model each named closing action as its own task, in sequence, so that the later action is a task placed before the end event and the end event follows the last action. Do not drop the later action or fold it into the earlier task, and do not end the process at the first action.

**LRN-011** (T6; refines FID-01; 1 description(s); confirmed: no)  
When the description says that an optional activity may also be performed (for example, 'may also' followed by one or more activities), and the main flow continues whether or not it is performed: Model the optional activities as tasks on one branch of an exclusive (XOR) split, with the other output of that split bypassing them. Route the optional branch and the bypass into one exclusive merge before the next step of the main flow. Label the split with a question built from the description's own wording, and do not connect the main flow past the optional tasks without a decision.

**LRN-013** (T5; refines PROC-04; 1 description(s); confirmed: no)  
When the description says a case can enter the process through one of several alternative channels, each a separate way to start it, and the channels then share one continuation: Model each alternative channel as its own entry path, starting with a start event and containing the task or catching event that the channel performs. Route every entry path into a single exclusive (merge) gateway, and connect that gateway to the shared continuation. Do not merge alternative channels with a parallel gateway, and do not collapse them into one task that represents all channels.

**LRN-014** (T6; refines FID-03; 1 description(s); confirmed: no)  
When The description states that the process begins when an external party performs an action through a channel, or that it ends after a stated final result, and that result is not a work step performed by a participant: Model the opening action as a start event and the stated final result as an end event, each labeled with the trigger or outcome named in the description. Do not model these as tasks.

**LRN-015** (T5; refines PROC-04; 1 description(s); confirmed: yes)  
When the description says that one case can begin through alternative channels (for example, several ways a request can be received), and each channel is a manual step by which the same case enters the process: Model a single start event for the process. Model one activity for each alternative channel, placed after the start event. Merge the channel activities with an exclusive gateway, and continue the common flow from that gateway. Do not create one start event per channel when the channels lead to the same case.

**LRN-016** (T5; refines PROC-05; 1 description(s); confirmed: no)  
When the description states that a process ends once a final outcome is reached, while a later event such as customer feedback or a return may start additional steps that the main flow does not require: Model the final outcome as an explicit task placed before the end event. After the activity that leads to that outcome, place an exclusive gateway with one branch to the outcome and end event and a second branch to the optional follow-up path. Start the follow-up path from an intermediate catch event for the later trigger, or from a separate process or event subprocess, and join it back into the main flow only where the description says the process can continue. Do not drop the outcome step, the decision gateway, or the optional follow-up branch.

**LRN-018** (T6; refines FID-03; 1 description(s); confirmed: yes)  
When the description lists several objects or alternatives within one step, joined by commas, 'and' or 'or': Label the task with one concise verb-object name that names the main action of that step. Leave out the secondary objects and the alternatives from the label, and keep the performing participant's verb rather than a generic receive verb.

**LRN-021** (T5; refines GW-03; 1 description(s); confirmed: no)  
When the description states that an activity may optionally be performed (for example, introduced with 'may be'), so it can be skipped after a preceding step: Model an exclusive gateway before the optional activity with one branch that performs it and one bypass branch that skips it. Model an exclusive merge gateway after the optional activity, where the performed branch and the bypass branch rejoin. Add a further exclusive decision gateway only where the description states the condition that selects the branch.

**LRN-023** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a later finalizing step happens only if a review by a separate party is approved, and the approval is itself a named action that the party carries out before the finalizing step begins: Model the review as its own task before the decision, and place an exclusive gateway after it. On the approved branch, add an explicit task named for the approval action, performed by the reviewing party, and connect it by a labeled flow to the finalizing step. Do not connect the gateway's approved branch directly to the finalizing step. On the not-approved branch, use a labeled flow to its own end event, and leave no outcome unconnected.

**LRN-024** (T1; refines EVT-01; 1 description(s); confirmed: yes)  
When the description says the process begins when an external party sends a message or reports a case, so the opening is a message occurrence that starts the case: Model the process opening as a plain start event (bpmn:startEvent) with no incoming sequence flow, and place a bpmn:messageEventDefinition child inside it to express the message. Never write a message start as its own element type directly under the process or subProcess (for example a messageStartEvent element), because BPMN 2.0.2 allows only flow element types such as startEvent in that position.

**LRN-026** (T6; refines ACT-07; 1 description(s); confirmed: yes)  
When the description says an item is checked in one or more review cycles in which feedback is given, and that changes are then decided on the basis of that feedback: Model the giving of feedback as its own task, labeled with the description's own wording for that act, placed after the review task it follows and before the exclusive gateway that decides whether changes are required. Route the gateway's change branch as the description states, and do not fold the feedback into the review task or omit it.

**LRN-028** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description joins two verbs with 'and' that apply to the same object in one sentence (for example, an item is both recorded and authorized), with no ordering, separate performer, or separate timing stated between them: Model the joined actions as one task that carries the combined action. Do not create a separate task for each verb. Split them only when the description states a dependency or order between the verbs, or names different performers for them.

**LRN-030** (T5; new; 1 description(s); confirmed: yes)  
When the description states that an outside party reviews the material the company has submitted and identifies issues in it, and that a later step carries out changes based on those findings, with no decision depending on the result: Model the outside party's review as its own task, labeled with the description's own wording for that review. Place it after the task or send task that submits the material and before the task that carries out the changes, and connect the three with sequence flows in that order. Do not merge the review into the submission task or the change task, and do not drop it.

**LRN-032** (T6; refines GW-02; 1 description(s); confirmed: no)  
When the description states a conditional sentence ('If <condition>, <consequence>') whose consequence is a list of several steps (for example introduced by 'which includes'), and the generated model replaces the condition and its steps with one container, subprocess or single task: Model the condition as an exclusive split with one outgoing flow into the first listed step and one flow for the case where the condition does not hold. Model each listed step as its own task, in the order given in the description, and rejoin the paths with an exclusive merge before the next step that follows the conditional. Do not collapse the condition and its listed steps into a single subprocess or task unless the description names them as one.

**LRN-034** (T5; refines FLOW-07; 1 description(s); confirmed: no)  
When the description says a repeated cycle continues until the participant reaches one of several stated end outcomes, for example one outcome that ends the cycle by completing and another that ends it by leaving: Place a decision gateway at the end of the repeated cycle. Give it a loop-back branch to the start of the cycle for the continuing case, and a separate outgoing branch for each stated exit outcome. Model each exit outcome as its own activity on its branch, and do not let the exit branches merge back into the cycle.

**LRN-035** (T5; new; 1 description(s); confirmed: no)  
When the description states that a step follows one earlier activity, is independent of the payment-related branches that run alongside it, and the process continues only after all of these parallel steps are done: Start the independent step from the same parallel (AND) split that opens the simultaneous branches, with its own unconditional outgoing flow and its own task. Do not route that branch through another parallel gateway in series, and do not let it pass through a gateway that belongs to another branch. Close all branches with one parallel join before the next decision or step that waits on them, and connect each branch's final task to that join.

**LRN-036** (T5; refines GW-06; 1 description(s); confirmed: yes)  
When the description states that two or more activities are performed after a step, joined by 'and', where one of them happens only 'if necessary' or under a stated condition while another is always performed, so the set of activities that actually occur varies but is never empty: Model an inclusive split before these activities. Label the outgoing flow of the conditional activity with the stated condition, and leave the always-performed activity's outgoing flow unconditional. Close the activities with a matching inclusive join before the next step. Do not use an exclusive gateway, because both activities can occur together.

**LRN-037** (T7; new; 1 description(s); confirmed: yes)  
When the description states that a role takes a decision on whether one or more optional activities are needed, the activities that follow are performed by other roles and may occur together, and they then converge before a later step performed by a role: Model the split as an inclusive gateway placed in the lane of the role that takes the decision, and do not leave it out of the model. Put the conditional activities each in the lane of their performing role, with one flow from the split to each activity labeled with its stated condition. Close them with a matching inclusive join placed in the lane of the role responsible for the step that follows, and connect that join to the next step. Do not add a start event for the receiving side and do not end the process after an intermediate handoff.

**LRN-113** (T6; refines ACT-04; 1 description(s); confirmed: no)  
When the description states that one participant sends a decision or document to another participant, and the other participant then reviews or acts on it as a later step: Model the sending step as its own task performed by the sending participant, placed before the receiving participant's review task, so that every stated action appears as a task in the described order. Do not omit a hand-off sentence because it seems to be only a transfer of information. If the two participants are in different pools, connect the send task to the receiving side with a message flow, not a sequence flow.

**LRN-116** (T5; refines ACT-05; 1 description(s); confirmed: yes)  
When the description states that one participant sends a request or notice to another participant, and the receiving participant then acts on it (for example by reviewing it): Model the sending as a task performed by the sender, placed in the sender's pool or lane, and connect it by a sequence flow to the receiver's activity. Do not replace the sending action with a start event. A start event marks only the process's initiating node; if the sending is the first described action, place a plain start event before the sender's send task.

**LRN-117** (T6; new; 1 description(s); confirmed: yes)  
When the description states that a participant performs an action on a request received from another participant (such as checking, examining or answering it), and the action leads to several stated alternative results, without stating that a message is sent for each result: Model the participant's action as one plain task in that participant's pool or lane, labeled with the description's own verb and object, and placed where the description places it. Model the alternative results as the outgoing branches of an exclusive gateway after that task, each branch leading to its own outcome. Do not create one send task per alternative result, and do not replace the action with a start event.

**LRN-118** (T5; new; 1 description(s); confirmed: yes)  
When the description says that when a check fails, the flow returns to an earlier step, and that same earlier step is also reached from the step that normally precedes it: Model an exclusive merge gateway immediately before the repeated step. Connect the normal predecessor and every loop-back branch from the failed checks to this merge gateway, and give the merge gateway a single outgoing flow into the repeated step. Do not connect the loop-back flows directly to the repeated step.

**LRN-119** (T5; new; 1 description(s); confirmed: yes)  
When the description says that a branch returns to a named step, and that named step is one of several consecutive actions stated together in one sentence or sequence (for example, a step described as performing two actions in a row): Place the exclusive merge gateway immediately before the named action itself, not before the first action of the sequence. Keep the preceding actions of that sequence upstream of the merge, so the normal flow passes through them into the merge. Connect the loop-back flow to the merge gateway, and let the merge's single outgoing flow lead to the named action and then to the later steps. Do not repeat the earlier actions of the sequence on the loop-back path.

## Example-specific guidelines

**EXS-002** (T6; refines EVT-01; 1 description(s); confirmed: yes)  
When the description says that a process starts when a participant performs an activity, such as identifying a need, or that a later phase begins when a participant performs an activity after a preceding step, and that activity is stated as work to be done: Model the performed activity as a bpmn:task, never as a start event. Use a start event only as the process's own trigger: if the process kicks off with that activity, put a start event at the process entry and connect it to a task for the activity. If a later phase begins after a preceding step or decision, connect that step's outgoing flow to a task for the phase's first activity, not to a new start event.

**EXS-003** (T5; new; 1 description(s); confirmed: yes)  
When the description states that an optional activity may or may not take place after a step (for example, 'X may take place'), so the activity is not guaranteed to run on every case: Model the optional activity behind an exclusive (XOR) split placed right after the preceding step. One outgoing flow leads into the optional activity and a second, unconditional bypass flow skips it. Route both paths into a second exclusive merge gateway before the next step, so the flow continues whether or not the optional activity ran. Do not connect the preceding step directly to the next step, and do not use a parallel gateway for an optional path.

**EXS-006** (T5; new; 1 description(s); confirmed: no)  
When the description presents two alternative activities that each by itself lead to the same next point, so either one is enough and the description does not require both: Model an exclusive (XOR) split before the alternative activities, with one outgoing flow into each alternative. Route every alternative into an exclusive merge gateway placed before the shared next step, so the flow continues after whichever alternative occurred. Do not connect the preceding point directly to only one alternative, and do not use a parallel gateway for alternatives that exclude each other.

**EXS-008** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When The description lists factors (for example cost, delivery time, reliability) that are weighed while an activity is carried out, and does not state them as a separate step or decision: Do not create a separate task for the listed factors. Keep them as part of the activity they qualify, such as by naming them in that task's label or in its documentation. Model a separate task only when the description states a distinct action to be performed.

**EXS-019** (T5; new; 1 description(s); confirmed: no)  
When the description lists several actions performed by the same participant in one sentence, with no order stated between them, and one of the listed actions depends on the outcome of the others (for example, it proposes something based on what the others found): Model a parallel (AND) split after the activity that precedes the list, with each action that does not depend on the others as its own task on its own branch. Close those independent branches with a parallel (AND) join, and place the dependent action as a task after that join. Do not put the dependent action on a parallel branch alongside the actions it depends on, and do not serialize the independent actions in an arbitrary order.

**EXS-022** (T5; refines GW-04; 1 description(s); confirmed: no)  
When the description states that after a development plan is created, the employee carries on several activities at the same time (such as skill work alongside receiving feedback), and that a later step starts only once milestones are reached, so it waits for those concurrent activities to complete: Right after the activity that creates the plan, place a parallel gateway that splits into one outgoing branch per concurrent activity, with no decision conditions on those branches. Connect each concurrent activity to a parallel gateway that joins them, and place that joining gateway before the later step, so the later step starts only after every concurrent branch has completed. Do not replace the split or join with an exclusive gateway, and do not let the later step follow any single concurrent branch.

**EXS-027** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description says a plan goes through one or more review rounds in which feedback is given, and that adjustments are then decided on the basis of that feedback: Model the act of giving feedback as its own task, labeled with the description's own wording for that act, placed after the review task it follows and before the exclusive gateway that decides whether adjustments are required. Route the gateway's adjustment branch as the description states, and do not fold the feedback into the review task or omit it.

**EXS-028** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a review of a deliverable is followed by a possible adjustment, that each adjustment must then be approved, and that the approved result is used for the next step: Connect each stated activity to the activity that the description places immediately after it with a sequence flow, including the flow from the review activity into the gateway that decides whether another review or an adjustment is needed, the flow from each adjustment activity into its approval activity, and the flow from the final approval into the next stated activity. When the description allows a review to repeat, add an exclusive gateway after the review that loops back to the review or continues to the next stated activity. Do not leave any stated step without its incoming flow from the preceding step or its outgoing flow to the following step.

**EXS-043** (T5; new; 1 description(s); confirmed: no)  
When the description says that after a payment request is sent to a party, a reminder is to be set up, and that if the expected payment has still not arrived when the deadline is reached, the case is forwarded to another party: Model the reminder as an intermediate timer catch event that fires at the deadline. Place it in the waiting sequence after the request step, as the timer branch of the event-based gateway that also has the response branch, and connect it directly to the follow-up action the description attaches to the deadline. Do not model the reminder as an ordinary task, and do not omit it so that the gateway branch leads straight to the follow-up action.

**EXS-045** (T5; refines EVT-03; 1 description(s); confirmed: no)  
When the description states that a process waits for either a party's response or a time-based event such as a reminder or a deadline, and the time-based event itself leads to a further activity: Model the waiting point as an event-based gateway with one outgoing branch per possible event. Model each time-based event (reminder or deadline) as an intermediate timer catch event placed directly after the gateway, and give that timer event its own sequence flow into the next activity it leads to. Do not route the timer branch through an exclusive gateway that only merges it with other paths, and do not add a decision gateway unless the description states a decision.

**EXS-046** (T6; refines EVT-01; 1 description(s); confirmed: no)  
When the description opens with a conditional statement that decides whether the case is handled at all (for example, "if a possibility arises, I get information about it") before any activity is described: Model that opening condition as a start event of the process, placed before the first task that acts on the case. Do not omit it, and do not encode it as a gateway or as a task placed before the start.

**EXS-049** (T7; refines ACT-05; 1 description(s); confirmed: no)  
When the description says a participant performs a named action directed at a separate participant (for example setting off a signal, calling someone over, or handing something on), and that other participant then reacts to it as a separate step: Model the acting participant's action as a task in that participant's own pool, labeled with the description's wording for the action. Draw a message flow from that task to the catch event (or receive task) in the reacting participant's pool that handles the reaction. Do not model the action as a send task paired with a separate receive or catch event for the same action, and do not add an extra catch event that re-states the reaction.

**EXS-050** (T5; refines ACT-05; 1 description(s); confirmed: no)  
When the description says one participant informs a colleague that a step is finished, and no separate participant pool is described for the recipient: Model the informing as a plain task in the informing participant's lane, labeled with the verb and object the description uses for that act. Do not model it as a send task. Use a send task only when the description says the message is transmitted to another participant's pool.

**EXS-053** (T5; refines ACT-05; 1 description(s); confirmed: yes)  
When the description says a participant is told by another participant's action (a notice or message) that a state has been reached, and the process then continues with further steps of the first participant: Model the moment the participant learns of that state as an intermediate catch event in the receiving participant's lane, placed at the position the description gives and labeled with the notice's content. The notifying action is a task in the notifier's lane linked to this event. Do not model the milestone as an end event, because the process continues after it.

**EXS-054** (T6; refines EVT-03; 1 description(s); confirmed: yes)  
When the description says a participant holds at a point until a condition is reached, such as until its turn comes or until it is reported that something is ready, and further steps of the process follow after that point: Model the hold as an intermediate catch event in the flow of the participant that holds, placed at the position where the hold occurs and labeled with the condition as the description states it. Connect it with sequence flow so the following steps continue from it. Do not model the hold as a task, which implies work being performed, and do not model it as an end event, because the flow continues after the condition is reached.

**EXS-055** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description states that a party performs a specific action or transition on an object using a particular verb (for example, 'you enter the ... phase' or 'you rate the ...'), and the generated task for that step is labeled with a different verb or a different object, such as one for completing, reviewing or viewing a related thing: Model the task with the verb and object the description uses for that action or transition, keeping the stated verb (for example enter, start, rate or submit) and the stated object. Do not replace it with a verb for finishing, reviewing or viewing the same stage, and do not substitute a related but different object, such as a job offer for a job application or reviews for the company itself.

**EXS-056** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description lists several distinct kinds of occurrence that one actor must all notify to the same recipient, and the steps that follow depend on which kind occurred: After the notifying task, model an exclusive gateway that classifies which kind of occurrence has been reported. Give it one outgoing branch per kind listed in the description, and let each branch continue with the follow-up stated for that kind. Do not place the later condition gateways directly after the notifying task, because that leaves the classification implicit.

**EXS-057** (T6; new; 1 description(s); confirmed: no)  
When the description makes a branch depend on an event together with a status that the affected party must have, for example being insured or a severity threshold that applies only to some parties, so the decision tests both conditions at once: Name the exclusive gateway with a question that states the triggering event and the required status together, using the description's own terms. Make each outgoing flow test that same combined criterion, with one flow for each outcome. Do not name the gateway after only one of the two conditions, and do not leave one condition implicit in the flow labels.

**EXS-058** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description lists several kinds of occurrence that the actor must each report, and a different reporting obligation (recipient, deadline, or form) is stated for at least one of those kinds: Model an exclusive gateway after the step in which the actor first reports the occurrence, with one outgoing flow per kind of occurrence, each labeled with that kind's condition in the description's own wording. Place each kind's stated follow-up reporting task (or its end) behind its own flow, labeled with that obligation's wording, so that the deadline, recipient, or form applies only to its kind. Do not place these follow-up reports in an unconditioned sequence, do not join them into one task, and do not connect them with parallel flows.

**EXS-059** (T6; refines FID-02; 1 description(s); confirmed: no)  
When the description states that a party must notify an external body or insurer about an event under one stated condition, and states a separate notification duty for the same event under a different stated condition, each with its own deadline or recipient: Model each separately stated notification duty as its own task, labelled with the description's notification wording, placed in the branch where its condition holds and after the gateway that tests that condition. Do not let one notification task stand in for a duty with a different condition, and do not leave out a duty whose condition is stated separately.

**EXS-060** (T5; refines FID-01; 1 description(s); confirmed: no)  
When the description states that one participant must report several kinds of occurrence, and after that report the kinds differ in their further steps, some requiring a separate follow-up step and others requiring none: Model an exclusive (XOR) gateway directly after the reporting activity. Give it one outgoing flow per kind stated in the description, labeled with the condition that distinguishes that kind. Each flow leads either to the follow-up activity for that kind or to the shared continuation when that kind has no further step. Do not replace this gateway with a user activity that only classifies the occurrence, and do not put the follow-up activities before the gateway.

**EXS-061** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description states a required action toward a named party (such as an insurer, authority or employer) and attaches to that action a time limit or a list of qualifying criteria: Label the task with a short verb-object phrase that names the required action and the receiving party, in the description's own wording. Keep the time limit and the qualifying criteria out of the label. Do not copy a full list entry or a deadline phrase into the task name.

**EXS-064** (T5; new; 1 description(s); confirmed: yes)  
When the description says the user can check whether they already have a required item or status (such as an account or an active subscription), and the next step depends on the result of that check: Model the check as a service task placed directly before an exclusive gateway whose outgoing flows cover the has-item and does-not-have-item outcomes. On the does-not-have-item branch, model the supplying of the missing item as its own user task when the description says the user must provide it, and route that task into the step the description names next. Do not drop the check or connect the negative branch past the dependent step.

**EXS-071** (T5; new; 1 description(s); confirmed: no)  
When the description says that a request or instruction sent to an outside party is repeated, with the process waiting for each reply, until a satisfaction condition is met, so that the process loops back to the repeated request after an unsatisfactory reply: Model each repeated request as an activity whose reply is awaited by an intermediate message catch event, followed by an exclusive gateway that decides whether the process is satisfied. Place an exclusive merge gateway before the repeated request activity, so that the first entry into the loop and the return from the 'not satisfied' branch both enter it. Connect the 'not satisfied' outgoing flow of the decision gateway back to that merge gateway, and leave the 'satisfied' outgoing flow to continue the process. Do not connect the decision gateway directly to the request activity without a merge, and do not omit the wait before the decision.

**EXS-073** (T5; refines FID-02; 1 description(s); confirmed: no)  
When the description states that each of several separately built items is then tested individually, with the build and test of each item following in a stated order, and the items are brought together only after their tests: Model each item's stated sequence (build, then test) as its own task pair inside a parallel branch, one branch per item, with each test as a separate task. Open the branches with a parallel split and close them with a parallel join before the step that brings the items together, so that this step starts only after every item has been built and tested. Model the test outcome of each item as an exclusive gateway: the successful outcome continues toward the joining step, and the unsuccessful outcome loops back to the redesign and rebuild activity for that item. Do not collapse the per-item builds and tests into one task, and do not place the joining step after a single branch.

**EXS-076** (T6; new; 1 description(s); confirmed: no)  
When the description says a product is made of several components, each component is produced by an activity and then checked on its own, and a later assembly step is performed only if every check succeeds, with failed components sent back for rebuilding: Model one produce-then-check pair of tasks per component, each pair in its own branch. Start all component branches with a parallel (AND) split gateway and close them with a parallel (AND) join gateway. After the join, place an exclusive decision gateway on the overall check outcome: the success flow continues to the assembly step, and the failure flow returns to the rebuild task of the failed components. Do not model all components with one generic produce task and one generic check task, and do not use exclusive gateways for the split or the join.

**EXS-082** (T6; refines FID-03; 1 description(s); confirmed: yes)  
When The description names a step with a verb and an object (for example 'send X to Y', 'deliver X to Z', 'perform a test X'), and the generated label would change that verb, use a synonym, or drop a qualifier the description states: Label the task with the verb the description uses for that step and the object with its stated qualifiers (for example a 'test' qualifier), so the label keeps the described action and direction. Do not swap the verb for a near-synonym or a different activity type, and do not shorten the object by dropping a stated qualifier.

**EXS-083** (T6; refines ACT-04; 1 description(s); confirmed: no)  
When the description says the process sends the same information or material to several different parties, each of which carries out a different piece of work on it: Model one send task per receiving party, in the order the description gives, each labeled with what is sent and to whom. Give every party named in the description its own send task, and do not merge the dispatches into one element or leave one party out. Choose the element type from the direction of the verb: a send verb gets a send task, not a receive task or a manual task.

**EXS-084** (T5; refines ACT-04; 1 description(s); confirmed: no)  
When the description says the participant itself must query several external suppliers to learn their available quantities, cost and lead times before choosing among their answers: Model the querying as a user task performed by the participant, placed before the exclusive gateway that decides among the answers. Do not model it as a receive task, since the participant's own inquiry is the unit of work and the wait is not the modeled activity.

**EXS-094** (T6; new; 1 description(s); confirmed: no)  
When the description states that the actor carries out an activity after receiving or being offered something from another party (for example, an offer to help, or instructions to follow), and the activity itself is work the actor performs: Name the activity after the action the actor performs (for example, contacting a party or carrying out the work), not after the information received. Model the received information as data or as the input of that activity, and use a manual or user task according to who performs the work. Keep the label in the description's own verb and object wording.

**EXS-095** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description says the user may optionally obtain an item from another party, such as by asking a contact for an offer, and otherwise obtains it through another route, so the user first decides whether to pursue that optional route: When the user can choose whether to use an optional route that requires waiting for another party's reply, model an exclusive gateway before the wait. One outgoing branch leads to the wait for the reply, and the other branch leads to the alternative route the description gives. Keep the decision as its own gateway so the wait is reached only when the optional route is chosen.

**EXS-097** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that a participant must enter several separate pieces of information one after another, each of which is a distinct input: Model a separate user task for each distinct piece of information the participant enters, and label each task with the single item that task asks the participant to enter. Do not label one user task with a combined list of several items, and do not label a task with a generic or merged phrase that covers more than one input.

**EXS-098** (T5; new; 1 description(s); confirmed: yes)  
When the description states that data is collected automatically from an external device or system after the user has entered identifying details for that device (such as its type and serial number): Model a service task that establishes the connection to that device. Place it in sequence after the user task where the identifying details are entered and before the service task that performs the automatic data collection. Do not start the automatic collection directly from the identifying-data entry. Keep the connection step distinct from the user-performed steps, and do not add gateways or other elements that the description does not state.

**EXS-103** (T6; new; 1 description(s); confirmed: no)  
When the description says a visit by an outside party may end with the work still unfinished because something is still needed, so a later visit is required, and it describes an optional follow-up, such as a rating, that comes after the work is completed: After each such visit, model an exclusive gateway placed directly after the visit and before any optional follow-up. Its question asks whether the work is finished on this visit. The not-finished branch returns to the event or task that waits for the next visit. The finished branch continues to the optional follow-up, and the process then ends with an end event. Do not place this completion decision after the optional follow-up, and do not leave the not-finished branch without a path back to the waiting step.

**EXS-104** (T6; new; 1 description(s); confirmed: no)  
When the description states that a consequence is imposed on the user by the system when an obligation is not met within a stated period after a point in the process: Model the stated period as a timer intermediate catch event on the branch that starts at that point, and let the branch where the obligation is still unmet continue from that timer. Model the imposed consequence as a service task that the system performs on that branch, and end the process with an end event after that task. Do not replace the consequence with an end event that carries only its outcome label, and do not drop the consequence.

**EXS-107** (T5; new; 1 description(s); confirmed: yes)  
When the description says a participant asks another party a question while an earlier activity is still running, and the answer decides which of several alternative paths is taken next: Model the asking and recording of the answer as a userTask performed by the participant who records the answer, placed in the branch where the question is asked, directly before the exclusiveGateway that branches on that answer, and connect it in sequence. Do not model the question as a plain task without a user performer, and do not let the decision follow a task that does not capture the answer. Keep each question as its own userTask, so that each choice has a distinct element.

**EXS-108** (T6; new; 1 description(s); confirmed: no)  
When the description states a question that a person asks, with two named options as the possible answers, and the answer determines which activity follows; the question is stated while another activity is in progress or as a step in the sequence: Model the question as one exclusive gateway at the point in the sequence where the description states it. Label the gateway with the question in the description's own wording, including both options (for example 'X or Y?'). Label each outgoing branch with the option it represents. Do not create a separate task whose label restates the question, and do not place the gateway before or after the activity the description ties it to.

**EXS-128** (T6; new; 1 description(s); confirmed: no)  
When the description states that one participant sends a request to another participant, that the receiving participant examines the request, and that it then gives an answer to the request that depends on the examination outcome, with each outcome described as its own answer: Model the sending of the request as its own task in the sender's pool or lane, placed before the receiver's examination, and connect it to the receiver with a message flow. Model the examination as one task in the receiver's pool. After it, place an exclusive gateway on the examination outcome. Model each stated answer as its own task in the receiver's pool on the gateway branch that leads to it, labeled with the description's verb and object, and let the branch continue from that answer task. Do not replace the sending step with a start event that only names receipt, and do not end a branch at an end event or a bare flow label without the stated answer task.
