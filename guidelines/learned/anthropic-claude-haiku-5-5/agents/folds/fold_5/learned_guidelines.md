# Learned guidelines: Claude Haiku 5.5, Reuse training, round 5 (44 descriptions)

121 generic and 47 example-specific error-driven guidelines; 69 generic guidelines confirmed. Full records (evidence, confirmation tests, provenance): `learned_guidelines.json`.

## Generic guidelines

**LRN-019** (T5; refines GW-04; 8 description(s); confirmed: yes)  
When the description lists two or more activities that follow one step or act on the same item, and it states no order among them, only that they are performed to be completed before a later step: Model these activities as the outgoing branches of a parallel gateway that opens them all, and close them with a parallel gateway that joins all branches before the next step that depends on their completion. Do not sequence them one after another and do not add decision conditions to these branches.

**LRN-003** (T5; refines FID-02; 4 description(s); confirmed: yes)  
When the description names several actions within one phase in a comma-separated or 'and'-joined list, such as 'A, B, and C', or joins two actions with 'and' in one clause: Model each listed action as its own task, in the order the description states them, connected by sequence flows. Do not combine the listed actions into one task label, and do not drop any action from the list.

**LRN-006** (T5; refines GW-05; 4 description(s); confirmed: yes)  
When the description lists several activities of a stage with no order stated between them, and the stage or the process ends only after all of those activities are finished: Model a parallel gateway directly after the task that starts the stage or precedes the list. Fork it into one task per listed activity, each as its own task with the action the description gives for it. Connect every one of those tasks into a second parallel gateway that joins them. Place the join before the next step or the end event, and connect it onward from there. Do not chain the unordered activities in sequence, and do not use an exclusive gateway for either the fork or the join.

**LRN-009** (T6; refines GW-04; 4 description(s); confirmed: no)  
When the description states that an activity is carried out alongside a monitoring or follow-up activity that runs at the same time (joined by 'and' or 'while'), and a later step is reached only after both are finished: Model a parallel gateway that splits into the concurrent activities, and a parallel gateway that joins them before the next step. Do not model the concurrent activities as one sequential chain, and do not add conditions to the branches.

**LRN-065** (T5; refines GW-05; 4 description(s); confirmed: yes)  
When the description states that one step requires several concurrent activities or several parties to be handled together, and a later point is described as needing all of them finished or available: Model each concurrent activity or party as its own branch after a parallel gateway fork, with its own task or event in each branch, and close the branches with a parallel gateway join before the later point. Do not collapse the branches into one activity, do not let a single branch continue alone, and do not use an exclusive gateway for a join where every branch must complete.

**LRN-001** (T5; refines ACT-07; 3 description(s); confirmed: no)  
When the description states that a step is performed only if a condition holds, introduced by a conditional phrase such as 'If ..., they are ...' or 'If ..., the process ...': Model an exclusive gateway immediately before that conditional step. Give it one outgoing sequence flow to the conditional step and one to the alternative path, which may skip to a later point or end the process. Route both branches back into the main flow with an exclusive join where they reconverge.

**LRN-002** (T5; refines ACT-07; 3 description(s); confirmed: yes)  
When the description states that a later step is performed only if a stated condition holds, using an 'if ... then' phrasing that gates that step on a decision made earlier in the process: Model an exclusive gateway immediately before the gated step, with one outgoing branch that leads to the gated step under the stated condition and another branch that skips it or leads to the process's alternative path. Keep the gateway after the activity that establishes the condition, so the decision is evaluated in the order the description gives.

**LRN-004** (T6; refines EVT-01; 3 description(s); confirmed: yes)  
When the description says the process starts when a party (such as a department) performs a stated action, for example identifying a need, before any further work is described: Model a start event for the triggering occurrence, and place a separate task directly after it that is named with the action the party performs. Do not fold that action into the start event's label. Connect the task to the next step of the described flow.

**LRN-007** (T5; refines GW-03; 3 description(s); confirmed: yes)  
When the description offers an either-or choice between two named ways of carrying out one step (for example 'X or Y'), and both ways continue to the same following step: Model each named way as its own task or path. Place an exclusive gateway before the alternatives to split the flow, with one outgoing branch per alternative. Join the alternative branches with an exclusive gateway before the common next step. Do not drop an alternative, and do not collapse the alternatives into one generic activity.

**LRN-018** (T6; refines FID-02; 3 description(s); confirmed: yes)  
When the description states that the flow terminates in one of two alternative actions performed on the subject, with each action named in the description: Place an exclusive gateway at the point where the alternative is chosen. After each branch, model the named action as its own task, labeled with the action the description names, and connect that task to its own end event. Do not model an action only as an end event labeled with the resulting state, and do not merge the alternative action tasks into one task.

**LRN-035** (T6; refines FID-03; 3 description(s); confirmed: yes)  
When the description names an activity or outcome in a short phrase, and a generated task or event label adds qualifiers such as the time period, the recipient, or a status that the description does not use as the activity's name: Label the task or event with the core verb-object action or outcome that the description names, and omit added qualifiers (periods, recipients, statuses) unless the description uses them as part of the activity's name.

**LRN-043** (T5; refines ACT-05; 3 description(s); confirmed: yes)  
When the description states that a participant itself receives or confirms the result of a step, and a next action follows directly after it, with no stated waiting time and no external message or condition the process waits for: Model that result as a task carried out by the participant, placed in the sequence before the next action. Use an intermediate catch event or an event-based gateway only when the description states that the process waits for an external message, signal, time or condition.

**LRN-050** (T5; refines GW-05; 3 description(s); confirmed: yes)  
When the description states that several activities are carried out side by side (linked by 'while', 'and', or 'in any order') and a later step may only be reached once all of them are complete: Model each of the side-by-side activities as its own task, each on a separate branch opened by a parallel split gateway. Close all branches with a parallel join gateway before the later step, so the next step waits for every branch. Do not merge the activities into one task or subprocess, do not drop any of them, and do not insert an exclusive gateway or decision condition among the branches.

**LRN-094** (T5; refines EVT-03; 3 description(s); confirmed: yes)  
When the description says that after a prior step, the process must wait for an external party to respond or arrive at a time not fixed in advance, and a later step or decision depends on that response or arrival: Model an intermediate catch event that represents the wait between the prior step and the dependent step or gateway. Do not fold the waiting into the prior task, do not model the wait as a separate task, and do not connect the two steps with a plain sequence flow that hides the wait.

**LRN-008** (T5; new; 2 description(s); confirmed: yes)  
When the description says that an activity follows the receipt of an item or delivery (for example 'upon receiving X, ...'), and it does not describe any message, signal, time or condition that the process waits for: Do not insert an intermediate catch event for the receipt. Connect the preceding activity directly by a sequence flow to the first activity the description gives after the receipt. Use an intermediate catch event only when the description states a wait for an external message, signal, timer or condition.

**LRN-010** (T5; refines GW-05; 2 description(s); confirmed: yes)  
When the description states that two or more activities are carried out at the same time (one of them ongoing, such as monitoring, while others such as follow-up or analysis run in parallel) and a later step, such as the closing of the process, is described only after these activities are complete: Open the concurrent activities with a parallel gateway (split), so that all branches start. Close the branches with a parallel gateway (join) before the step that follows them, and connect the join to the concluding step with a sequence flow. Do not use exclusive gateways for these branches, and do not add conditions to the parallel flows.

**LRN-012** (T6; refines EVT-03; 2 description(s); confirmed: no)  
When the description says the process waits until an external milestone is reached (for example, an item arriving at a recipient's location) and later steps depend on that milestone having occurred: Model the wait as an intermediate catch event, not a task, and name that catch event with the milestone as the description states it, so the stage stays identifiable in the model. Do not replace the wait with a task, and do not leave the milestone unnamed or rename it to a generic label.

**LRN-015** (T6; refines FID-02; 2 description(s); confirmed: yes)  
When the description applies one action verb to several named objects joined by 'and' or 'or' within one sentence, such as 'X and Y' or 'X or Y' used as the objects of that action, so each named object is a separate thing the action is performed on: Model each named object as its own task, with the action label taken from the description and the object named separately, placed in the order the description gives. Do not merge the named objects into one combined task label, and do not drop any of them. If the sentence makes the whole group optional, place each of these tasks in the branch that the optional-step gateway controls.

**LRN-017** (T5; new; 2 description(s); confirmed: yes)  
When the description ends the process with a choice between alternative outcomes, each stated as an action performed on the handled object, and the outcomes do not lead back into the flow: Place an exclusive gateway after the last step that produces the choice, with one outgoing branch per stated outcome. On each branch, model the outcome's stated action as its own task on the handled object, and follow that task with its own end event. Do not connect the gateway directly to end events, and do not drop any outcome.

**LRN-022** (T5; refines GW-04; 2 description(s); confirmed: yes)  
When the description lists several actions that all occur after one completed step, with no condition choosing among them, and a later step is reached only after all of those actions are finished: Model a parallel gateway split directly after the completed step, with one outgoing sequence flow to each listed action, and a matching parallel gateway join that collects those actions before the later step. Do not use an exclusive gateway or a condition on these branches.

**LRN-023** (T6; new; 2 description(s); confirmed: yes)  
When the description says the process begins when a participant performs an action (for example, filling in information or signing up) that is followed by further system activity: Model the process start as a plain start event, then model the participant's described action as a task placed after it and before the next system activity. Do not use the action as the label of the start event.

**LRN-044** (T6; refines EVT-01; 2 description(s); confirmed: no)  
When the description states a customer report or external occurrence that happens partway through the process, after an earlier step such as delivery, rather than as the event that starts the process: Do not model such an occurrence as a start event. Start events are only for triggers that begin the process. Model the mid-process occurrence as an intermediate catch event at the point where it happens, and keep the step that follows it as a separate activity.

**LRN-049** (T5; new; 2 description(s); confirmed: no)  
When the description states that when a check finds a condition not met, a task is performed to correct the item, and the process then goes back to repeat that same check before continuing: Model the check as an exclusive gateway with one branch to the correction task and one branch onward to the next step. Connect the correction task's outgoing flow back into an exclusive gateway (merge) placed before the check, so that the check is repeated. Do not connect the correction task directly to the next step, do not omit the merge, and do not add a parallel gateway to this loop.

**LRN-054** (T7; refines COL-07; 2 description(s); confirmed: yes)  
When the description says one participant asks several outside parties to return a response and then picks one of those responses, and gives no steps for the outside parties beyond returning their response: Model the request and the selection as tasks in the lane of the requesting participant, in the order the description states them, with a gateway only if the outcome branches. Do not create a separate pool for the outside parties and do not add message flows to or from them. Use a separate pool with message flows only when the description gives the outside parties their own steps or treats them as independent communicating participants.

**LRN-062** (T6; new; 2 description(s); confirmed: yes)  
When the description states that a party may optionally carry out an activity between two steps, and names no message, signal, time or condition that the process waits for: Model that activity as exactly one task performed by that party, placed in the sequence where the description places it, and label it with the action verb and object the description states. Do not model it as an intermediate catch event that waits for it, and do not add a second element (such as a manual task) for the same activity.

**LRN-063** (T6; refines ACT-02; 2 description(s); confirmed: no)  
When the description states that a person themselves selects an option or makes a decision, and it mentions no software, system, form or application that supports that choice: Model that step as a bpmn:manualTask performed by that person, placed where the description places it and labeled with the action verb and object the description states. Do not model it as a bpmn:userTask unless the description names software or a system that assists the step.

**LRN-069** (T5; refines FID-01; 2 description(s); confirmed: no)  
When the description says that a participant enters one or more items of information, each stated in its own sentence or clause, as input the participant performs before later steps use these values: Model each stated input item as its own bpmn:userTask performed by that participant, one task per item, in the order the description gives. Place these tasks before the tasks that use the entered values. Do not omit an item and do not merge several items into one generic input task.

**LRN-072** (T6; refines GW-07; 2 description(s); confirmed: no)  
When the description says the process waits for a response from an outside party or group, or until a period of time or a later point in time has passed, whichever comes first, before it continues to a decision or the next step: Model the wait as an event-based gateway. Give one branch an intermediate message catch event for the expected response. Give the other branch an intermediate timer catch event for the stated duration or point in time. Place any step the description ties to the timeout (for example, escalating or forwarding) after the timer event. Do not model the wait as an extra task or as sequential catch events, because the description states a race between the two outcomes.

**LRN-074** (T5; refines EVT-03; 2 description(s); confirmed: no)  
When the description says a process sends a request to, or depends on, an outside participant, and the next step may only begin after that participant replies, delivers a list, or reaches a stated agreement, with no timer or alternative path named for the wait: Model the wait as an intermediate catch event that receives a message flow from the send task of the outside participant's pool, placed between the requesting activity and the dependent step. Do not model the wait as an extra task or as a plain sequence flow from a task in the same pool. If the description says an activity continues while the process waits, keep that activity in parallel with the catch event. Place the sending and receiving elements in different pools so the message flow is valid.

**LRN-107** (T6; refines PROC-04; 2 description(s); confirmed: yes)  
When the description states that an exclusive decision has an alternative branch in which an actor performs a described action (for example taking an item away or declaring an activity finished), and the description does not say that this branch ends the whole process: Model the alternative branch as a task labeled with the actor and the described action, placed after the decision gateway. Route its outgoing flow into the merge gateway that joins the branches before the shared continuation, instead of giving it its own end event. Use a separate end event only for an outcome the description explicitly presents as terminal.

**LRN-005** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description says that a stage begins after a preceding step is accepted, names the stage's start, and then lists several separate activities that the stage includes, with the stage ending only after those activities are finished: Model a separate task that represents starting the stage, placed directly after the preceding step, and label it with the start verb the description uses for the stage (for example 'Begin ...'). Then model each listed activity as its own task after it, labeled with the action the description gives for that activity. Do not label any listed activity with the stage-start verb, and do not let the starting task stand in for one of the listed activities.

**LRN-011** (T6; refines EVT-03; 1 description(s); confirmed: no)  
When the description says the process concludes when a time period or an external condition ends, so the flow must wait for that moment before the process ends: Model the wait for the period or condition to end as a bpmn:intermediateCatchEvent (timer or condition as appropriate) placed directly before the end event, not as a bpmn:task. Do not use a task to represent a wait.

**LRN-013** (T6; refines FLOW-07; 1 description(s); confirmed: no)  
When the description says an activity is carried out repeatedly until a stated condition is reached, so the activity repeats until the condition holds, and the process moves on only after that point: Model the repeated activity as a single task, followed by an exclusive gateway that checks whether the stated condition has been reached. Give one outgoing sequence flow that loops back to the repeated task while the condition is not met, and one outgoing sequence flow that leads to the next step once it is met. Do not model the repetition as an unconditional sequence of separate tasks, and do not leave the exit condition implicit.

**LRN-014** (T5; new; 1 description(s); confirmed: yes)  
When the description says the process ends after a participant carries out a stated activity, and it names no message, signal, timer or condition that the process waits for: Model that activity as a task in the participant's pool or lane, placed before the end event and connected by sequence flows. Do not model it as an intermediate catch event. Use an intermediate catch event only where the description states a wait for an external message, signal, time or condition.

**LRN-016** (T6; new; 1 description(s); confirmed: no)  
When The description states that an activity may happen only in some cases (for example, "may receive" or "may be sent") and the process continues the same way whether or not it happens: Model the activity as an optional branch: place an exclusive gateway before the activity to decide whether it runs, add a bypass sequence flow around it, and close both paths with an exclusive gateway before the next step. Give the decision a condition that matches the description's wording.

**LRN-020** (T5; refines ACT-04; 1 description(s); confirmed: yes)  
When the description says the process starts when a party performs a stated action (for example, submitting something) and names no message, signal, or other message exchange that the action sends: Model the process start as a bpmn:startEvent with no incoming sequence flow. Place a plain bpmn:task (not a bpmn:sendTask) for the party's action directly after the start event, and connect it by a sequence flow to the next step of the described flow. Do not add a second start event for the action, and do not add an end event after the action.

**LRN-021** (T6; refines ACT-04; 1 description(s); confirmed: no)  
When the description says a participant submits or raises a request that starts the process, as an action the participant performs (for example filling in and submitting a request), not as a message the process sends to another system or party: Model that submission as a plain bpmn:task (performed work) that comes after the single process start event and before the parallel split into the assessment branches. Do not model it as a bpmn:sendTask, and do not give it its own start or end event.

**LRN-024** (T6; new; 1 description(s); confirmed: no)  
When the description states that, depending on a condition, several different actions may be carried out, and the wording allows all of them to happen together rather than selecting one: Place a split gateway after the point where the condition is evaluated. Use an inclusive gateway when the wording allows any combination of the actions, including all of them. Give each action its own outgoing branch with a condition that matches the description's wording. Join the branches with a matching inclusive merge before the next step. Use an exclusive gateway only when the description frames the choice as one outcome among alternatives.

**LRN-025** (T1; refines XML-06; 1 description(s); confirmed: yes)  
When The description names a message that a process event sends or waits for, so the model needs a message event definition: Place the event's name on the event element itself (or on a referenced bpmn:message element). On the bpmn:messageEventDefinition, set only its id and messageRef attributes, and never give it a name attribute, because the BPMN 2.0.2 XSD does not allow one.

**LRN-026** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a review leads to an approval decision, that only the approved outcome is then carried out, and that the approved outcome consists of several actions that must all be done before the process moves on: Model the review as a task, and the approval decision as an exclusive gateway with a conditioned approved branch and a separate non-approved branch that ends in its own end event. On the approved branch, first place a task that carries out the approval, then open a parallel gateway that splits into one task per required action, and close those tasks with a matching parallel gateway join before the next step. Do not skip the approval task or route the approved actions directly from the decision gateway.

**LRN-027** (T5; refines GW-04; 1 description(s); confirmed: no)  
When the description states that work on one activity continues in parallel with another activity or feedback stream, and it states no condition, decision or criterion at the point where those concurrent branches split or rejoin: Model the split with a parallel gateway and close the concurrent branches with a matching parallel gateway that waits for all of them. Do not insert exclusive gateways at the split or join, and do not add condition labels to these branches. Use an exclusive gateway only where the description names a decision with alternative outcomes.

**LRN-028** (T5; refines PROC-04; 1 description(s); confirmed: no)  
When the description states a review or approval outcome that can be approved or not approved, where the approved outcome leads to a finalization activity and the not-approved outcome ends the process on a separate branch: Model the outcome as an exclusive decision gateway placed directly after the review activity, with one outgoing flow for each outcome. Give the not-approved flow its own terminal end event. Do not route the approved flow to a termination or a shared end before the finalization activity. Use an exclusive gateway only where the outcome selects one branch, and do not add it to parallel branches.

**LRN-029** (T5; refines FLOW-06; 1 description(s); confirmed: yes)  
When the description states that a decision outcome is communicated to a participant, and one outcome requires a further processing step while the other outcome only needs its own notice, with both paths then leading to a common closing step: Model each outcome as its own branch. Place an exclusive gateway after the decision has been determined, and give each outcome flow a condition that matches the description's wording. Put the outcome-specific notice task on the branch whose outcome needs it, and do not reuse one shared notice task for both outcomes. Place the further processing step after the notice for the outcome that requires it, connected by a sequence flow. Reunite the branches with an exclusive join gateway before the common closing step or end event. Do not leave a branch without a continuation.

**LRN-030** (T6; refines ACT-05; 1 description(s); confirmed: yes)  
When the description states that, after the case has been closed, an outside participant can optionally perform an action such as giving a response or input, and the description describes this as something the participant does rather than something the process waits to receive: Model this optional action as a task performed by that participant, placed in the participant's pool or lane and connected after the closing step. Do not model it as an intermediate catch event that waits for a message, and do not add a receive event that the process must wait on.

**LRN-031** (T5; refines GW-03; 1 description(s); confirmed: no)  
When the description states that one of several alternative outcomes (each branch ends in its own step) is followed by one shared activity or end, and only one of those outcomes has to occur before that shared step: Model each alternative outcome as its own branch, then join the branches with an exclusive gateway used as a merge placed before the shared following activity or end event. Do not add an intermediate catch event in only one branch to wait for a notice that the other alternative does not wait for, and do not add an extra end event for a branch that only leads to the shared step.

**LRN-032** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description says the process ends when some occurrence happens, and in the same sentence it names a participant who then begins or carries out a further action (for example, putting a decision into effect): Do not place the end event directly after the occurrence named as the end condition. Model the participant's described further action as its own task, connected by a sequence flow from that occurrence and followed by the end event. Keep the end event after that task so the action is not dropped.

**LRN-033** (T5; refines FID-02; 1 description(s); confirmed: yes)  
When the description ends the process with a hand-off step, and then states that the recipient goes on to carry out a further action: Model that stated further action as its own task, placed after the hand-off task and before the end event, and label it with the action the description names. Do not fold this action into the end event's label, and do not let the hand-off task stand in for it.

**LRN-034** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a review stage produces feedback, and a later exclusive choice decides whether further changes are needed in response to that feedback: Model the handling of the feedback as its own task placed after the review task and before the exclusive gateway that decides whether changes are required. Route the gateway's changes-needed branch back to the revision work and its no-changes branch onward, so the feedback is processed as a distinct step before the decision.

**LRN-036** (T5; refines FID-01; 1 description(s); confirmed: yes)  
When the description says the process begins when a participant performs a named action, and that same action is also described as a step the participant carries out: Model a start event that marks the beginning of the process, followed by a task that carries the named action as an activity. Do not use the start event's label as the only representation of that action, so the action appears as a task in the flow.

**LRN-037** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that a group's preparation work is completed before a separately described activity that a different party carries out, and that this party's later review of findings is a distinct step: Model the activity that the other party carries out as its own task. Place it after the join that completes the preparation work and before the task for reviewing findings, with sequence flows connecting them in that order. Do not merge this activity into the review task, and do not drop it because the review task seems to cover the same party.

**LRN-038** (T5; refines FID-02; 1 description(s); confirmed: yes)  
When the description mentions an activity only inside a phrase that orders other steps (such as a timing reference placed before or after other steps), and that activity is itself performed between the steps it is positioned between: Model the mentioned activity as its own task. Place it in the sequence between the step that precedes it and the step that follows it, and connect them with sequence flows so the preceding stage flows into it and it flows into the following step. Do not omit it because it appears only as a timing reference, and do not merge it into the neighbouring tasks.

**LRN-039** (T3; refines PROC-05; 1 description(s); confirmed: yes)  
When the description states that a conditional branch sends a request to another party and that the process continues only after that party's response, with the response then leading on to the activity that follows the branch: When a conditional split leads to a request and a later response, model the response as an activity that receives its own incoming sequence flow from the split and sends a sequence flow onward to the merge point where the unconditional path rejoins. Join the no-issue path and the response path with a gateway before the next activity, so that no response activity forms a separate start-to-end chain.

**LRN-040** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description says a reviewer may either approve an item or send it back for rework, and the send-back branch is followed by a further action and then by a resubmission for another review of the same item: Place an exclusive gateway at the decision point, with one outgoing branch per outcome the description names. On the approval branch, model the approval as its own task on the item. On the send-back branch, model the return action the description names as its own task, then model the rework as a separate task, then model the resubmission as its own task that leads back to the same review step. Do not merge the return action and the rework into one task, and do not label the rework task with the name of the return action.

**LRN-041** (T5; refines FID-01; 1 description(s); confirmed: yes)  
When the description states that, after an ordered sequence of earlier steps has finished, one further action is performed that concludes the whole process (for example 'the whole process is then wrapped up'): Model the stated concluding action as its own task placed after the last preceding step and before the final end event, labeled with the action the description gives. Do not replace it with an end event alone, and do not drop it or merge it into the label of an earlier task.

**LRN-042** (T5; refines SUB-03; 1 description(s); confirmed: yes)  
When the description states that a conditional branch starts a named activity, and the steps it involves are described as its contents rather than as steps of the main flow: Model the named activity as a single task on that conditional branch, connected by sequence flows to the surrounding gateways. Do not replace it with an embedded subprocess that has its own start and end events, and do not lift its listed contents into the main flow as separate branches unless the description sequences them as main steps.

**LRN-045** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description names alternative outcomes of one activity, joined by 'or', where only one of the alternatives will be carried out: Model each named alternative as its own task placed after an exclusive gateway that splits the flow, and do not merge the alternatives into one task whose label lists them all.

**LRN-046** (T6; refines ACT-07; 1 description(s); confirmed: no)  
When the description says a required action by a participant must be completed within a stated time limit, and a different outcome applies when that action is not completed in time: Model an exclusive gateway directly after the action that the time limit applies to. Give one outgoing flow that continues the normal process when the action is completed in time, and one outgoing flow that leads to a separate terminal end event for the alternative outcome. Do not fold the alternative outcome into the normal continuation.

**LRN-047** (T5; refines GW-04; 1 description(s); confirmed: no)  
When the description lists several activities that are carried out together or that must all be finished before a following step, and none of them is stated as conditional or alternative: Open the group with a parallel gateway whose outgoing flows start every activity in the group. Close the group with a parallel gateway that waits for all branches before the next step. Do not use an exclusive gateway to join branches that must all complete, and do not add decision conditions to these branches.

**LRN-048** (T6; refines FLOW-07; 1 description(s); confirmed: no)  
When the description states that a repeating cycle continues until a participant reaches one of several named outcomes, and each outcome is an action the participant performs: Model each named outcome action as an explicit task performed by the participant before the decision. Follow those tasks with an exclusive gateway that routes either back to the start of the repeated cycle or to a separate terminal end event for each outcome. Do not connect the gateway directly to the end events when the outcome is an action the description names.

When the description says one named participant sends something to a different named participant, and that second participant then acts on it (for example reviews it and decides): Model the sending as a message exchange between the two participants: place the send step in the sender's pool and connect it to the receiver's pool with a message flow, and have the receiver's handling begin at a message start or message catch event in its own pool. Do not add a separate start event or end event around the send step, and do not connect the send step to the receiver's work with sequence flows.

**LRN-116** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description states that a named participant performs an action (such as reviewing, confirming, declining or sending) on an object, where the action is directed at or concerns another named participant: Label the task with the performing participant as subject, followed by the action verb and its object, in the order the description states them (for example 'Participant reviews the object'). Do not drop the performing participant from the label, and do not relabel the step from the receiving side with a 'Receive ... from ...' phrasing. Keep the action verb the description uses.

**LRN-117** (T5; new; 1 description(s); confirmed: no)  
When the description states that an action is carried out in one of several alternative ways (for example, 'using X, or Y') and a decision is then taken on the outcome of that action: Model the action itself as a task. Place it after the exclusive gateway that selects the method, with one branch per method converging into that task. Place the decision gateway after this task, not directly after the method-selection gateway, so that the decision is taken on the performed action's result.

**LRN-118** (T5; new; 1 description(s); confirmed: no)  
When the description states that an action is carried out in one of several alternative manners joined by 'or', and a later sentence states a decision on whether the result of that action is acceptable: Model the action as its own task, placed before the decision gateway, with a sequence flow from that task into the gateway. Do not let the decision gateway stand in for the action, and do not route the alternative manners around the task. The choice between manners only specifies how the task is performed.

**LRN-119** (T3; refines PROC-04; 1 description(s); confirmed: yes)  
When the description gives one initiating action for the process and then a sequence of steps in which each later step follows from the outcome of earlier ones (for example, continuing on success or stopping on failure), and it names no separate trigger for any other part of the process: Model one start event for the process, connected by a sequence flow to the first step of the sequence. Route every later step, including any stop outcome, from that main flow. Do not add a second start event whose path forms a separate start-to-end chain that is not joined to the main flow.

**LRN-120** (T5; new; 1 description(s); confirmed: no)  
When the description says a participant performs an action on a system themselves, and then states that the participant has to wait for a confirmation from that system or an external party before the process continues: Model the participant's own action as a bpmn:manualTask performed by that participant, placed before the wait in the order the description states. Model the stated wait for the confirmation as a bpmn:intermediateCatchEvent that follows the manual task, and place the check or decision that uses the outcome after the catch event. Do not omit the manual task, and do not fold the action into the label of the catch event or of the following check.

**LRN-121** (T6; refines GW-05; 1 description(s); confirmed: no)  
When the description says that several parallel activities must all be completed before a later step, and the generated model would synchronize these branches with a send task and an intermediate catch event inside the same process: Close the parallel branches with a parallel join gateway placed before the later step, and connect each branch's last activity or event to that join. Do not use a send task paired with an intermediate catch event to synchronize branches within the same process: message tasks and message catch events are for communication between participants, and a send task with no receiving participant in another pool leaves the synchronization undefined.

## Example-specific guidelines

**EXS-010** (T6; refines EVT-02; 1 description(s); confirmed: yes)  
When the description says the process ends when the item is either one outcome or another, where each outcome is an action carried out on the item (for example, the item is acted on by one of two named actions): Place an exclusive gateway at the point where the outcome is chosen. After each branch, model the named outcome action as its own task, labeled with the action the description gives, and then connect that task to its own end event. Do not model an outcome action only as an end event labeled with the resulting state, and do not merge the alternative outcome tasks into one task.

**EXS-015** (T5; new; 1 description(s); confirmed: yes)  
When the description ends the process with an allocation or distribution step, and then states that the receiving party goes on to carry out a further action, such as starting to implement what was allocated: Model that stated further action as its own task, placed after the allocation or distribution task and before the end event, and label it with the action the description names. Do not fold this action into the end event's label, and do not let the allocation task stand in for it.

**EXS-019** (T5; new; 1 description(s); confirmed: yes)  
When the description mentions an activity only inside a phrase that orders other steps (for example 'before the external audit' or 'after the corrections'), and that activity is itself performed between the stated steps it is positioned between: Model the mentioned activity as its own task. Place it in the sequence between the step that precedes it and the step that follows it, and connect them with sequence flows so the preceding stage flows into it and it flows into the following step. Do not omit it because it is referred to only as a timing reference, and do not merge it into the neighbouring tasks.

**EXS-020** (T5; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that the whole process is then closed as a final action, after an ordered sequence of earlier steps has finished (for example 'the entire process is then closed'): Model the stated closing action as its own bpmn:task placed after the last preceding step and before the final end event, labeled with the action the description gives. Do not replace it with an end event alone, and do not drop it or fold it into the label of an earlier task.

**EXS-022** (T6; refines GW-05; 1 description(s); confirmed: no)  
When the description says a set of activities can be done in any order but all of them must be completed before the process continues: Model each activity in that set as its own task. Place these tasks between a parallel split gateway and a parallel join gateway, so that all branches start and the join waits for all of them before the next step. Do not place an exclusive gateway or any decision condition among these branches, and do not use a single task or a subprocess to stand for the set.

**EXS-024** (T6; refines SUB-01; 1 description(s); confirmed: yes)  
When the description states that a conditional branch launches an action and then lists that action's parts (such as analysis, interviews or visits), with no separate nested workflow of its own described: Model the launched action as a single task on the main flow, placed after the branch's conditional gateway, and model its listed parts as tasks or gateways in the main flow where the description orders them. Do not model the launched action as an embedded subprocess with its own start and end events.

**EXS-025** (T5; refines ACT-05; 1 description(s); confirmed: yes)  
When the description states that the company itself receives or confirms an outcome of a step, and a next action follows directly after it, with no stated waiting time and no external message or condition the process waits for: Model that outcome as a task performed by the company, placed in the sequence before the next action. Use an intermediate catch event or an event-based gateway only when the description states that the process waits for an external message, signal, time or condition.

**EXS-029** (T5; refines GW-04; 1 description(s); confirmed: no)  
When the description states that several activities are part of one step or happen concurrently, and a later step is described as starting only after all of them are done: Model the activities as parallel branches that start from a parallel split, and join all of them with a parallel gateway before the later step. Do not let one branch lead directly into the later step, and do not use an exclusive gateway for a join where every branch must finish.

**EXS-031** (T7; new; 1 description(s); confirmed: yes)  
When the description says one participant invites several outside parties to submit proposals and then chooses one of them, and gives no steps for those outside parties beyond submitting their proposals: Model the invitation and the choice as tasks in the lane of the inviting participant, in the order the description states them, with a gateway only if the outcome branches. Do not create a separate pool for the outside parties and do not add message flows to or from them. Use a separate pool with message flows only when the description gives the outside parties their own steps or treats them as independent communicating participants.

**EXS-034** (T6; refines EVT-03; 1 description(s); confirmed: no)  
When the description has the process wait for an outside party's response, and it also states a deadline or a later point in time for the process to act on, such as a deadline for disagreement after which a further step follows: Model the wait as an event-based gateway. One branch starts with a catch event for the expected response. Another branch starts with an intermediate timer catch event for the stated deadline or later point in time. Place the step that the description ties to that point (for example, forwarding the case to another party) after the timer event, so the timed path stays visible next to the response path.

**EXS-038** (T7; refines COL-02; 1 description(s); confirmed: yes)  
When the description has a software front-end, used by a person in one participant's organization, that hands a request to a back-end process of another participant and must receive that process's result back at the front-end: Model the front-end system as its own black-box pool with no internal workflow. Connect the front-end's request to a message start event in the back-end process pool with a message flow. Connect the back-end's final send task to that same front-end pool with a message flow. Do not represent the front-end's exchange with the back-end as a sequence flow, and do not fold the front-end into a lane of the back-end pool or replace it with a generic person pool.

**EXS-039** (T5; new; 1 description(s); confirmed: no)  
When The description states a decision after a first quick step: one outcome is returned immediately, while the other is a delay that the performing participant reports to another participant before it runs a longer step and then sends the final outcome back to that participant: Model the decision with an exclusive gateway placed after the quick step, with one branch that sends the immediate outcome to the receiving participant and one branch for the delay. On the delay branch, model the notice of delay as a send task, then model the longer step as a task in the performing participant's pool. Model the sending of the final outcome as its own send task after that longer step, connected by a message flow to the receiving participant. On the receiving side, model the wait for the final outcome as an intermediate catch event after the delay notice. Reunite the branches before the common closing end event, so that every path ends in an end event and no send-back step is dropped.

**EXS-040** (T6; refines ACT-07; 1 description(s); confirmed: no)  
When the description says that a requested evaluation is sometimes completed at once and sometimes only after a slower second evaluation, and the requesting process is told of the slower path before the answer comes back: After the step that sends the request and the first quick evaluation, place an exclusive gateway that separates the immediate-answer case from the slower case. On the immediate branch, send the answer to the requester and go to the end event. On the slower branch, notify the requester of the delay, continue with the slower evaluation, and model the answer's return as a message from the responding party to the requester, received by an intermediate catch event in the requesting process before the answer is handled. Route the handled answer to the same end event as the immediate branch, so that both branches are joined and no branch ends at the delay notice.

**EXS-041** (T7; refines COL-03; 1 description(s); confirmed: no)  
When the description says a process sends a request to another participant, and that participant later sends back a reply, a delay notice, or a final answer that the process waits for through a catch event or a receive step: Model each reply as a message flow from the send task on the replying participant's side to the intermediate catch event or receive task that waits for it on the requesting side. Do not connect the waiting element by a sequence flow from another task of the same pool. Place the sending and waiting elements in different pools so that the message flow is valid.

**EXS-042** (T5; new; 1 description(s); confirmed: no)  
When the description says an external participant first carries out a step, and the outcome either comes back at once, or, if that step is not finished at once, the participant first sends a postponement notice to the requester, then carries out a further step, and afterwards sends the final outcome back to the requester: In the external participant's pool, model the first step as a task followed by an exclusive gateway with one outgoing flow per outcome. On the at-once branch, send the outcome to the requester with a send task and a message flow. On the postponed branch, send the postponement notice with a send task and a message flow, then a task for the further step, then a send task that returns the final outcome by a message flow. In the requester's pool, after the postponement notice, place an intermediate catch event that waits for the final outcome before the requester continues. Do not end the postponed branch at the notice or at the further step, and do not treat the notice as the end of the wait. Reunite the two outcome branches with an exclusive join where they lead to a common continuation.

**EXS-043** (T6; new; 1 description(s); confirmed: no)  
When the description states that an external participant performs a step that takes time (such as an evaluation or computation) and afterwards sends its outcome back to the process, which is waiting for that outcome: Model the external participant's step as a task in that participant's pool. Place a send task in the same pool directly after that task, connected by a sequence flow, and connect the send task to the receiving element in the process pool with a message flow. Do not leave the outcome of the step without a send task, even when the process pool receives the outcome later or through a separate waiting element.

**EXS-044** (T5; refines ACT-06; 1 description(s); confirmed: no)  
When the description states that a participant has to regularly perform a recurring or obligatory action, such as reporting something or confirming receipt of an item, and the process depends on that action being done: Model each such stated obligatory action as its own task in the lane or pool of the participant who performs it. Use a manual task when the participant performs it personally, and a service task only when a system performs it. Place the task where the description puts the action in the sequence, and do not omit it or fold it into another task.

**EXS-046** (T6; new; 1 description(s); confirmed: no)  
When The description says a party moves into a stage or phase of an activity (for example 'you enter the ... phase'), and a generated task for that stage would be labeled with a verb for a later moment of the same stage, such as finishing or completing it: Label the task that represents the stage with the same action verb and object the description uses for entering that stage, and do not substitute a verb for a later moment or outcome of the stage, such as finishing or completing it. Model any completion of the stage as a separate step only if the description states one.

**EXS-047** (T1; refines XML-01; 1 description(s); confirmed: yes)  
When the description is long and contains several separately headed sections, each with its own rules, obligations or responsible parties, that a modeler might be tempted to write out as separate documents: Emit exactly one bpmn:definitions root for the whole description. Place every section's process, collaboration or participant elements inside that single root, and place the bpmndi:BPMNDiagram element inside it as its last child. Never open a second bpmn:definitions element, nested or appended after the diagram, and never close the root before the end of the document.

**EXS-048** (T5; new; 1 description(s); confirmed: no)  
When the description states that an event already notified to one recipient must be notified again to a different recipient only when a stated condition on the event's severity or outcome holds, and the later notice has its own deadline: Model an exclusive gateway after the event has been classified, with one outgoing flow for each outcome of the stated condition. Put the further notification task for the named recipient on the branch where the condition holds, and give it a flow that carries its own deadline. Keep the earlier notification as a separate activity that does not replace the later one. Give the other branch a flow that continues without the further notice. Reunite the branches with an exclusive join before the next step, and keep the notification tasks in the order the description gives.

**EXS-049** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description attaches an additional notification requirement to the most severe outcome of an event, which must be met even when the event has already been notified under a general rule, and it gives that requirement its own deadline: Model a separate notification step for that most severe outcome, placed after the gateway that separates that outcome from the other cases. Label it with the recipient and the deadline in the description's own terms. Do not fold this step into the earlier general notification step, and do not reuse one shared notification task for both the general and the additional requirement.

**EXS-051** (T6; new; 1 description(s); confirmed: no)  
When the description states a branch decision as a yes/no fact about a person, event or status, and the generated exclusive gateway question adds the consequence, deadline or recipient that the description attaches elsewhere, so the question no longer matches the wording the description uses for that decision: Label each exclusive gateway with a yes/no question that uses the description's own term for the decided fact, for example the type of event or the status of a person. Leave out the consequence, the deadline and the recipient, which belong on the task or flow that follows. Keep the question's terms close to the description's sentence, and do not replace them with a paraphrase that changes what is being decided.

**EXS-053** (T6; refines GW-01; 1 description(s); confirmed: no)  
When the description says the user can accept or deny an item, so the choice between the two outcomes is made by the user and the process then branches on it: Model the branch as an exclusive gateway labeled with a short yes/no question that uses the decision verb the description gives for that choice (for example, the accept-or-deny action applied to the item, phrased as a question about that action). Label the outgoing flows with the two outcomes. Do not label the gateway with a summary of the outcomes or with a generic status phrase.

**EXS-057** (T5; new; 1 description(s); confirmed: yes)  
When the description lists several separate requirements that an applicant must provide or prove, and it states that checking them has a fulfilled outcome and a not-fulfilled outcome with a named remedial step: Model each listed requirement as its own task in the order the description gives: a user task where the applicant must prepare or obtain the item, and a service task where the description states an automated check. Do not wrap these tasks in an embedded subprocess. After the last check, place an exclusive gateway with one branch for the fulfilled outcome and one for the not-fulfilled outcome. On the not-fulfilled branch, model the remedial action the description names as its own manual or user task, then route back to the check. Keep every listed requirement and every named remedial action as a separate element, and keep any gateway the description implies before the first check or after the verification.

**EXS-058** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a participant's document must meet validity or eligibility conditions (such as a minimum remaining validity period, an issue-date limit, or a required number of blank pages) before an application can be accepted: Model a separate user task, performed by the participant or the reviewing party, that checks the document against the stated conditions. Place this check before the exclusive gateway that decides whether the application can proceed. If the check fails, model a separate task in which the participant obtains a replacement document, and connect that task back into a merge gateway placed before the check so the check is repeated. Do not fold the document check into the decision gateway or into a generic preparation task.

**EXS-060** (T5; refines EVT-03; 1 description(s); confirmed: no)  
When The description says the participant asks other people for a reply or information (for example their availability or how much of something they need), and a later decision or step depends on those replies, but the description does not explicitly say that the process waits: Model the period until the replies arrive as an intermediate catch event placed between the task that sends the request or gathers the information and the gateway that depends on the answers. Do not leave the wait implicit as a direct sequence flow from the request task to the decision, and do not model the waiting period as an extra task.

**EXS-064** (T5; new; 1 description(s); confirmed: no)  
When the description states that several items are each checked after their own build step, and that a following joint step on all of the items is performed only when every check succeeds, while a failed check leads to rework of that item: Model each check as its own task on its item, placed after that item's build step. After the checks, place an exclusive gateway with a question about whether all checks succeeded. Give one outgoing sequence flow to the joint step and one to the rework path. Do not omit this gateway, and do not connect the checks straight to the joint step. If the rework is followed by the checks again, route it back through an exclusive merge.

**EXS-065** (T6; new; 1 description(s); confirmed: no)  
When the description states that a later step is performed only if a condition on the outcomes of earlier work holds, either for every item in a set (for example, all items must succeed before the next step) or while a supply of items still remains, and it states a different corrective action for the case where the condition fails: Model the condition as an exclusive gateway placed after the activity or activities that produce the outcomes it checks, and before the gated step. Give the branch where the condition holds a labeled outgoing flow to the gated step. Give the failing branch a labeled outgoing flow to the stated corrective task. If the description says the work resumes or is checked again afterwards, route the corrective task's outgoing flow back into a merge gateway placed before this gateway. Do not omit the decision point, and do not connect the corrective task directly to the gated step.

**EXS-066** (T5; new; 1 description(s); confirmed: yes)  
When the description states that items acquired by an earlier step are handed over to a group of people, who then carry out a sorting or processing activity on those items, so the handover is a separate step between the acquisition and the group's work: Model the handover as its own manual task performed by the person who hands the items over. Place it after the task that acquires the items and before the group's sorting or processing task, with sequence flows connecting them in that order. Do not omit the handover and do not merge it into the group's task.

**EXS-067** (T6; new; 1 description(s); confirmed: yes)  
When the description states that a repeated activity draws its inputs from a supply that can run out, and that when the supply is exhausted a replenishment action must happen before the activity can continue: Model an exclusive gateway directly after each use of the supply by the repeated activity, asking whether the supply still has items. Give the branch where items remain a condition matching that wording and route it onward to the next step. Give the exhausted branch a condition matching the empty state and route it to the replenishment activity the description names, then return the flow to the point where the supply is used. Do not place the check only before the first use, and do not leave the exhausted outcome without a continuation.

**EXS-070** (T5; refines FID-02; 1 description(s); confirmed: no)  
When the description says a receipt (a start or arrival of information or items) is followed by an action the company itself performs on the work, such as determining details, ordering from several sources in parallel, or inspecting and assembling, and the description states the arrival of the resulting items as a separate later occurrence: Model the receipt only as the start event or intermediate catch event for that occurrence. Model each stated company action as its own task (use a service task if the description says it is performed by a system or external source, otherwise a user task), placed in the order the description gives: directly after the receiving element, and before any parallel split or join that the description puts around it. When the description says several such actions run in parallel, place them after one parallel split and join them before the next step. Model a later arrival of items as an intermediate catch event that only represents the wait, and keep it separate from the company's action on those items. Do not let the receipt event or the arrival event replace or absorb a stated action, and do not drop an action because a related event already appears in the model.

**EXS-071** (T6; new; 1 description(s); confirmed: yes)  
When the description says a participant itself carries out a named check or inspection of received material as a step placed between two other steps, and names no message, signal, time or condition that the process waits for for that step: Model that step as a bpmn:userTask performed by the participant, placed in the sequence where the description places it, and labelled with the action verb and object the description states. Do not model it as a bpmn:manualTask, and do not add a second element for the same step.

**EXS-074** (T6; new; 1 description(s); confirmed: yes)  
When the description names a specific party (such as a team, company or region) as the recipient of a request or piece of work, for example inside an 'e.g.' example, and a separate send step is made for that party: Label the send task for that work with the specific party name exactly as the description gives it (for example, the named team or region), not with a generic collective term such as 'the teams' or 'manufacturing teams'. Add a labelled send task only for parties the description actually names, and do not invent further parties from other sources.

**EXS-077** (T6; new; 1 description(s); confirmed: yes)  
When the description says the process sends messages to outside people asking them to carry out work, and it names no reply, message or condition that the process waits for before continuing: Model the sending of the requests as one send task labeled with the sending action and its content as the description states them, placed where the description places the sending. Model the work those people carry out as a separate manual task placed after the send task, in the sequence where the description says that work is needed. Do not merge the sending and the work into one task, do not label the sending as a call or a generic step, and do not add an intermediate catch event for a reply the description does not state.

**EXS-079** (T5; new; 1 description(s); confirmed: no)  
When the description says the actor sends messages to several other people so that they carry out work for the actor, and the description gives no message content, no reply, and no formal message exchange with a receiving party: Model the contacting as a bpmn:manualTask labeled with the contacting action as the description words it, placed where the description places it in the sequence. Do not model it as a bpmn:sendTask, because no message is exchanged with a process participant. Connect it with sequence flows to the surrounding steps, and model any later work the people perform as a separate task only when the description states it.

**EXS-083** (T6; new; 1 description(s); confirmed: no)  
When the description states that the system or tool gives the user guidance or information on how to carry out an activity, and the user then performs that activity: Model the delivery of the guidance as its own task, labeled with the verb and object the description uses for that delivery, and model the performance of the activity as a separate later task (performed by the user). Do not merge the delivery and the performance into one task named after the performed work, and do not assign the performance to the system.

**EXS-084** (T5; refines ACT-04; 1 description(s); confirmed: no)  
When the description says a person performs an action themselves, with the help of an online application or software (for example entering data, selecting an option, contacting other people, buying items, or writing a review), and does not say that the process waits for a message, signal, time or condition at that step: Model each such action as one bpmn:userTask placed in the sequence where the description places it, labeled with the action verb and object the description states. Model an optional branch of such actions (for example contacting others only in some cases) as its own userTask in that branch. Do not model the action as a bpmn:sendTask unless sending a message is itself the described unit of work, and do not add a receive element or a second element for the same action.

**EXS-085** (T6; new; 1 description(s); confirmed: yes)  
When the description says an online tool or system gives the actor instructions or information, and the actor then physically performs the work those instructions describe, with no system involvement in the physical work itself: Model the tool's provision of the instructions as a task that the system performs (a serviceTask, or a userTask if the actor operates the tool), placed before the physical work and labeled with the provision action the description states. Model the actor's hands-on work as a bpmn:manualTask performed by the actor, placed after the instructions and labeled with the physical action the description states. Do not swap these labels, so that the physical work is not labeled as a system task and the receipt of instructions is not labeled as the work itself.

**EXS-086** (T3; refines PROC-05; 1 description(s); confirmed: yes)  
When The description describes a repeating activity (for example, measuring continuously) that resumes after an interruption, and a monitored condition (for example, a lost connection or a measurement crossing a limit) ends the whole process while the repetition otherwise continues: Model the repeating flow with a decision point where the monitored condition is checked. Connect the branch in which the condition holds to its own terminal path, and end that path with an explicit end event. If the description attaches a further action to the ending, place that action as a task before the end event. The repeating flow must keep its own exit, so the process has at least one explicit end event and no loop is left without a way out.

**EXS-090** (T5; new; 1 description(s); confirmed: no)  
When the description states that after an interruption of a repeated activity (for example, a stopped device is brought back online), the same repeated activity must continue measuring: Model the continuation as a task placed after the step that ended the interruption, and connect it with a sequence flow back into the gateway that starts each cycle of the repeated activity. Do not model the continuation as a new start event or as a separate process, so the repetition keeps its loop and its existing entry point.

**EXS-092** (T6; refines ACT-04; 1 description(s); confirmed: yes)  
When the description says that a party itself gathers or describes information (for example symptoms or an item's type) and then sends it on to another party, with no statement that the sender waits for a reply: Model the gathering or describing of the information as a task performed by that party (a manual or user task, according to who does the work), placed directly before a separate send task that transmits the information. Do not model the gathering step as a receive task, and do not omit it. Use a receive task only when the description states that the process waits for an incoming message.

**EXS-094** (T5; new; 1 description(s); confirmed: no)  
When the description has a participant put a question to a person, phrased as whether that person wants one option or another, and the person's reply decides which branch follows: Model the question as a user task placed after the start event and before an exclusive gateway. Connect the start event to the question task, and connect the question task to the gateway. The gateway gets one outgoing flow per possible reply, each labeled with its condition. Do not connect the start event directly to the decision gateway, because that skips the question the description states.

**EXS-095** (T6; new; 1 description(s); confirmed: no)  
When the description says the actor asks the customer a question whose answer decides which branch the process takes next (for example, a choice between two offered options): Model an exclusive gateway immediately after the question, and label it with the question in the description's own wording. Label each outgoing flow with one answer option as the description states it. Do not label the decision gateway with a different decision or with a status check on a later activity, and do not reuse the label of another gateway for it.

**EXS-098** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description states that after a step, one activity must wait for an external confirmation while another activity, such as entering further data, may proceed at the same time, and both must be completed before the following step: Place a parallel gateway directly after the preceding step to fork into a branch that contains the wait as an intermediate catch event and a branch for the concurrent activity. Join the branches with a parallel gateway before the next step. Do not omit the fork and do not connect the preceding step straight to the wait.

**EXS-100** (T6; refines EVT-03; 1 description(s); confirmed: no)  
When the description says the flow must wait for an outside delivery or arrival (for example, a reordered item) before it continues to a later step: Model the wait as an intermediate catch event placed between the ordering task and the next step that depends on the arrival. Do not omit the wait, and do not model it as a task. If the description attaches a timed consequence to the wait (such as a penalty when the wait exceeds a stated duration), place the decision on the wait's outcome after the catch event.

**EXS-104** (T6; new; 1 description(s); confirmed: no)  
When the description states, as a property of the system or application (for example 'the application is also connected to an external account'), a link to an external service, and the same sentence then describes a sharing action and a separate step that completes the process and provides payment details: Model the stated link to the external service as its own user task, placed before the task for the completing step and in the order the description gives. Label it with the connecting action the description names. Model the sharing action as a separate user task labeled with that sharing action, not with the completing step. Do not omit the connecting task, and do not give the completing task the label of the sharing or connecting action.

**EXS-107** (T5; refines QA-04; 1 description(s); confirmed: yes)  
When the description states that a check or test result decides between repeating a repair activity and an alternative branch in which a named completion step is performed, and that completion step then leads to a later outcome that is merged with another outcome: Model the named completion step as its own task on the alternative branch of the decision gateway. Connect the decision gateway to that task with a sequence flow labeled with the condition, and connect the task to the gateway that merges the outcomes. Do not connect the decision gateway directly to the merge, and do not drop the completion step. Keep the repeat branch as a separate flow back to the point where the repeated activities are joined, and do not insert an extra merge gateway that the description does not state.
