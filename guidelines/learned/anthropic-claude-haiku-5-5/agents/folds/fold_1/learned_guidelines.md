# Learned guidelines: Claude Haiku 5.5, Reuse training, round 1 (44 descriptions)

120 generic and 39 example-specific error-driven guidelines; 60 generic guidelines confirmed. Full records (evidence, confirmation tests, provenance): `learned_guidelines.json`.

## Generic guidelines

**LRN-006** (T6; refines GW-04; 9 description(s); confirmed: yes)  
When the description lists several activities that all belong to one stage, have no stated order between them, and a later step waits until every one of them has finished: Model each listed activity as its own task. Open the branches with a parallel gateway placed before the first of these tasks, and close them with a matching parallel gateway placed before the next step. Do not sequence the tasks unless the description states an order, and do not merge them into one task.

**LRN-010** (T5; refines ACT-07; 7 description(s); confirmed: no)  
When the description lists several activities that all follow the same preceding event and are performed together, and a later step continues only after all of them are done: Model an opening parallel gateway after the preceding step, with one branch per listed activity, and close those branches with a joining parallel gateway before the next step. Do not chain the activities in sequence, and do not use an exclusive gateway to join them.

**LRN-005** (T5; refines EVT-01; 5 description(s); confirmed: yes)  
When the description states that a participant performs an action (for example, identifying a need) that begins the process, and the action is described as work the participant does rather than as an occurrence that starts the process: Model a generic start event with no label that describes the action. Place a task, named after the participant's action, immediately after that start event and before the first step that follows from it. Do not use the start event label to carry the action.

**LRN-011** (T5; new; 5 description(s); confirmed: yes)  
When the description offers two alternative ways of performing the same signalling or checking step, joined by 'or', and both alternatives lead to the same next step: Model each alternative as its own task. Place an exclusive gateway before the alternatives, with one labelled outgoing flow per alternative, so that the choice of method is explicit. Join the alternatives with an exclusive merge gateway before the shared next step. Do not collapse the alternatives into one generic task, and do not leave either alternative without its choice gateway.

**LRN-009** (T6; refines GW-03; 4 description(s); confirmed: yes)  
When the description states that an activity may or may not take place (for example, 'may take place' or 'may occur'), so the activity is optional and its execution depends on circumstances the description leaves open: Model an exclusive gateway before the optional activity, with one outgoing flow into the activity and one skip flow that bypasses it. Place a second exclusive gateway after the activity that merges the activity path and the skip path before the next step. Do not model the optional activity as unconditional in the main sequence.

**LRN-021** (T6; refines FID-03; 4 description(s); confirmed: yes)  
When the description states an action on an object and then attaches a phrase giving its place, method, or the aspects it is checked against (for example, a list of criteria or a qualifying condition on where or how the action is done): Model the task with a label containing only the core verb and object taken from the description, and move the place, method, or criteria phrase into the task's documentation. Do not let the label carry the qualifier, and do not drop the qualifier from the model, since it belongs in the documentation.

**LRN-036** (T6; refines GW-05; 4 description(s); confirmed: yes)  
When the description states that two or more activities run at the same time (joined by 'while' or 'and', or stated as simultaneous), and a later step starts only after all of them are finished: Model the concurrent activities as separate branches that start at one parallel gateway, with each activity in its own branch and placed in the lane of the participant who performs it. Close all branches with one matching parallel gateway placed before the later step. Do not sequence the concurrent activities one after another, do not omit an activity or merge it into another, and do not use an exclusive gateway, because it would choose one path while the description requires all of them to proceed.

**LRN-062** (T6; new; 4 description(s); confirmed: yes)  
When the description states, in one sentence, several items that the same participant enters or selects, joined by commas or 'and', and each item is a distinct input or choice the participant makes: Model each item in that list as its own user task, in the order the sentence states them, and label each task with the verb and the single item it covers, taken from the description. Do not combine two items into one task label, and do not drop any item from the list.

**LRN-002** (T6; refines GW-06; 3 description(s); confirmed: yes)  
When the description states that a later step happens only if a stated condition holds, and it gives or implies an alternative outcome for when the condition does not hold: Model the decision as an exclusive gateway placed immediately before the conditional step. Label each outgoing flow with the condition from the description, route the alternative outcome to its own end or continuation, and do not drop the not-taken branch.

**LRN-013** (T5; refines FID-01; 3 description(s); confirmed: yes)  
When the description states that a participant carries out a series of its own actions, such as making choices or submitting information, in a stated order before a later step, and the description does not state that the process must wait for an external message, signal, time or condition at that point: Model each such action as its own task, in the order the description gives, placed on the sequence flow where the description places it. If the sequence begins with such an action, use a generic start event with no action label and place the first task after it. Do not record the completion of a participant's own action with an intermediate catch event. Reserve intermediate catch events for occurrences the process must wait for before it can continue.

**LRN-014** (T5; refines FID-02; 3 description(s); confirmed: yes)  
When the description states a participant's sequence of actions (an initial request or search, then a choice among options, then entry of further information or payment), each described as a separate step before a system step that depends on them: Model each stated participant action as its own user task, in the order the description gives, including the opening request or search that starts the process. Connect these tasks in sequence before the system task that depends on them. Do not omit a stated action because it appears only as a clause within a sentence, and do not fold several stated actions into one task.

**LRN-017** (T5; refines EVT-02; 3 description(s); confirmed: no)  
When the description ends a choice with alternative outcomes, where each outcome is a named action performed on the item (for example approving it or discarding it), and the generated model connects that outcome branch directly to an end event: Model each named outcome action as its own task on its branch, placed after the choice gateway and before the end event that closes the process. The end event follows the task and does not replace it. Do not use the end event label to carry the action.

**LRN-026** (T6; refines FID-03; 3 description(s); confirmed: yes)  
When the description states that a named actor performs an action that is part of the process, such as submitting a request or signing up: Model that action as a task whose label keeps the actor and the action verb and object as written in the description, for example 'Actor verb object', rather than a shortened verb-object label that drops the actor. Keep the task after the start event that the description implies, and do not replace it with a separate start event or a user task that repeats the actor's action.

**LRN-031** (T5; refines ACT-07; 3 description(s); confirmed: yes)  
When the description states that a decision or check leads to a named action on the item (for example a stated approval, a required revision, or a detected high-risk condition), and that the action is followed by further steps before the process continues: Model the named action as its own task on the sequence flow of that decision outcome, placed after the gateway and before the next step. Do not connect the decision gateway directly to the following step, and do not fold the action into the gateway label or the next task's label.

**LRN-032** (T5; refines FID-01; 3 description(s); confirmed: yes)  
When the description states that a participant carries out a named closing action as the last step before the process ends (for example closing or concluding the whole process after the final outcome), and this action is not a gateway condition or a flow label: Model that closing action as its own task on the sequence flow immediately before the end event, so the task performs the work and the end event only marks termination. Do not replace the stated action with an end event alone, and do not leave it out.

**LRN-040** (T7; refines COL-01; 3 description(s); confirmed: yes)  
When the description says an external participant, such as a person or another software system, starts the process by sending it a message, and the process sends messages back to that same participant while it runs: Model the external participant as its own pool. Inside that pool, model the sending of the initiating message as a task. Draw a message flow from that task to the message start event of the process pool. Draw a message flow from each process task that sends a message back to the external participant's pool. Do not place these sending and receiving steps inside the process pool itself.

**LRN-069** (T6; refines FID-03; 3 description(s); confirmed: no)  
When the description names a step with a specific verb and object, and the candidate task label would replace that verb or object with a synonym: When the description states a step with a verb and object, name the task with that same verb and object, keeping the description's word choice. Do not swap in a synonym that changes the verb, because the paraphrase can drift from what the description says the step does.

**LRN-004** (T6; new; 2 description(s); confirmed: yes)  
When the description states a conditional outcome (for example 'if X is interested') where one outcome leads to its own end and the other continues to later steps, and the continuing path is also reached from earlier steps before the decision: Model the outcome check as an exclusive gateway placed immediately before the conditional step, with one labelled outgoing flow per outcome, and route the not-taken outcome to its own end event. Where the flows from earlier steps converge into a shared step or decision point, join them with an exclusive merge gateway before that step rather than connecting several incoming flows directly to one activity. Do not add parallel gateways unless the description requires concurrent or synchronized branches.

**LRN-012** (T5; refines ACT-05; 2 description(s); confirmed: yes)  
When the description says a team sends a request to outside actors and then takes in their returned items as work the team carries out, and no stated occurrence is one the process must wait for before it can continue: Model the taking-in of the returned items as a task placed on the sequence flow after the request task and before the next step that uses them. Do not model it as an intermediate catch event. Reserve an intermediate catch event for an occurrence the process must wait for before it can continue.

**LRN-015** (T6; refines FID-02; 2 description(s); confirmed: no)  
When the description states, within a single clause, several distinct actions by one participant joined by commas, 'and' or 'or' (for example, in the sentence that states the outcome of the process, where one action changes a participant's status and another is a separate commitment): Model each named action in that clause as its own task, in the order the description states, each with a short verb-object label taken from the description. Do not merge the actions into one task label and do not drop any of them. When the clause states the outcome, place these tasks in sequence before the end event, and let the end event name only the outcome reached.

**LRN-022** (T6; refines FID-03; 2 description(s); confirmed: yes)  
When the description states a participant's action on an object and follows it with a prepositional complement or qualifier that names the recipient, purpose or scope of the action (for example 'to ...' or 'for ...'), or with a determiner or modifier that is part of the stated action: Label the task with the verb-object phrase as the description words it, keeping the prepositional complement, qualifier and determiner or modifier that belong to the stated action. Do not shorten the label to the bare verb and object, and do not drop the complement that says to whom, for what or in which scope the action is performed.

**LRN-027** (T5; new; 2 description(s); confirmed: yes)  
When the description states that a decision after a review is approved or not approved, and that the approved outcome is followed by a named action performed on the item before the process moves on to a later stage: Model the decision as an exclusive gateway with one conditional outgoing flow per outcome. On the approved flow, place a task that names the approved action, and connect that task to the next stage, so the approved path does not skip the action. On the not-approved flow, return to the earlier stage named in the description. Do not connect the decision gateway directly to the later stage, and do not omit the approval action task.

**LRN-035** (T5; refines ACT-07; 2 description(s); confirmed: yes)  
When the description states that after a step, the flow continues along one of several named alternative outcomes, each of which requires its own separate action: Model the choice between outcomes as an exclusive gateway placed directly after the step that precedes it, with one labelled outgoing flow per named outcome. Give each outcome its own task labelled with that outcome's action, and connect each task onward to the next step or to an end event. Do not leave any named alternative without its branch, and do not replace the choice with a single task or a plain sequence.

**LRN-044** (T7; refines COL-04; 2 description(s); confirmed: no)  
When the description has a step of one role whose result is passed to a different role, and the receiving role then performs its own described step as a task in its own pool (for example, a role that is asked to act on information or an item another role has sent): Model the receiving step as a task in the receiving role's pool and draw a message flow from the sending step in the sender's pool to that receiving task, with the arrow pointing from sender to receiver. Do not replace this flow with one that ends at a catch event when the receiver's described step is a performed task, and do not reverse the arrow direction.

**LRN-046** (T5; refines EVT-03; 2 description(s); confirmed: yes)  
When the description states that one participant is held until another participant makes something available or arrives, and then describes one or more further actions by the first participant on it, in a stated order: Model the awaited occurrence as an intermediate catch event. Model each described action of the participant as its own task, in the stated order, on the sequence flow after that event. Do not place an end event between the catch event and these tasks, and do not treat the occurrence itself as the completion of the process.

**LRN-050** (T6; new; 2 description(s); confirmed: yes)  
When the description names an action that a participant performs on a business object, using a specific verb (for example 'enter', 'submit', 'rate' or 'negotiate'): Label the corresponding user task with the verb and object the description uses for that action. Do not replace the verb with a synonym or a broader verb that changes what the action means, and do not add a state or outcome the description does not state.

**LRN-051** (T3; new; 2 description(s); confirmed: yes)  
When the description states that a flow ends when one condition holds, and that under a second, alternative condition the flow returns to an earlier ongoing activity that keeps delivering new items, so the two outcomes would be reunited before the flow ends: Model the ending outcome as its own branch that leads directly to an end event. Model the returning outcome as a sequence flow back to the earlier ongoing activity. If the two outcomes are reunited by a merge gateway, the merged path must still have a route to an end event: give the returning path its own decision that can lead to an end event, or do not merge it into the ending path at all. Verify that every merge gateway has an outgoing route to an end event.

**LRN-052** (T5; refines ACT-07; 2 description(s); confirmed: yes)  
When the description makes the time limit or the target of a follow-up action depend on a sequence of yes/no checks applied to the same subject, where each check's result changes the next step: Model each check as its own exclusive gateway, placed in the order the description gives the checks. Give each gateway one labelled outgoing flow per outcome, using the condition wording from the description. Attach each outcome flow to the action or step it triggers, including any stated time limit. Connect the not-taken outcome to the next check or to its own continuation. Do not replace these checks with a single task that assesses the subject, and do not omit a check merely because its outcome only changes a time limit.

**LRN-058** (T5; refines GW-04; 2 description(s); confirmed: no)  
When the description states that several distinct actions are carried out in parallel (for example, items are sent in parallel), or that a set of distinct actions must all be completed before the process continues: Model a parallel gateway that forks into one outgoing branch per action, so that all branches start, and a parallel gateway that joins those branches before the next step. Do not model the set as a single task, and do not use an exclusive gateway to merge branches that must all complete.

**LRN-059** (T6; refines FID-01; 2 description(s); confirmed: yes)  
When the description names two or more distinct values that a participant enters before a later step, and each value is described on its own: Model each named input as its own user task placed in sequence before the later step, labeling each task with exactly the input the description names. Do not add inputs, attributes or details that the description does not state, and do not fold unstated items into a task label.

**LRN-067** (T5; new; 2 description(s); confirmed: yes)  
When the description states that a participant first has to identify or decide which of several items they want, as a preparatory step before further work on those items begins: Model that identification as a user task on the sequence flow directly after the process start event and before the first step that depends on the chosen items. Do not omit it, and do not model it as a second start event that stands beside the process start.

**LRN-105** (T5; refines EVT-01; 2 description(s); confirmed: no)  
When the description states that a participant performs an action as the first step, and the later steps by other participants or parallel work depend on what that action supplies: Model that action as a task placed on the sequence flow after the start event, not as the start event itself, since the start event only marks that the process begins. If a person performs the action, use a bpmn:userTask. Place it before any gateway that splits the subsequent work, and do not omit it.

**LRN-112** (T6; refines ACT-05; 2 description(s); confirmed: no)  
When the description states that one participant sends a document or message to another participant as an action that participant performs, and the receiving participant then acts on it: Model the sending as a task performed in the sender's pool or lane, with the sender's action visible as work. Do not replace that sending task with a start event in the receiver's pool. If the receiver's reception must be shown, add it as a separate message event or message flow in the receiver's pool, after the sending task.

**LRN-114** (T6; refines FID-02; 2 description(s); confirmed: yes)  
When the description states that a named participant performs a concrete action as a step of its own, either directed at another participant or applied to a work object, and the description names no separate external trigger for that action: Model that action as a task in the performing participant's lane, labelled with the action as the description words it, and place it on the path where the action occurs. Keep distinct actions, such as a checking action and a later handback action, as separate tasks. Use a start event only for an external trigger the description names, and use an end event only for an outcome that follows the action task, not for the action itself.

**LRN-001** (T5; refines ACT-04; 1 description(s); confirmed: yes)  
When the description states that the process begins when an external party sends an inquiry or request before any internal work is described: Model a start event as the process trigger, followed by a receive task that accepts the incoming inquiry as the first activity, before any internal activity such as collecting information or responding. Do not omit the receiving activity or leave the internal activities as the first step.

**LRN-003** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description states that a later step proceeds only after a party approves or accepts something previously provided, so the approval decides whether the process continues: model the approval as an exclusive gateway with one outgoing flow per outcome (approved and not approved), not as an ordinary task that merely performs the approval

**LRN-007** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description states that a set of selected items each receive a notification or request to take part, and that each item's own choice then determines which of several follow-up paths is taken: Model the notification or request sent to the selected items as its own task, placed on the sequence flow after the preceding step and before the gateway that splits on each item's choice. Do not drop this action, and do not connect the preceding task directly to the choice gateway.

**LRN-008** (T5; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that a stage of work begins only after a previously sent outcome has been accepted, and that this stage then consists of several activities that run side by side before the process concludes: Model the acceptance as an exclusive gateway with one outgoing flow per outcome (accepted and not accepted), as the approval guideline requires. Do not model the acceptance itself as a task that stands in for the stage start. On the accepted path, add a task that names the start of the following stage, and connect it to the parallel gateway that opens the stage's concurrent activities. Do not connect the acceptance gateway directly to the parallel split. Close the parallel branches with a matching parallel join, and connect that join to the end event that concludes the process.

**LRN-016** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description lists several activities in one sentence, performed by the same actor or team, and states no concurrency, order condition, or synchronization between them: Model the listed activities as consecutive tasks in the order the text gives, connected by sequence flows. Do not insert a parallel gateway unless the description states that the activities run at the same time or must all finish before the next step.

**LRN-018** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states, within one sentence, several named checks of the same object, joined by commas or 'and', where each names the aspect it examines (for example, its size, its weight and its color): Model each named check as its own task, labelled with the short verb-object form of the aspect it examines, taken from the description. Keep the order in which the description states them, and do not invent an order if none is stated. Do not merge them into one combined task and do not drop any of them. Connect them in sequence before any later step that depends on their results.

**LRN-019** (T6; refines FID-02; 1 description(s); confirmed: no)  
When the description states one step in which a participant performs two distinct actions joined by 'and', and the second action has its own purpose or result that is not part of the first: Model each distinct action as its own bpmn:task, in the order the description gives, on the sequence flow where the step occurs. Give each task a label that names only its own action. Do not combine the actions into one task label, and do not drop the second action because the first action's label seems to cover it.

**LRN-020** (T5; refines PROC-04; 1 description(s); confirmed: yes)  
When the description states that the process starts from a single triggering request or submission by one party, and no other distinct start trigger is stated: Model exactly one start event for that trigger. Do not add a second start event for the same submission, and do not add a separate user task that duplicates the submission already represented by the start. Keep one start event per distinct trigger stated in the description.

**LRN-023** (T5; refines FID-02; 1 description(s); confirmed: no)  
When The description names several distinct kinds of outgoing communication sent to the same party within one stated activity, joined by commas or 'or' (for example, different notice or update types), and does not say they are alternatives in a decision: Model each named kind of communication as its own send task within the activity, rather than merging them into a single task labelled with all the kinds. Connect these tasks with sequence flows or a gateway that reflects the stated relationship between them, and do not collapse them into one generic send task.

**LRN-024** (T5; refines EVT-01; 1 description(s); confirmed: no)  
When the description says the process is started by a participant performing an action that is itself work, such as providing data or registering, and that action is the first described step before any system processing begins: Model a plain bpmn:startEvent that carries no activity label. Place a bpmn:task labeled with only that participant action directly after the start event, connected by a sequence flow, and connect that task by a sequence flow to the next described step. Do not let the start event itself carry the participant's action.

**LRN-025** (T6; refines EVT-01; 1 description(s); confirmed: no)  
When the description opens with a participant performing an action as the first step (for example signing up or submitting information), and that action is work the participant performs rather than a message, timer, or condition: Model a plain start event with a neutral trigger label and no incoming flow, then model the participant's action as a task named with a verb-object label. Do not place the performed action in the start event label.

**LRN-028** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that, after an approval outcome, several distinct actions follow in sequence (for example a change in pay, a change in duties, and a move into a new role), and then says the process ends once the last of them is done: Model each listed action after the approval outcome as its own task, in the order the description states, on the approved path. Do not merge them into one task whose label lists all the actions, and do not fold the last action into the end event label. Place the end event after the final action task, and label it with the outcome it represents.

**LRN-029** (T5; refines PROC-04; 1 description(s); confirmed: no)  
When the description states that a check of criteria leads to a positive path that ends with a final output task, while a negative outcome ends the process without that output, and both outcomes are distinct terminal results: Model the final output task as the last activity of the positive branch and connect it to the end event that represents the completion of that branch. Do not add a second end event after the output task for the same completion. Keep a separate end event only for the distinct negative outcome, so that each terminal outcome has one end event.

**LRN-030** (T5; refines SUB-01; 1 description(s); confirmed: yes)  
When the description says that a conditional branch triggers a group of listed activities that are performed together, some of them only in certain cases, and that the main flow continues only after the group completes, without presenting the group as a separate nested sub-flow: Do not wrap the group in an embedded subprocess. Model the conditional trigger as an exclusive gateway in the main flow, and model each listed activity as its own task directly in the main flow. Open a parallel gateway for the activities that run together. Put each case-dependent activity behind its own exclusive gateway within its branch, with an exclusive merge before the closing parallel gateway. Continue the main flow only after the matching parallel gateway.

**LRN-033** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description states a participant performing a work action as its own sentence step, and that step is directly followed by a decision or by the end of the process: Model each such work action as its own task, labelled with the action the description states. Do not fold the action into the decision gateway's question or into the label of an end event, and do not drop it when the next element is a decision or the end.

**LRN-034** (T6; new; 1 description(s); confirmed: no)  
When the description says a repeated cycle ends when one of several named outcomes occurs (for example graduating or withdrawing), with each outcome leaving the loop through a decision: Place an exclusive gateway after the repeat check, with one labelled outgoing flow per named exit outcome. Model each named exit outcome as its own task on its branch, placed after the gateway and before the end event that closes that branch. Do not route the exit gateway straight to an end event, and do not merge the named outcomes into one generic exit task or into the end event label.

**LRN-037** (T7; refines COL-07; 1 description(s); confirmed: yes)  
When the description mentions an outside party only as the recipient of a request the company sends, or as the target of a case the company hands over, and never describes that party's own actions as a process participant: Do not create a pool for that outside party and do not draw message flows to or from it. Model the sending of the request or the handover as a task in the company's own process, and model any awaited reply as an intermediate catch event or event-based gateway in that same process.

**LRN-038** (T5; refines GW-07; 1 description(s); confirmed: yes)  
When the description says that after a request is sent, the process waits for one of several occurrences, and that if a stated deadline passes without one of them, a follow-up action is taken: Model the wait as an event-based gateway with one outgoing branch per occurrence the process can receive. Model the deadline as its own branch that starts with a timer intermediate catch event, placed directly after the event-based gateway, and that leads to the follow-up action. Do not replace the deadline branch with an exclusive gateway that tests whether the deadline has passed, and do not connect the gateway directly to the follow-up action.

**LRN-039** (T7; new; 1 description(s); confirmed: yes)  
When the description is written in the first person as the account of one performing role that carries out the process's own steps, and the other parties it mentions (such as the party it sends requests to or receives replies from) are never described as having modeled steps of their own: Model the performing role as its own bpmn:participant pool inside a bpmn:collaboration, and place all of the process's start and end events, tasks, gateways and intermediate events in that pool. Do not create a pool for the other parties mentioned, and do not draw message flows to or from them unless the description states a message exchange. Model any reply the process must wait for as an intermediate catch event or event-based gateway inside the performer's pool.

**LRN-041** (T5; new; 1 description(s); confirmed: no)  
When the description says that, after an external party reports that a requested outcome is delayed, the process notifies a human user of the delay and asks the user to check again, and only afterwards the process waits for the outcome to arrive so it can be shown to that user: Model the notification of the delay to the user as its own task (a user task or manual task that the process performs for the user), placed on the sequence flow right after the event that reports the delay and before the intermediate catch event that waits for the outcome. Do not omit the notification, and do not let the wait event stand in for it, because the wait event only records that the outcome has arrived.

**LRN-042** (T7; refines ACT-04; 1 description(s); confirmed: yes)  
When the description says that, right after a step starts, the process sends a message to another participant and then keeps waiting for separate incoming messages from that participant or from another participant, so the sending is not the end of the flow: Model the sending as a send task in the process pool, with a message flow to the receiving pool, and give it an outgoing sequence flow to the next step that waits for the incoming messages. Do not place an end event at the sending point, and do not use one generic intermediate catch event to merge distinct incoming messages; model each distinct expected incoming message as its own receiving step after the send task.

**LRN-043** (T5; refines EVT-03; 1 description(s); confirmed: yes)  
When the description says that a participant remains idle, pausing until a stated turn or a stated readiness of something is reached, before a following step can begin, and the description does not say that the participant performs any work during that pause: Model the pause as an intermediate catch event on the sequence flow between the preceding step and the following step, and do not model the pause as a task. Use a task only for work that the description says is actually performed during the pause.

**LRN-045** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description has a participant perform two or more of its own actions on the same item in one sentence, joined by a conjunction such as 'and', after being told the item is available for it, and the generated model shows only one task or merges them into a state label: Model each action the participant performs on the item as its own task, in the order the sentence gives, after the wait for the stated availability. Label each task with the action the description states (for example, the participant takes the item, then the participant uses it). Do not merge them into one task, and do not use a catch event or an end event to stand for the action.

**LRN-047** (T5; refines ACT-05; 1 description(s); confirmed: no)

**LRN-111** (T6; refines ACT-08; 1 description(s); confirmed: no)  
When the description states an action performed on an item by no named system or role, using passive wording such as 'is registered' or 'is returned to' a party, and does not say that software performs it: Model that action as a plain task (bpmn:task) labeled with the described action or outcome. Reserve bpmn:serviceTask for steps the description says an automated system performs, and bpmn:userTask for steps it says a named person performs. Do not assign a service or user subtype from the verb alone.

**LRN-113** (T6; new; 1 description(s); confirmed: no)  
When the description states that a reviewer's decision is one of two alternatives (for example, opposing or confirming an item), and each alternative is a separately described action that the description names with its own verb phrase: Model each alternative as its own task, labelled with the action as the description words it, and place each task on its own outgoing branch of the exclusive gateway that follows the decision. Do not rename the described action into a different verb or noun, do not substitute a generic label, and do not drop the task of one alternative.

**LRN-115** (T5; refines ACT-04; 1 description(s); confirmed: no)  
When the description opens by stating that one participant sends an item or request to another participant, and that other participant then reviews it before any outcome is decided: Model the sending step as its own task that follows the start event and precedes the receiving participant's review task, connected by sequence flows; do not begin the process directly at the review step and leave the sending action out of the model.

**LRN-116** (T6; refines ACT-04; 1 description(s); confirmed: no)  
When the description states that one participant sends an item to another participant, and that other participant then acts on it in a later step: Model the sending step as its own activity in the sender's pool, placed before the receiver's first activity, and connect it to the receiver's pool with a message flow. Do not drop the send step and attach only the message flow to the receiver's activity.

**LRN-117** (T5; new; 1 description(s); confirmed: yes)  
When the description says one participant sends a request to another participant, that other participant then checks the request, and the first participant waits for an answer that depends on the outcome of that check: Model the sending step as a task, the checking step as its own task placed after it, and the answer-receiving step after the checking task. Connect these three steps with sequence flows in that order. Do not connect the sending step directly to the answer-receiving step, and do not merge the check into the sending or answer step. Place any decision on the outcome after the checking task.

**LRN-118** (T6; new; 1 description(s); confirmed: yes)  
When the description states that one participant replies to a request from another participant, and the content of that reply depends on the outcome of a check the replying participant performed, with the possible reply contents listed as alternatives within the same sentence: Model the reply as one task owned by the replying participant, labelled with that participant's name and the reply action in the description's own wording, placed after the checking task. Do not split the reply into an exclusive gateway with one send task per listed alternative, and do not model the requesting participant's side as a separate receive task whose label restates the reply. Use a gateway and separate tasks only when the description gives each alternative its own follow-up actions.

**LRN-119** (T3; refines PROC-05; 1 description(s); confirmed: yes)  
When the description states that one stage begins right after a completed sequence of steps, and it names no new event, message, time or condition that starts that stage: Do not model a start event for that stage. Connect the last element of the preceding sequence to the first element of the stage with a sequence flow in the same process, so that the stage stays on the main flow. Use a parallel split gateway only if the description states that two or more following activities run simultaneously.

**LRN-120** (T5; refines EVT-03; 1 description(s); confirmed: yes)  
When the description says that a participant has to wait until an external party confirms something it has already provided, and that wait happens on one branch of a parallel split whose other branches continue meanwhile: Model the wait for the external confirmation as an intermediate catch event on that branch, placed after the task in which the participant provides the information. Do not add a separate send task for the handover unless the description names sending as its own action. Join the branch with the other parallel branches at a parallel gateway, with a sequence flow from the wait event into that join gateway.

## Example-specific guidelines

**EXS-007** (T5; refines GW-03; 1 description(s); confirmed: no)  
When the description offers two alternative ways to signal or perform the same step, joined by 'or', and both alternatives are described as leading to the same next decision: Model the alternatives as an exclusive gateway that splits into one task per alternative. Give each alternative its own task, even when the description names only one of them as an automated or system-driven option. Connect each alternative task by its own outgoing flow into the same exclusive merge gateway that precedes the next decision. Do not omit an alternative task, and do not route one alternative's flow directly past the merge.

**EXS-014** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description's sentence that states the outcome or end of the process joins two distinct actions with 'and', where one action changes the status of a participant and the other is the performance of a separate commitment: Model each action joined by 'and' as its own task, in the order the sentence gives, and place these tasks in sequence before the end event. Do not merge the joined actions into one task whose label names both, and do not let the end event label carry one of the actions; the end event should only name the outcome reached.

**EXS-020** (T6; refines FID-03; 1 description(s); confirmed: yes)  
When the description states, within one sentence, several named assessments of the same object, joined by commas or 'and', where each names the aspect it evaluates (for example, its functionality, its safety and its market potential): Model each named assessment as its own task, labelled with the short verb-object form of the aspect it evaluates, taken from the description. Keep the order in which the description states them, and do not invent an order if none is stated. Do not merge them into one combined task and do not drop any of them. Connect them in sequence before the next step that depends on their results.

**EXS-027** (T6; refines GW-01; 1 description(s); confirmed: no)  
When the description states that one participant keeps performing an activity while another participant provides feedback, evaluation, or support, or that two or more activities are joined by 'while' or 'and' and are stated to happen together rather than in order: Model the concurrent activities as separate parallel branches that start at a parallel gateway, so they can run at the same time. Close the branches with a parallel gateway that waits for all of them before the next step. Do not sequence the concurrent activities one after another, and do not route them through an exclusive gateway, because an exclusive gateway chooses one path while the description requires both to proceed.

**EXS-030** (T5; new; 1 description(s); confirmed: yes)  
When the description says that a conditional branch launches a follow-up investigation whose listed activities are performed as one group, some of those activities run only in certain cases, and the main process continues only after the group has finished, without describing the group as a separate nested workflow: Do not wrap the follow-up group in an embedded subprocess. Model the conditional launch as an exclusive gateway in the main flow. Model each listed activity as its own task directly in the main flow. Open a parallel gateway for the activities that run together, and model any case-dependent activity behind its own exclusive gateway inside that branch, with an exclusive merge before the joining parallel gateway. Close the branches with a matching parallel gateway before the next step.

**EXS-033** (T5; refines ACT-07; 1 description(s); confirmed: yes)  
When the description states that after a step, the process continues along one of several named alternative outcomes, such as completing an action by a deadline or otherwise having the item cancelled, and each outcome is a separate action to perform: Model the outcome choice as an exclusive gateway placed immediately after the step that precedes it, with one labelled outgoing flow per named outcome. Give each outcome its own task labelled with that outcome's action, and connect each task onward to the next step or to an end event. Do not leave any named alternative without its branch, and do not replace the outcome choice with a single task or a plain sequence.

**EXS-035** (T5; refines GW-04; 1 description(s); confirmed: yes)  
When the description states that an activity follows a previously described activity but is independent of the activities that come after it, and those later activities are performed concurrently with one another before a choice is made: Model the dependent activity as a branch that opens from the activity it follows, running in parallel with the independent concurrent activities. Do not place it in sequence between the join of the concurrent activities and the following decision. Close all branches with a parallel join before the decision that needs their results, so that the decision is not preceded by an unrelated gateway.

**EXS-044** (T5; refines ACT-07; 1 description(s); confirmed: no)  
When the description states that a reply from an external party to a request may be either a result that is available at once or a notice that the result is delayed, and that a later result follows only in the delayed case: After the point where the reply is received, model an exclusive gateway that splits the flow by which reply arrived: one outgoing flow for the case where the final result is available and leads to presenting or processing it, and one outgoing flow for the case where only a delay notice arrived, which leads to handling the notice and then waiting for the later result. Do not model the two replies as one unconditional path, and do not omit the decision point. Join the flows again only where the process continues with the common steps.

**EXS-045** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description names the content of a message exchanged between the process and an outside party with a noun phrase that includes a domain modifier (for example a particular kind of request or score), and the generated send or receive element would use a generic word such as result or response instead: Label the send task or catch event that carries that message with the noun phrase the description uses for its content, keeping the modifier that identifies the kind of content. Use a generic word only when the description itself uses only that generic word.

**EXS-046** (T7; new; 1 description(s); confirmed: yes)  
When the description says an outside party, such as a person or a frontend system, starts the process by sending it a request, and the process later returns a result or a delay notice to that same party: Model the outside party as its own pool. Inside that pool, model the sending of the request as a task. Draw a message flow from that task to the message start event of the process pool. Draw message flows from each process task that returns a result or a delay notice to the outside party's pool. Do not place these request or receipt steps in the process pool itself.

**EXS-048** (T7; new; 1 description(s); confirmed: no)  
When the description says an outside participant may answer a request with an immediate result, or with a delay notice that is followed later by a separate final result, and the process must wait for each of these replies: Model each message the outside participant sends as its own send task in that participant's pool, in the order the description gives. Give each message its own intermediate catch event in the process pool, placed where the process waits for it. Do not let one catch event wait for two replies that the description separates in time, such as an immediate result and a later delay notice. When a delay notice is followed by a later result, model the notice as a send task that comes before the participant's continued work, and model the later result as a separate send task and a separate catch event after it.

**EXS-050** (T7; new; 1 description(s); confirmed: yes)  
When the description says that the process sends a request to an outside party right after it starts and then keeps waiting for replies from that party or from a requester, so the sending does not end the process: Model the sending of the request as a send task in the process pool, with a message flow to the receiving pool, and give it an outgoing sequence flow to the next step that waits for the replies. Do not end the flow with an end event at the point of sending, and do not use a generic intermediate catch event that merges several different replies (such as an immediate result and a delay notice). Model each expected reply that the description distinguishes as its own receiving step, placed after the send task.

**EXS-054** (T5; refines EVT-03; 1 description(s); confirmed: yes)  
When the description states that a participant waits for another participant to make something available or to arrive, and then performs one or more further described actions on it in a stated order, such as picking up and then consuming the item: Model the waited-for occurrence as an intermediate catch event. Then model each described action of the participant as its own task, in the stated order, on the sequence flow after that event. Do not place an end event between the catch event and these tasks, and do not treat the occurrence itself as the completion of the process.

**EXS-057** (T3; new; 1 description(s); confirmed: no)  
When the description says that after a case outcome (for example a job becoming permanent) the case ends, or else, when a rating or other stated condition holds, it keeps going and returns to an earlier activity to receive further items: Model the outcome as an exclusive gateway after the activity that produces it. Route the ending branch to an end event. Route the continuing branch back to the earlier activity through an exclusive merge gateway placed before that activity. Trace the cycle: every merge gateway on it must have an outgoing path that reaches an end event through the outcome gateway's ending branch, so the cycle can be exited and is not a closed loop.

**EXS-060** (T6; refines FID-01; 1 description(s); confirmed: no)  
When the description states that a meeting or interview between two parties can be negotiated or arranged, so the agreed meeting will later be carried out by a participant: Model the negotiating or arranging as its own step, such as a task or an event for the request. Also model the meeting itself as a separate user task named after the meeting that the participant performs, placed after the agreement. Do not let the request or negotiation step stand in for the meeting, and do not fold the meeting into a gateway question.

**EXS-061** (T1; refines XML-03; 1 description(s); confirmed: yes)  
When the description states several distinct outcomes that each end in a report to a different recipient or authority, and the reporting wording is the same or nearly the same across those outcomes: Create one bpmn:endEvent per distinct outcome. Build each end event's xs:ID from the specific recipient and condition that outcome represents, not from the shared reporting wording. Before finishing, check every id attribute in the model, including those of end events, tasks, gateways and sequence flows, and make sure no id value appears more than once.

**EXS-062** (T5; new; 1 description(s); confirmed: yes)  
When the description makes the reporting deadline or the recipient of an event depend on a sequence of yes/no checks on that event (for example whether it was fatal, whether it meets a stated severity or duration threshold, and whether another party already received a report), and each check changes the next step: Model each check as its own exclusive gateway, placed in the order the description gives the checks. Give each gateway one labelled outgoing flow per outcome, using the condition wording from the description. Attach each outcome flow to the report or step it triggers, including any stated deadline. Route the not-taken outcome to the next check or to its own continuation. Do not replace these checks with a task that assesses the event, and do not drop a check because its outcome only changes a deadline.

**EXS-066** (T6; new; 1 description(s); confirmed: no)  
When the description states a reporting duty for an occurrence, and then states that a subset of the same occurrence (defined by a stated outcome) must be reported again with its own shorter deadline even though it has already been reported: Model the general report and the repeat report as two separate tasks in sequence. Place the repeat report after the general report, on the branch of an exclusive gateway whose question states the outcome condition in the description's own terms. Label each task with only its verb, object and recipient as the description names them. Record the repeat report's own deadline and its 'even if already reported' qualification in the documentation of that task, and do not place the outcome condition or the deadline in either task label.

**EXS-070** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description names two or more separate values that a participant enters before a later step, so each value is described on its own: Model each separately named input as its own user task placed in sequence before the later step, and label each task with exactly the input the description names. Do not add inputs, attributes or details that the description does not state, and do not fold unstated items into a task label.

**EXS-071** (T5; new; 1 description(s); confirmed: yes)  
When the description lists requirements that a party must meet before a later step, and states that additional documents may be requested depending on circumstances, so the requirement check can either lead onward or lead to a request for more documents: Model the requirement check as a task, then place an exclusive gateway after it with one labelled outgoing flow for the outcome where the requirements are met and one for the outcome where additional documents are requested. Put the request for documents as its own task on the second outcome branch, and do not drop that branch. Model any re-check or loop back to the check only where the description explicitly states that the supplied documents are examined again. Do not add a loop or a separate verification step that the description does not state.

**EXS-084** (T6; new; 1 description(s); confirmed: no)  
When the description says the actor sends material or a draft to an outside party and then repeatedly tells that party what to change until the actor is satisfied with the returned result: Model the returned revised result as its own receive element placed after the sending activity and before the decision that checks satisfaction. Model the feedback to the outside party as a task. Route the decision back to that feedback task when the actor is not satisfied, so the receive element sits inside the loop. Do not model the returned result as part of the sending activity, the feedback task, or the decision.

**EXS-086** (T5; new; 1 description(s); confirmed: yes)  
When the description states that materials are given to a group of people who then perform a sorting step on them before the next activity: Model the hand-over of the materials as its own manual task, placed after the activity that obtains the materials and before the group's sorting activity, connected by sequence flows. Do not omit this hand-over task or fold it into the group's sorting activity.

**EXS-087** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description states that materials or items are handed over to a group of people who then carry out a stated activity on them, so the handover is a step before that activity: Model the handover as its own manual task, performed by people and not by a system, placed after the step that prepares the materials and before the group's activity. Model the group's activity as a separate following task. Do not omit the handover, and do not fold it into the label of the group's activity task.

**EXS-091** (T5; refines FID-01; 1 description(s); confirmed: no)  
When the description states that an external party (such as a customer) supplies the requirements or properties of an order, and that parallel work on the order starts only after those requirements are known: Model the act of receiving those requirements as a bpmn:userTask placed on the sequence flow after the process start event and before the parallel gateway that splits the work. Do not make the receipt of the requirements the start event itself, and do not omit the task.

**EXS-097** (T6; refines FID-02; 1 description(s); confirmed: no)  
When the description says that one set of information is sent to several different parties, each of which produces a separate part that is needed later: Model one send activity per receiving party, each placed after the step that prepares the information and each leading to its own part-producing activity. Do not merge these sends into a single send activity. Join the parallel branches with a parallel gateway before the step that needs all the parts, because all branches must complete.

**EXS-099** (T5; new; 1 description(s); confirmed: yes)  
When the description states that when a supplier cannot deliver the full amount of an item, the remaining amount must be ordered from several other suppliers, and otherwise the order continues with one supplier, so a sufficiency check follows the placement of the orders: After the orders are placed, model an exclusive gateway whose question asks whether the chosen supplier covers the full required amount. Give one labelled outgoing flow for 'enough' that continues to the next step, and one for 'not enough' that leads to a task ordering the remaining amount from several other suppliers. Merge the flows back with an exclusive merge gateway before the parallel gateway that starts the work. Do not omit the check or route all orders straight to the start of the work.

**EXS-103** (T5; new; 1 description(s); confirmed: no)  
When the description states a condition on a quantity that changes as deliveries or other events arrive (for example, a count of items still needed or a level that falls over time), and it says that a follow-up action, a repetition, or a further wait follows depending on whether that condition holds: Model an exclusive gateway at the point in the flow where the condition is checked, placed after the event or activity that changes the quantity and before the step the condition controls. Label it with the condition in the description's wording and give it one labelled outgoing flow per outcome. Route the outcome that repeats or continues waiting back through an exclusive merge to the earlier step. Do not fold the check into the arrival event or the preceding activity, and do not omit the gateway because the next step seems to follow anyway.

**EXS-105** (T6; refines ACT-05; 1 description(s); confirmed: no)  
When the description says that the participant asks other people to carry out a piece of work, and a later sentence makes a following step start only after that work is finished: Model the requested work as its own manual task (performed outside the system) placed after the sending of the request and before the step that depends on it, and connect the dependent step after that task in the sequence flow. Use the request itself as a send or manual task as the description states it. Do not replace the delegated work with an intermediate catch event named after its completion. Use an intermediate catch event only for an incoming message, signal, time, or condition that the description does not present as a piece of work performed by someone.

**EXS-109** (T7; refines COL-04; 1 description(s); confirmed: no)  
When the description says a task sends requirements, an order or other work input to an actor outside the process owner's organization, and that actor's returned output (such as a draft or revision) is something the process receives before it moves on to the next step: Model the outside actor as its own bpmn:participant pool in the collaboration. Draw a message flow from the sending task to that pool. Draw a message flow from that pool to a bpmn:intermediateCatchEvent of type message in the process pool, placed before the step that uses the returned output. Do not replace the receiving step with a task, and do not leave the outside actor as an unconnected pool.

**EXS-110** (T3; refines PROC-05; 1 description(s); confirmed: yes)  
When the description orders that the process as a whole is ended, or that an activity is halted, when a measured quantity drops below a limit or a connection to equipment is lost, and it may add a follow-up action for a person such as a notification: Model each such halting condition as a conditional branch from the point where the condition is checked. End that branch with its own explicit end event, placed after any follow-up action the description states for that branch (for example, notifying a person). When the halt applies to the whole process, make sure each such branch ends in an end event, so the process has at least one end event and no halting instruction is left without a terminal element.

**EXS-111** (T5; refines FID-02; 1 description(s); confirmed: no)  
When the description states that one derived figure is calculated from data collected from a single source, and the description names several distinct kinds of data or measures that enter that calculation: Model a separate retrieval task for each distinct kind of data or measure the description names, placed before the calculation task of the derived figure, with each retrieval task on the sequence path into the calculation. Do not collapse these distinct kinds into one generic data-collection task, and do not add retrieval tasks for kinds the description does not name.

**EXS-113** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that a conditional branch performs an action on a named physical object (such as a machine or piece of equipment), and a separate statement says that a state change of that same object (such as being disconnected) ends the process: Label the task in the conditional branch with the verb and the object exactly as the branch names them, and model the process-ending outcome as its own path that begins at the state-change event and ends at an end event, not as a task that relabels the object as the process. Keep the two actions on different objects as separate elements, and do not give a task a label that names an object the description does not name for that action.

**EXS-115** (T5; refines GW-04; 1 description(s); confirmed: no)  
When the description lists, within one step, a human action (such as pressing or entering something) and a system action (such as collecting or showing data) that are both to happen, and both must be completed before the flow continues: Model the human action and the system action as separate bpmn:userTask and bpmn:serviceTask elements in parallel branches. Place a bpmn:parallelGateway as split before the branches and a bpmn:parallelGateway as join after them, so the flow continues only when every branch is complete. Do not add conditions to these branches and do not replace the join with an exclusive gateway.

**EXS-119** (T6; new; 1 description(s); confirmed: no)  
When the description states that a follow-up step is performed only depending on the outcome of an inspection step, and the inspection step is described generically (for example as a check of the machine) without naming the specific property that decides the branch: Model the inspection step as a task whose label names the specific property it verifies, using the description's own terms for that property, not a generic label such as 'check' or 'verify' results. Place an exclusive gateway directly after that task and label it with a yes/no condition about that same property that the outcome either meets or does not meet. Do not label the gateway with a status such as completion of earlier work or a statement that an activity is done. Label each outgoing flow with the outcome it corresponds to.

**EXS-127** (T5; new; 1 description(s); confirmed: yes)  
When the description makes a decision depend on a duration that is not stated directly but must be derived from two moments it mentions (for example, the time remaining between a starting moment and an end moment), and then tests that derived duration against a threshold: Model a service task that computes the duration from the two moments. Place it after the step that yields the later-needed moment and before the exclusive gateway that tests the threshold. Connect the calculation task to that gateway with a sequence flow, so the gateway's condition tests the computed result. Do not leave the derivation implicit in the gateway's condition label, and do not omit the calculation task.

**EXS-129** (T6; refines FID-02; 1 description(s); confirmed: no)  
When the description states that a named participant performs a concrete action, such as bringing in an item, checking an item, or taking an item away, as its own sentence step, and that action either opens a path or closes a path with an outcome: Model each such action as its own task performed by that participant, placed on the path where the action occurs. Keep a checking action separate from any later step that hands results back, and do not merge the two into one task. Use a start event only to mark the trigger that begins the process, and use an end event only to mark the outcome that follows the action task, not the action itself.

**EXS-131** (T6; new; 1 description(s); confirmed: no)  
When the description says one participant produces an output and a different, more senior participant then checks that output, and the check is followed by a separate statement in which the checker records an OK or Not OK decision that routes the flow: Model the check as a task labelled with the checking act and its performer as the description words them. Model the decision as a separate task labelled with the decision act itself (for example the verb of deciding the outcome, with the outcome values), placed after the check and before the exclusive gateway that routes on that outcome. Do not label either task with a generic verb such as record or register, or with the name of a later process step, when the description names a different act. Keep the wording taken from the description.

**EXS-132** (T6; new; 1 description(s); confirmed: no)  
When the description states that one outcome of a check sends the flow back to an earlier activity, and that the other outcome says the process proceeds to further handling that is not described as ending it: Do not close the flow with an end event on the outcome that proceeds. Model the continuation the description names as its own task, or as the flow into the next described step, and place the end event only where the description says the process ends. Keep the rework flow on the other outcome as described.

**EXS-135** (T6; new; 1 description(s); confirmed: no)  
When the description states that one participant performs an action directed at another participant (for example a transmission, a check or a reply), and a task for that action could be labeled from the receiving participant's side (for example as receiving or getting something): Label the task with the acting participant as the subject, followed by the verb and object the description uses for that action (for example 'Participant A transmits the request to Participant B'). Do not rephrase the task as what the other participant receives or obtains, and do not swap the subject to the receiver, so the label matches the description's actor and action.
