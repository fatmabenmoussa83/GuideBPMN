## Generic guidelines

**LRN-011** (T5; refines GW-04; 10 description(s); confirmed: yes)  
When the description lists two or more activities that are performed without a stated order and must all be completed before a later step begins: Model a parallel gateway that splits into one outgoing branch per listed activity, and a parallel gateway that joins those branches before the next step. Do not chain the activities in sequence, and do not use an exclusive gateway for them.

**LRN-010** (T5; refines ACT-07; 8 description(s); confirmed: yes)  
When the description lists two or more actions that must all be carried out after a common point, with no order or alternative stated between them, and only then leads to a later step: Model a parallel gateway that splits into one task per listed action, keeping each action as its own task with the description's wording, in a separate branch. Join all branches with a parallel gateway before the later step, so the later step waits for every action. Do not chain the actions in sequence, do not use an exclusive gateway for them, and do not leave any branch without a connecting flow to the join.

**LRN-003** (T6; refines FID-02; 5 description(s); confirmed: yes)  
When the description states one sentence in which a performer or performer group carries out two distinct activities joined by 'and', where the second activity responds to or resolves issues raised by the first: Model each of the two activities as its own task, in the order stated in the sentence, connected by a sequence flow. Do not merge them into one task whose label combines both actions, and do not drop either activity from the model.

**LRN-001** (T5; refines ACT-07; 4 description(s); confirmed: yes)  
When the description states a conditional choice whose alternative outcomes later reconverge on a shared next activity or on an end event, while one branch leaves the process early: Model an exclusive gateway at the split for the conditional choice, with one labeled outgoing flow per outcome. Where the alternative paths come together again before a shared next activity or end event, insert a separate exclusive gateway as the merge point, so that each path enters the common step through a gateway rather than through a direct flow from several branches. Keep an early-exit branch as its own path to an end event instead of merging it into the continuing flow.

**LRN-022** (T5; refines FID-01; 4 description(s); confirmed: yes)  
When the description states one action in a sentence whose object is a list of distinct items joined by commas or 'and' (for example, an actor selects several things, or provides several kinds of information, in one phrase): Model each distinct item in that list as its own activity, in the order the description gives them, instead of merging the list into a single activity. Keep the activities in sequence and do not add gateways unless the description states a choice or concurrency.

**LRN-024** (T5; refines FID-01; 4 description(s); confirmed: no)  
When the description opens with an actor performing an action that initiates the process, such as submitting, reporting or requesting something, and that action is itself described as work done by the actor: Model a start event for the process trigger, then a task for the initiating action performed by that actor, and connect the start event to that task with a sequence flow. Do not make the initiating action itself the start event; the start event marks only the occurrence that begins the process.

**LRN-005** (T5; refines ACT-07; 3 description(s); confirmed: yes)  
When the description lists several activities that must all be finished before the process ends, with no order stated among them, and the end is described as waiting until every one of them is done: Model each listed activity as its own task. Fork them from one parallel gateway, merge them through a second parallel gateway, and place the end event after that join. Do not chain the activities in an arbitrary sequence, and do not let any branch reach the end event before the others have finished.

**LRN-020** (T5; refines FID-02; 3 description(s); confirmed: yes)  
When the description states one user action whose clause joins several distinct inputs or choices with 'and' (for example, 'provides X and Y' or 'selects A, B, and C'), followed by a further step that depends on them: Model each distinct input or choice named in that clause as its own user task, in the order the description states them, and connect these tasks in sequence before the task for the dependent step. Do not merge the items into one task, and do not leave any stated item out of the model.

**LRN-082** (T6; refines FID-03; 3 description(s); confirmed: yes)  
When the description states an action in a sentence whose main verb names that action, and the label a generator would give the corresponding task replaces that verb with a different verb or adds an object or qualifier the sentence does not contain: Label the task with the verb and object the description uses for that action, keeping the description's own verb (for example, the verb of a sentence that states a state change or a start). Do not substitute a new verb-object phrase that describes a different or more specific action, and do not add qualifiers such as 'urgency' or 'to farm' that the sentence does not state.

**LRN-098** (T5; refines GW-05; 3 description(s); confirmed: no)  
When the description says several activities or branches can run independently at the same time, and a later step can only follow once all of them are finished: Model a parallel gateway that splits into one concurrent branch per activity, with each branch carrying its own steps. Join all branches with a parallel gateway whose single outgoing flow leads to the subsequent step, so that the step waits for every branch. Do not leave a parallel split without a matching join, and do not replace either with an exclusive gateway. If a branch contains a choice between alternative outcomes, model that choice as an exclusive gateway inside the branch rather than as a parallel gateway.

**LRN-115** (T5; refines GW-05; 3 description(s); confirmed: yes)  
When the description says that several separate activities must all be performed, each handled as its own step with its own target or source, and a later step can only proceed once all of them are done: Model each separate activity as its own task in a parallel branch that starts at one parallel gateway (split), and join all branches with a matching parallel gateway before the next step, so that step runs only after every branch completes. Do not merge the separate activities into one generic task, do not chain them in sequence, and do not use an exclusive gateway, because every activity is required.

**LRN-004** (T5; refines EVT-01; 2 description(s); confirmed: yes)  
When the description opens with an action taken by an external party (for example, a customer making an inquiry) and then describes the organization's own work in response to it: Model a start event for the external occurrence that triggers the process, with no incoming flow. Model the organization's first response to that occurrence as a separate task placed after the start event, and do not name the start event after the work the organization performs.

**LRN-007** (T6; refines FID-01; 2 description(s); confirmed: yes)  
When the description states that the process is started or continued by an action an actor performs (for example, a department identifies a need, or HR creates or posts a document), and that action is a distinct piece of work rather than a message or time occurrence: Model that performed action as a bpmn:task in the lane or pool of the actor who performs it. If it also triggers the process, add a start event before the task, and do not replace the task with the start event. Keep the task even when a later step has a similar name, so each described action has its own task.

**LRN-009** (T5; refines ACT-07; 2 description(s); confirmed: yes)  
When the description presents two or more alternative ways that can each establish the same condition and then lead to the same next step: Model an exclusive gateway that splits into one task (or activity) per alternative, and merge the branches back with an exclusive merge gateway before the shared next step, so that the alternatives are not left as unconnected or unmerged paths.

**LRN-012** (T5; new; 2 description(s); confirmed: no)  
When the description says the team may optionally carry out one of two or more separately named activities joined by 'or', and the rest of the process continues whether or not that optional work is done: Model each named alternative as its own task. Place an exclusive decision gateway before them, with one outgoing flow to each task and one bypass flow that skips the optional work. Merge all of these paths at one exclusive merge gateway before the next step. Do not collapse the alternatives into a single task, and do not connect the bypass or the task outputs directly to the next step without that merge.

**LRN-014** (T6; refines PROC-05; 2 description(s); confirmed: no)  
When the description states that the process ends once a completion step has been carried out successfully, and that a later occurrence (such as feedback or a return) may follow after the end: Model the completion step as its own task on the main flow, placed directly before a single end event. Name the end event for the process end, not for the outcome. Model the later occurrence as a separate task or branch that is joined to the main flow through a gateway, and do not fold it into the label of the end event.

**LRN-018** (T6; refines FID-03; 2 description(s); confirmed: yes)  
When the description states an activity together with its recipient, its completion endpoint, or a second action coordinated with it (for example 'generates ... and sends it to the recipient', or 'sends ... to the recipient', or 'monitors ... until a stated condition'): Name the task so that its label keeps every element the description attaches to that activity: the recipient, the endpoint or completion condition, and any coordinated second action. Use the description's verbs and the qualifiers it states, and do not shorten the label to a bare verb-object pair that drops them. Keep the label short, but do not remove a stated part of the action.

**LRN-019** (T5; refines FID-02; 2 description(s); confirmed: no)  
When the description introduces a user action in a dependent clause that begins with a selection or choice (for example, 'after selecting X'), and then states a further user action that follows it and depends on it: Model the selection or choice as its own user task, placed before the task for the following user action. Keep each described user action as a separate task using the description's wording, so that no stated user step is dropped or merged into another task. Connect the tasks in the order the description states, with the dependent action only after the selection.

**LRN-026** (T5; refines FID-02; 2 description(s); confirmed: yes)  
When the description states that one item is subjected to several named checks or assessments, each with its own stated aim, and gives no order between them: Model each named check or assessment as its own task, keeping the description's wording for it, and place these tasks in a parallel split after the common starting point. Do not merge them into one combined task. Join all branches with a parallel gateway before the next step that needs all of the results.

**LRN-029** (T5; refines EVT-01; 2 description(s); confirmed: yes)  
When the description says the process begins with an action performed by an actor, such as a person signing up, and that action is itself described as work the actor performs: Model a plain start event with no incoming flow, followed by a task that represents the performed action. Do not place the performed action on the start event itself. The task then leads into the subsequent steps.

**LRN-030** (T5; refines GW-04; 2 description(s); confirmed: yes)  
When the description states that a check by one party yields a positive outcome on one branch, that this positive outcome is followed by a described action with several consequences occurring together, and that the process ends after a later described step is completed: Model the check as an exclusive gateway with the positive and negative outcomes as separate outgoing flows. On the positive branch, place an explicit task for the described action, using the description's wording, before any split. Route that task into a parallel gateway that splits the concurrent consequences, and model each consequence as its own task in a separate branch. Join the branches with a parallel gateway, then place the described later step as its own task before a single end event named for the process end. Do not skip the action task or connect the positive branch directly to the parallel split.

**LRN-031** (T5; refines GW-05; 2 description(s); confirmed: yes)  
When the description says a later step starts once a condition or state is reached, and that state is reached when the concurrent activities running before it have progressed, without describing a wait for an external message, signal, time, or condition: Connect the parallel join that closes those concurrent activities directly to the task that starts the later step. Do not insert a separate intermediate catch event to represent the state being reached, because the join already represents that synchronization.

**LRN-034** (T5; new; 2 description(s); confirmed: yes)  
When the description says an external party, such as a customer, performs an action (for example, providing feedback) that is optional after the case is handled, and it does not describe waiting for an incoming message, signal, time, or condition: Model that action as a task performed by that party on the optional branch, named for the action in the description's wording. Do not model it as an intermediate catch event. Reserve an intermediate catch event or event-based gateway for a wait that the description explicitly states (a message, signal, timer, or condition that must arrive before the process continues).

**LRN-037** (T6; refines ACT-07; 2 description(s); confirmed: yes)  
When the description states a condition that decides whether the process continues to a further outcome or ends, for example 'if all criteria are met, ...' followed by a consequence: Model an exclusive gateway at the point where the condition is decided, with one labeled outgoing sequence flow for each outcome the description states. Place the gateway before the outcome that the condition governs, and do not leave the conditional outcome as an unconditional sequence of tasks.

**LRN-039** (T6; new; 2 description(s); confirmed: yes)  
When the description states a step with a plain action verb and object for a party, and mentions no request, submission, sending, or message for that step, while a generated task label for that step adds such a communication verb: Model a plain task whose label reuses the description's own verb and object for that step. Do not add a communication verb such as request, submit, or send to the label, and do not turn the task into a send task or receive task unless the description states a message or sending for that step.

**LRN-042** (T6; refines FID-01; 2 description(s); confirmed: no)  
When the description states that a branch of a decision or condition is followed by a named action that a participant performs on that branch (for example an action taken when a condition holds, or one of several options the participant may choose), and the generated model leaves that branch with only the gateway flow, replaces the action with an event or a bare outcome label, or drops it: Model each such action as a task on the branch of the gateway it belongs to, labeled with the action's verb phrase from the description and keeping its stated object and qualifiers, and place it before the next step that depends on it. Do not replace the action with an end event, a start event, or a bare outcome label, and do not leave the branch without it.

**LRN-044** (T5; refines EVT-03; 2 description(s); confirmed: yes)  
When The description states a step as work that a party performs, such as receiving an item or verifying a delivery, and the next described step follows it directly with no stated pause, timeout, or external occurrence being awaited: Model that step as a task in the sequence, with the flow continuing straight to the next step. Do not replace it with an intermediate catch event. Use an intermediate catch event only where the description says the flow pauses until an external message, signal, time, or condition occurs.

**LRN-054** (T5; refines FID-01; 2 description(s); confirmed: yes)  
When the description states that a branch or outcome ends with a closing or recording action performed by a participant, such as closing an item or making a booking, before the process outcome is reached: Model each such stated action as a task on that branch, placed after the decision or preceding step and before the end event of that outcome. Do not omit the action or connect the decision directly to the end event.

**LRN-059** (T7; refines COL-04; 2 description(s); confirmed: yes)  
When the description names an external party, such as another organization, a remote service, or a user-facing system, that exchanges messages with the process while the process runs: Model each such external party as its own pool, not as a lane inside the process's pool. Show the exchanges with it as message flows between the pools: from the process's sending tasks to the external pool, and from the external pool to the process's receiving events or tasks. Do not draw these exchanges as sequence flows, and do not place the external party in a lane of the process pool.

**LRN-074** (T5; new; 2 description(s); confirmed: no)  
When the description lists several items or conditions that a request must satisfy before it can be decided, gives no order between them, and some of them are to be checked by a system or an external institution while others must be supplied by the applicant: Model each listed item or condition as its own activity, keeping the description's wording, in a parallel split placed after the common starting point. Model items checked by a system or an external institution as service or manual activities in their own branch, and items the applicant must supply as user activities. When the description says an item must be obtained or renewed if it does not meet a stated condition, add an explicit activity for obtaining it on that route. Join all branches with a parallel gateway before the decision or the next step, so the next step waits for every item. Do not merge the items into one combined activity and do not chain them in sequence.

**LRN-092** (T5; new; 2 description(s); confirmed: yes)  
When the description says the actor orders an item from an external party, or requests a reply from that party, and the next decision or step can only follow once the item has physically arrived or the reply has come back: Model the order or request as a send activity. Then model the arrival of a physical item as a manual task performed by the actor, and the arrival of a reply or confirmation as a receive task. Place this receipt activity directly after the send and before the gateway or activity that depends on it. Do not connect the send straight to the later decision or step, and do not drop the receipt from the flow.

**LRN-099** (T6; refines FID-03; 2 description(s); confirmed: yes)  
When The description states an activity together with its object and a named recipient or performer (for example, items sent to one or several parties, or work done by a stated party), and the activity is to be modeled as a send, receive or manual task: Label the task with the verb and object the description uses, and keep the stated recipient or performer in the label. If the description names several recipients or performers for the same activity, keep that whole set in the label, or model one task per recipient when they are handled separately. Do not narrow the set to a single party that the description does not name.

**LRN-112** (T6; new; 2 description(s); confirmed: no)  
When the description states a yes/no decision whose two outcomes are described as success or failure of a result, or as availability or non-availability of an option, and the branches lead to different next steps: Model the decision as an exclusive gateway and label it as a closed yes/no question that names the condition being tested, using the description's own terms for that condition (for example, whether the result works or whether the option can be obtained). Keep the same condition wording on the outgoing flows, and avoid generic labels such as 'Decision' or 'Check'.

**LRN-117** (T5; refines ACT-03; 2 description(s); confirmed: no)  
When the description states that, after the user enters identifying data for a device, the application automatically connects to or collects data from that device, and later steps depend on that connection: Model the automatic connection as its own bpmn:serviceTask placed in sequence directly after the user task that captures the identifying data, and before any user task that depends on the connection. Do not fold the automatic connection into the data entry user task, and do not represent it as a user task.

**LRN-138** (T5; refines EVT-03; 2 description(s); confirmed: no)  
When the description states that a participant physically performs an action as a step in the process, and no message, signal, timer or condition is awaited for that action: Model the participant's physical action as a manual task at the point where it occurs in the flow, labeled with the action in the description's own wording, and connect it to the following step or end event with a sequence flow. Do not model it as an intermediate catch event; catch events are reserved for waiting on a received message, signal, timer or condition.

**LRN-148** (T5; refines GW-03; 2 description(s); confirmed: yes)  
When the description states that a participant's decision leads to one of several alternative outcomes (for example, "X or Y"), and each outcome is described as its own activity: After the activities of the alternative outcomes, join the branches with an exclusive merge gateway before the process continues or ends, so the alternatives converge in one flow.

**LRN-151** (T5; refines ACT-04; 2 description(s); confirmed: no)  
When the description states that one participant hands a request, order, data, or notice of completion to another participant, with no reply, confirmation, or waiting condition stated on the sender's side, and the receiving participant's next stated activity is to process it: Model the sending step as a plain task in the sender's pool, not as a sendTask. In the receiver's pool, use a message start event if the handed-over item begins the receiver's flow, or an intermediate message catch event placed before the step it enables if the receiver's flow continues only after it. Connect the sending task to that event with one message flow. Add no waiting event on the sender's side when no reply is stated. Do not model the receiving side as a receiveTask, and do not pair a sendTask with a receiveTask for the same exchange.

**LRN-002** (T5; new; 1 description(s); confirmed: no)  
When the description states that a later step happens only if a condition about the customer holds, and the condition is stated before that step: Place an exclusive gateway with a conditional branch immediately before the first activity that depends on that condition, so that no dependent activity is reached before the decision. Do not place the decision after later activities that do not depend on it. The branch that fails the condition should lead to a separate path or end.

**LRN-006** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description lists several activities only as bare nouns in one enumeration (for example after 'including'), with no verb stated for each item: Model each listed item as its own task. Label it with a verb-object name in which the verb names the action performed on that item and the noun from the description is the object. Do not merge two listed items into one task, do not rename an item with a verb the description does not state, and do not leave an item out of the model.

**LRN-008** (T5; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that once an agreement or acceptance is reached, a new phase begins with a described starting activity, and then lists several sub-activities that run within that phase: Model the phase-starting activity as its own task, placed after the point where the agreement or acceptance is reached and before the parallel split. Model each listed sub-activity as its own task in a separate branch of that split, and join the branches before the next step. Keep each described sub-activity as its own task, using the description's wording, and do not replace one with a differently named task.

**LRN-013** (T5; new; 1 description(s); confirmed: no)  
When the description says the process is started by an external participant who can perform the initiating action through one of several alternative channels, each described as a distinct action: Model a single start event with no incoming flow. Model each alternative channel as its own bpmn:task in the pool or lane of the external participant who performs it. Place an exclusive split after the start event that leads to these tasks, and join them with an exclusive merge before the organization's first internal activity. Do not merge the alternatives into one generic task or drop a channel that the description names.

**LRN-015** (T5; refines PROC-04; 1 description(s); confirmed: no)  
When the description says the process begins when an actor performs one of several alternative actions (for example placing an order through one channel or another), and no single event itself starts the process: Model one start event for the process. Model each alternative action as its own task that follows the start event, and merge these alternative tasks with an exclusive gateway before the next activity. Do not model the actor's alternative actions as separate start events, and do not omit them from the model.

**LRN-016** (T6; refines PROC-04; 1 description(s); confirmed: no)  
When the description states that a process begins when an external party performs one of several alternative actions, each through a different channel, and the organization's response is the same whichever channel is used: Model each alternative channel as its own start event with no incoming flow, and let every such start event lead into the same first internal task of the process. Do not collapse the alternative channels into one generic start event with no trace of the channel, and do not model the external action itself as a task performed by the organization.

**LRN-017** (T3; refines PROC-04; 1 description(s); confirmed: no)  
When the description says the main work of the process ends once a completion step is done, and then says that a later occurrence from an external party (such as a reply or a return) may lead to additional work: Do not give the later occurrence its own start event with a separate chain to its own end event inside the same process. Keep one main flow with one end event. Route the later occurrence into that main flow through a gateway placed before the end event, or model it as an event subprocess or as a separate process. Every start event in the process must lead into the main flow or into a clearly separate process.

**LRN-021** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description states an activity on an object together with an alternative channel or option (for example, 'via one channel or another', or a list of alternatives joined by 'or') that is not the core verb and object of the action: Name the task with only the core verb and object the description states for that action. Do not add the alternative channels, options, or further clauses to the label. Keep the alternative as a separate branch or decision only when the description makes it one.

**LRN-023** (T6; new; 1 description(s); confirmed: no)  
When the description states that one party sends or delivers something to another party (for example, a document or notice that a system sends to a customer), possibly with an alternative channel named: Name the task with the sending or delivering action of the party that the description makes responsible for it, using the description's verb and the object being sent. Keep the other party as the recipient, and do not rename the task with the recipient's receiving verb. Leave the channel alternatives out of the label and show them only as a separate branch if the description makes them one.

**LRN-025** (T5; refines EVT-02; 1 description(s); confirmed: yes)

**LRN-027** (T6; new; 1 description(s); confirmed: no)

**LRN-028** (T5; refines EVT-01; 1 description(s); confirmed: no)

**LRN-032** (T6; refines ACT-07; 1 description(s); confirmed: yes)

Route only the outcome that requires follow-up into its own follow-up task, such as processing a payment. **LRN-033** (T5; refines GW-01; 1 description(s); confirmed: yes)

One outgoing flow leads into the optional task and the other bypasses it. Join the end of the optional task and the bypass flow with a separate exclusive gateway before the next step. Do not make the optional task mandatory, and do not use a parallel gateway for this choice.

**LRN-035** (T6; new; 1 description(s); confirmed: yes)

**LRN-036** (T5; refines PROC-04; 1 description(s); confirmed: yes)

**LRN-038** (T5; refines FID-02; 1 description(s); confirmed: yes)

**LRN-040** (T5; refines SUB-01; 1 description(s); confirmed: yes)

**LRN-043** (T6; refines FID-02; 1 description(s); confirmed: yes)

When the description says that software, after the user supplies input, generates a list of items or a set of options (such as required supplies or selectable alternatives) that the user then acts on: Model the software's generation of that list as a bpmn:serviceTask placed after the user's input step and before the human tasks that use the list. Do not model the system-generated list as a userTask or manualTask, and do not omit it.

**LRN-109** (T6; refines FID-03; 1 description(s); confirmed: yes)  
When The description states that a system or service itself provides, gives or shows items or guidance to the user as a step, and the description does not state that the user chooses or selects among them at that step: Label the activity with the provider's verb and object as the description states them (for example provide, give or show), keeping the stated qualifier. Do not relabel it with a user-action verb such as receive or choose, because that changes which party acts. Do not substitute a near-synonym for the description's verb.

**LRN-110** (T6; new; 1 description(s); confirmed: yes)  
When the description says that the system presents a list of items, or a set of options, to a participant, using a specific verb for presenting or offering and a specific term for the items or options: Model the step as a task whose label uses the description's own verb for presenting or offering and the exact item or option term it uses. Do not replace these with a generic verb such as give or choose, and keep each listed category as a separate, stated item or option.

**LRN-111** (T5; refines FID-01; 1 description(s); confirmed: no)  
When the description states, on a conditional branch, one or more user actions that the user may perform as alternatives or in combination (joined by 'and/or' or 'and'), each named as a distinct action the user carries out: Model each named user action on that branch as its own bpmn:userTask, placed after the branch's decision or gateway and before the next step. Use the description's own wording for each task. Do not drop an action because it is optional, and do not merge several actions into one task. Keep the and/or alternatives as separate tasks connected through a gateway that matches their semantics (an inclusive gateway for 'and/or', a parallel gateway if all must be done).

**LRN-113** (T1; refines XML-06; 1 description(s); confirmed: yes)  
When the description asks for a complete BPMN model that includes a diagram layout, so the output must carry a diagram interchange section with shapes and edges: Model every bpmndi:BPMNDiagram with exactly one bpmndi:BPMNPlane as its child, and reference the process or collaboration from that plane through its bpmnElement attribute. Place all shapes and edges for the model inside that plane. Never leave a BPMNDiagram without its BPMNPlane, because the BPMN20.xsd schema requires the plane as a child element.

**LRN-114** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description asks to compute a composite indicator from several component measures, and the component measures are not described as one single data-collection step: Model one service task per component measure that the composite indicator depends on, placed before the calculation task. Do not collapse all component acquisitions into one generic data-collection task, and keep the calculation task after all of them so the dependency is visible.

**LRN-116** (T6; refines EVT-03; 1 description(s); confirmed: no)  
When the description states that after a wait for an external state change ends, the process must perform a named activity again before continuing its cycle (for example, an activity that is resumed rather than simply rejoined): After the intermediate catch event that ends the wait, model the resumed activity as an explicit task (not as a bare sequence flow) and then route the flow into the cycle's join or decision gateway, so that the resumed work is visible in the model.

**LRN-118** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that the user enters two or more distinct data items one after another before a later stage of the process begins: Model each separately described data entry as its own user task, in the order the description gives, and keep the later stage after the last entry. Do not combine the entries into one task, even when they are described together in one sentence.

**LRN-119** (T6; refines FID-02; 1 description(s); confirmed: no)  
When the description states that the application automatically collects data from a device and that the collected data is then presented to the user, whether both actions appear in one clause (for example, joined by 'and') or in separate clauses: Model the automatic collection as its own bpmn:serviceTask. Model the presentation of the collected data as a second, separate bpmn:serviceTask placed directly after the collection, in the order the description gives. Do not combine the collection and the presentation into one bpmn:serviceTask, even when one clause describes both. If the description states that the user presses a control before the collection starts, model each press as its own bpmn:userTask placed before the collection serviceTask.

**LRN-120** (T6; refines EVT-03; 1 description(s); confirmed: yes)  
When the description says that an external party or a later event will act at a time that is not fixed in advance (for example, they arrive at a random time) and that a following activity can only start after that moment: Model the waiting period as an intermediate catch event placed immediately before the activity that depends on it, and do not represent the wait by a task or by the dependent activity itself.

**LRN-121** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a final activity is optional (for example, 'you can' do it) after the main work is done, with no condition that forces it: Model an exclusive gateway before the optional activity, with one outgoing flow into the activity and one bypass flow that goes directly to the process end event. Connect the activity to the same end event so that both the performed and the skipped paths terminate the process. Do not make the optional activity an unconditional step that every path must pass through, and do not omit the end event.

**LRN-122** (T3; refines PROC-05; 1 description(s); confirmed: yes)  
When the description states an outcome that is reported after an ongoing waiting period (for example, a status or completion that is entered once the wait is over) and that continues the same case, rather than beginning a new case: Do not give that outcome its own start event. Place it as an intermediate catch event in the same sequence flow, after the waiting activity, and continue the flow from there to the subsequent steps and the end. Use a start event only for a separate trigger that begins a new case.

**LRN-123** (T6; refines EVT-05; 1 description(s); confirmed: yes)  
When the description states that a consequence (such as a fine) applies to a party only if a required action is not completed within a stated time period, and the process continues afterwards: Model an exclusive gateway at the point where the deadline outcome is decided, with one labeled outgoing sequence flow for the not-completed case and one for the completed case. On the not-completed branch, model the consequence as a task (for example a service task) that applies it, not as a terminal end event. Then join the branch back into the normal flow, so the process continues afterwards. Use a timer intermediate event for the time period only if the description states the period as a wait to be awaited, and do not replace the decision with it.

**LRN-124** (T6; refines GW-01; 1 description(s); confirmed: no)  
When the description says that a party poses a question to the customer, and the answer selects one of several alternative activities that each follow a different path: Model the question as an activity, then place an exclusive gateway directly after it. Give the gateway one outgoing conditional flow per answer the description states, labeled with that answer, and connect each flow to the activity for that alternative. Do not model the choice as a question task alone, and do not leave the alternative activities without a gateway that routes the flow.

**LRN-125** (T6; new; 1 description(s); confirmed: no)  
When the description poses two or more successive customer questions, each choosing among alternatives and each asked at a different point in the process (for example, one question before a preparation step and another asked while that step is still running): Model each question as its own user task placed at the point where the description poses it, followed directly by its own exclusive gateway. Label each task and its gateway with the choice wording the description gives at that point, and label each outgoing flow with one stated answer. Do not reuse or swap the labels between decisions: a gateway's label must name only the choice of its own question, so that every decision is identifiable by its label alone and matches the position in the flow where the description poses it.

**LRN-126** (T5; refines FID-02; 1 description(s); confirmed: yes)  
When the description states a step that a person performs (for example a user checking a status, or logging in) between automated system steps, and names no software performing that step: Model each such person-performed step as a bpmn:manualTask at its described position in the sequence, including when a later system task or decision depends on its result. Do not omit it or fold it into the adjacent system task.

**LRN-127** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description states that a participant, after performing an action, also performs a separate check of their own (for example whether all items have been handled) and the next decision depends on the outcome of that check: Model the participant's check as its own task (a manual task if no software is used, a user task if software assists it), placed after the action it follows and before the decision gateway that depends on its outcome. Do not fold the check into the preceding task or leave it out, and do not connect the preceding action directly to the decision.

**LRN-128** (T5; refines FLOW-06; 1 description(s); confirmed: yes)  
When the description says that the outcome of an activity or a completed repetition decides whether the process continues to a later step, so the activity is followed by a decision gateway, and that gateway has one outgoing flow for the continuing outcome and one for the other outcome: Connect the preceding activity by a sequence flow to a decision (exclusive) gateway placed right after it. Give that gateway one labeled outgoing flow for each outcome the description states, and route the continuing outcome directly to the next step the description names. Do not leave a decision gateway's outcome unconnected, and do not omit the flow from the activity into the decision gateway. Where the decision closes a repetition or a branch, its continuing outcome must reach the next step, not be dropped.

**LRN-129** (T1; refines XML-06; 1 description(s); confirmed: yes)  
When the description asks for a complete BPMN model that includes a diagram layout, so the output must carry shapes and edges for the process: Write the diagram section as a bpmndi:BPMNDiagram element in the BPMN DI namespace (http://www.omg.org/spec/BPMN/20100524/DI) and place it as a direct child of the definitions root, after the process and collaboration elements. Never write the diagram element in the BPMN model namespace (http://www.omg.org/spec/BPMN/20100524/MODEL), because the BPMN20.xsd schema accepts only a DI BPMNDiagram or a model relationship as children of definitions.

**LRN-130** (T5; new; 1 description(s); confirmed: yes)  
When the description says that after waiting for an external delivery or reply, a side action (such as a charge or a demand to the other party) is performed automatically if the wait exceeded a stated duration, and the main flow then continues to a later step whether or not the side action was needed: Model the wait as a receive task or intermediate catch event. Follow it with an exclusive gateway that tests whether the stated duration was exceeded. The 'exceeded' branch goes to a task that performs the side action, and that task's outgoing flow leads into an exclusive gateway that merges back into the main flow at the next step. The other branch goes directly to that same merge gateway. Do not model the threshold as a timer boundary event on the waiting activity, do not end the process after the side action, and do not add a separate end event for it unless the description says the process ends there.

**LRN-131** (T5; refines FID-03; 1 description(s); confirmed: yes)  
When the description has a title naming the process and states no explicit occurrence that starts the process: Label the start event with the title's own term for the process, not a generic label such as 'Process started'. Do not add a trigger the description does not state.

**LRN-132** (T6; new; 1 description(s); confirmed: no)  
When the description says that when a condition is not met, the process selects another item and then starts again with the same check that was already performed earlier in the process: Do not add a second decision gateway that asks the same condition again. Model the selection or preparation step that the description names as an explicit task, place it on the branch after the failed outcome, and route a sequence flow from that task back into the existing decision gateway that performed the check. Keep the original gateway as the only place where that condition is decided.

**LRN-133** (T6; new; 1 description(s); confirmed: no)  
When the description states a yes/no check that is reached only on the negative outcome of an earlier yes/no check (introduced with wording such as 'if not, you need to check whether ...'), and the outcomes of the new check lead to different next steps: Model the nested check as its own exclusive gateway placed on the negative outgoing flow of the earlier gateway, not merged into or reordered with that earlier gateway. Label the new gateway as a closed yes/no question that names the condition using the description's own terms, and give its two outgoing flows the answer labels. Do not reuse the label of the earlier gateway or move the new check ahead of it.

**LRN-134** (T5; refines FID-02; 1 description(s); confirmed: no)  
When the description contains a short standalone imperative sentence that directs the user to make a choice or perform an action (for example 'Select one.'), placed after a presentation of options and before a later step: Model that imperative sentence as its own user task, placed in the sequence where it occurs: after the task or event that presents the options, and before the next step of the process. Do not drop it, and do not fold it into the neighbouring task.

**LRN-135** (T6; new; 1 description(s); confirmed: no)  
When the description states that, on a branch reached only when a resource is available, the system presents a list of options to the performer, and the performer then is told to choose one of them (for example 'select one' after the list is shown): Model the choice as its own user task, named with the description's verb for the choice, placed on the branch after the outgoing flow of the availability gateway and before the next decision or step that depends on the chosen option. Do not leave the selection implicit in the gateway condition, and do not start the branch directly at the next decision.

**LRN-136** (T6; new; 1 description(s); confirmed: no)  
When the description joins, in one clause with 'and', a physical activity that a person performs and a separate measuring or recording action on that activity (for example, a measured time or result): Model the performed activity and the measuring or recording action as two separate tasks, in the order the description gives. Place the measuring task directly after the performed activity. Use a bpmn:serviceTask for the measuring when the description says a device or application takes the measurement, and a bpmn:manualTask otherwise. Do not merge the two actions into one task, even when one clause describes both.

**LRN-137** (T6; refines ACT-07; 1 description(s); confirmed: no)  
When the description states that two activities are performed at the same time (for example by joining them with 'at the same time' or by a clause such as 'while doing X, you do Y'): Model the concurrent activities as parallel branches: place a bpmn:parallelGateway before them with one outgoing flow to each activity, and join those branches with a matching bpmn:parallelGateway before the next step in the description. Do not sequence the simultaneous activities one after another, and do not use an exclusive gateway for them.

**LRN-139** (T5; new; 1 description(s); confirmed: yes)  
When the description states that the process opens with a participant's physical action on an item (such as bringing it in) that is performed as a step before the first checking or processing activity, and no message, signal, timer or condition is awaited for it: Model a none start event, then a manualTask labeled with the action in the description's own wording, placed as the first step in the flow, followed by the next activity via a sequence flow. Do not model the physical action as the start event itself, and do not model it as an intermediate catch event.

**LRN-140** (T5; refines GW-01; 1 description(s); confirmed: yes)  
When the description states that a person reviews an item and then records an outcome label (such as OK or Not OK) on it, and a decision gateway routes the flow according to that recorded label: Model the review as a user task performed by that person. Model the recording of the outcome label as its own user task, performed by the reviewing person and placed after the review and before the decision gateway. The gateway should only route on the recorded outcome and must not stand in for the recording action. Give each outcome branch the task or end event that the description states for it.

**LRN-141** (T6; new; 1 description(s); confirmed: yes)  
When the description states a stage of the process in passive form, such as 'is registered', 'is sent back', or 'proceeds', without naming a performing participant, and the generated model turns that stage into a start event, an end event, or a bare branch label instead of a task: Model each such stated stage as a task on the main flow or on the branch where it occurs, labeled with the description's own verb phrase and object. Place the task before the next step that depends on it. Reserve start and end events for the actual beginning and end of the process, not for a stage that the description says continues afterwards.

**LRN-142** (T5; refines FID-01; 1 description(s); confirmed: yes)  
When the description states that a work product is checked by a reviewer who then marks it with an outcome (for example OK or Not OK) that decides the next step: Model the reviewer's check as its own task in the reviewer's lane, and model the recording of the verdict as a separate task performed by that reviewer, placed before an exclusive gateway that routes the flow on the verdict. Do not fold the check and the verdict into the gateway alone.

**LRN-143** (T6; refines FID-01; 1 description(s); confirmed: yes)  
When the description states that the output of one actor's activity is then checked or reviewed by another actor, who decides an outcome (for example OK or Not OK) that the flow then branches on: Model the review as its own task performed by the reviewing actor (in that actor's lane if lanes are used), placed after the preceding activity and before the outcome gateway. Do not fold the review into the preceding task or into the gateway. If the description says a rejected outcome returns to the earlier actor for repetition, model that return as a flow back to the earlier activity.

**LRN-144** (T5; new; 1 description(s); confirmed: yes)  
When the description says that an item is passed to a deciding person who must approve or reject it, and that a rejection returns the item to its original submitter, who then reviews it before any further step: Model the passing of the item to the deciding person as a receiving task performed by that person's role (in its lane if lanes are used). Then model a separate decision task, performed by that same person, in which the approve or reject outcome is made. Place an exclusive gateway directly after that decision task, with one labeled outgoing flow per outcome. On the rejection branch, add a return task that hands the item back to the original submitter, and connect the gateway to the submitter's review task only through that return task. Do not connect the gateway directly to the submitter's review task, and do not let a generic review task stand in for the deciding person's decision.

**LRN-145** (T5; refines FID-02; 1 description(s); confirmed: no)  
When The description states that a request is first completed or registered by one actor, and only then is it passed on to another actor, who takes it up as the next step: Model the preparatory action (the registration or completion by the first actor) as its own task in that actor's lane, placed before the handover. Model the receiving actor's uptake of the request as a separate task in that actor's lane, placed after the handover and before that actor's next described step. Do not collapse the preparatory action and the handover into one receive task, and do not drop the preparatory task.

**LRN-146** (T6; refines FID-01; 1 description(s); confirmed: no)  
When the description says a request is first registered or submitted by one party and then forwarded so that another person receives it and must act on it: Model the registration or submission step as its own task, placed before the forwarding. Model the other person's receipt of the forwarded request as a user task (or manual task) that the next decision depends on, not as a receive task. Reserve receive tasks for steps the description presents as waiting for an incoming message.

**LRN-147** (T6; new; 1 description(s); confirmed: no)  
When the description states that a role receives an item after a prior submission, registration or automatic notice, or that a role must carry out a further step after such a notice, and it names that role and the action with specific wording: Model the receipt or the follow-up step as its own user task in that role's lane, placed after the prior step and before the next decision or end event. Label the task with the receiving role and the verb and object the description uses for that action. Do not use a generic label such as 'Receive ...' or 'Complete ... procedures' that drops the role or the described action.

**LRN-149** (T6; refines ACT-08; 1 description(s); confirmed: no)  
When the description states an action that one role performs toward another role within the same process (for example, sending something to or reviewing something for another role), and it names no message exchange with an external participant, no system the performer works in, and no form or screen the performer fills in: Model the action as a generic task. Do not use a send task for it, because no message leaves the process, and do not use a user task, because no human-computer interaction is described. Keep each separately described action as its own task, and do not merge it with neighbouring actions or drop it.

**LRN-150** (T5; refines ACT-04; 1 description(s); confirmed: no)  
When the description states that one participant sends something to another participant, and the receiving participant then acts on it: Model the sending step as a bpmn:sendTask in the sender's pool, placed in the sender's sequence flow where the description places it. Connect it with a message flow to the receiving participant's element. Do not split the sending into a separate start event and end event pair in each pool.

## Example-specific guidelines

**EXS-008** (T3; refines PROC-04; 1 description(s); confirmed: no)  
When the description states that the main flow reaches a defined end outcome, and then names a later occurrence from an outside party that may lead to additional handling: Do not model that later occurrence as a start event with no incoming flow that opens its own chain to an end event. Model it either as an event subprocess (triggeredByEvent=true, exactly one triggered start event, no sequence flows), as a separate process, or as a catch branch joined to the main flow through a gateway.

**EXS-020** (T6; new; 1 description(s); confirmed: no)  
When the description states that, after a main activity has started, the process keeps running for an extended period in which one party repeatedly receives several separately named kinds of communication from another party, such as regular updates, improvements or renewal notices: Model each separately named communication as its own task performed by the sending party, using the description's wording for that communication, and do not merge them into one generic notification task. Place these tasks inside the ongoing period, for example in a loop or on a repeating branch that returns to the point where the period is waiting for the next event. Keep the period's continuation and its exit path explicit with gateways, so that the communications are not omitted or left outside the ongoing phase.

**EXS-021** (T5; new; 1 description(s); confirmed: yes)  
When the description states that a review or evaluation by one party leads to an approved outcome on one branch, that the approved outcome is then carried out by a described action with several consequences that happen together, and that the process ends once a later described step is completed: Model the review as an exclusive gateway with the approved and not-approved outcomes as separate outgoing flows. On the approved branch, place an explicit task for the described action, using the description's wording, before any split. Route that task into a parallel gateway that splits the concurrent consequences, and model each consequence as its own task in a separate branch. Join the branches with a parallel gateway, then place the described later step as its own task before a single end event named for the process end. Do not skip the action task or connect the approved branch directly to the parallel split.

**EXS-044** (T6; new; 1 description(s); confirmed: no)  
When the description says that an external party's answer to a request may either arrive at once or be delayed, so that the process must handle a notice of delay and later a final answer, with the outcome varying from case to case: Model the external answer as a single decision point rather than as one catch event per outcome. After the request, model one wait for the external reply, followed by an exclusive gateway that routes an immediate final answer directly onward and a delay notice to a separate branch. In the delay branch, model a task performed by the process that reports the delay to the user, then an intermediate catch event that waits for the final answer, and then join that branch back with the immediate branch at an exclusive gateway before the answer is passed on. Each gateway outgoing flow must carry a condition that states which case it covers.

**EXS-047** (T7; refines COL-01; 1 description(s); confirmed: no)  
When The description says a process sends a request to an outside service provider, the provider reports a delay to the process, and later sends back its final outcome to the process: Model the outside service provider as its own pool. Model the process's request to the provider as a message flow into that pool. Model each notice the provider sends (such as a delay notice) and the final outcome as separate message flows from the provider's sending tasks or send events to the receiving events or tasks of the process. Do not connect the process and the provider with sequence flow, and do not leave these exchanges unmodeled.

**EXS-051** (T5; refines EVT-03; 1 description(s); confirmed: yes)  
When the description says that a participant is handed a device or notice that will later announce readiness, and that the participant then waits for that announcement before continuing to collect the result: When this holds, model the participant's wait as an intermediate catch event that is triggered by the later announcement, placed on the participant's path before the collection step. Model the announcing action on the other side as an intermediate throw event or a send task. Do not model the wait as a task, and do not connect the collection step directly without the catch event.

**EXS-052** (T6; new; 1 description(s); confirmed: yes)  
When the description lists several consecutive actions by the same participant, each stated in its own sentence or clause and each acting on a different resource or counterpart (for example, recording an entry in a system, then collecting something from a counterpart, then setting up an item and handing it over, then informing another party), before the flow moves on: Model each such action as its own task in that participant's lane, in the order the description states them, connected by sequence flows. Do not drop any stated action, and do not fold it into a neighbouring task. Keep each action as a separate task even when the next action follows directly with no stated pause.

**EXS-053** (T7; refines ACT-05; 1 description(s); confirmed: no)  
When the description says one participant passes an order, a request, or the news of a finished item on to another participant, and the receiving participant's flow either begins with that passing-on or continues only after it: Model the sending side as a plain task in the sender's pool, not as a sendTask. Model the receiving side in the receiver's pool as a message start event if the passed-on item begins the receiver's process, or as an intermediate message catch event placed before the step it enables if the receiver's flow continues only after it. Connect the two with one message flow from the sending task to that event. Do not model the receiving side as a receiveTask, and do not pair a sendTask with a receiveTask for the same exchange.

**EXS-054** (T3; refines PROC-04; 1 description(s); confirmed: yes)  
When the description says the process ends when a completion condition holds, but an exception based on a rating or threshold keeps the process running, so that an activity (such as collecting or combining incoming items) must continue to be performed after that exception applies: Model the completion condition as a decision after the completion step. Route the exception outcome back into the continuing activities, and route the ordinary outcome to an end event. Check every activity on the continuing branch, including activities that combine or merge incoming items, for a path to an end event. That path must still exist when the exception no longer applies, so the activity can always reach a terminal outcome.

**EXS-057** (T6; new; 1 description(s); confirmed: no)  
When the description states that a participant must regularly perform a reporting action, and a later gateway decides whether that reporting cycle repeats or ends: Model the stated reporting action as a user task inside the cycle, placed before the gateway that decides whether the cycle repeats. Label the task with the verb and object the description uses for that action, and keep any stated qualifier. Do not replace it with a bare outcome, an event, or a generic label.

**EXS-058** (T5; new; 1 description(s); confirmed: no)  
When the description makes a notification of an occurrence to one party conditional on whether the same occurrence has already been communicated to another party, and separately states that a notification of that occurrence must still be sent to a different party regardless of that earlier communication: Model an exclusive gateway before the conditional notification task, with one labeled outgoing sequence flow for the case where the earlier communication was made and one for the case where it was not. Route only the case the description makes conditional into the notification task. Model any notification the description requires regardless of the earlier communication as its own task on a path that is not controlled by that gateway, so it is never skipped. Do not nest the unconditional notification inside the branch of the conditional one.

**EXS-059** (T5; refines FID-02; 1 description(s); confirmed: no)  
When the description states that a party must notify an external body about an event only when two conditions hold in sequence, such as a severity condition on the event and a check that no other party has already made the same notification, and the notification must not happen otherwise: Model each condition as its own exclusive gateway, placed in the order the description states them. Place the notification as its own task only on the path where every condition holds, and keep it separate from other steps rather than merging it into a gateway or another task. Route the paths where any condition fails past the notification. Merge all paths with an exclusive gateway before the process continues.

**EXS-061** (T5; new; 1 description(s); confirmed: no)  
When the description states a check of one condition, and a second check on a different condition applies only to cases where the first check holds, with a required report or action following from the second check: Model one exclusive gateway per check, in the order the description states them. Route the branch where the first check holds by a sequence flow into the second gateway, so the second check is reached only after the first has passed. Place the required report or action as a task on the branch of the second gateway where its check holds. Do not connect the second gateway from any branch that bypasses the first check.

**EXS-063** (T5; refines GW-04; 1 description(s); confirmed: yes)  
When the description states that choosing one alternative at a decision point requires several follow-up actions that must all be performed, with no order stated between them, and that the remaining alternatives then become invalid: After the decision gateway, on the branch of the chosen alternative, model a parallel gateway that splits into one task per follow-up action, each action as its own task in its own branch with the description's wording. Join those branches with a parallel gateway before the next step, so the process continues only after every follow-up action is done. Do not chain the follow-up actions in sequence, and do not use an exclusive gateway to fan them out. Model the invalidation of the remaining alternatives as one of the parallel branches.

**EXS-065** (T6; refines ACT-07; 1 description(s); confirmed: no)  
When the description states that a review of the applicant's submitted items may lead to a request for further items, depending on circumstances, before the final outcome is reached: Model an exclusive gateway directly after the activity that submits or reviews the items. Phrase its question with the condition in the description's own wording (for example, whether further items are requested). Give one labeled outgoing sequence flow per stated outcome. The branch that requests further items leads to a task that supplies them and then returns to the same review. The other branch continues to the outcome. Place this gateway before the decision that the condition governs, and do not reuse a question about a different condition for it.

**EXS-066** (T6; refines FID-03; 1 description(s); confirmed: no)  
When the description states that a further request for items or evidence may follow a review 'depending on the circumstances' (an optional follow-up condition), and the outcome of the review is decided by a separate later condition: Model the optional follow-up as its own exclusive gateway placed right after the review that may trigger it. Phrase its question as the condition the description gives for the follow-up, and do not reuse that question for the outcome decision. Give the follow-up branch a user activity that supplies the requested items and returns to the review. Keep the outcome decision as a separate exclusive gateway whose question uses the description's own outcome condition.

**EXS-067** (T5; refines EVT-03; 1 description(s); confirmed: yes)  
When the description says that a period of gathering answers, games or other items continues until a stated condition is reached (for example, 'until enough people are free' or 'until all replies are in'), and a later decision or synchronization depends on the outcome of that period: Model the continuing period as an intermediate catch event placed after the activity that starts the gathering and before the gateway that uses its outcome. Do not connect the activity directly to that gateway, and do not fold the waiting period into the activity or the gateway.

**EXS-076** (T6; refines FID-02; 1 description(s); confirmed: yes)  
When the description says several components are each built and then tested individually, the whole machine may only be assembled when the tests succeed, and a failed test requires redesigning and rebuilding that component: Model one test task per individually tested component, not a single shared test task, and place each test after the build of its own component. Follow each test with an exclusive gateway that separates success from failure. The failure branch goes to a redesign-and-rebuild task that loops back to that component's build. Route the success branches into a join, and put an exclusive gateway with an explicit success/failure check before the assembly task, so that assembly is reached only when every test succeeded. Do not reuse one redesign task for a different component's test, and do not drop a test or the decision that guards assembly.

**EXS-078** (T5; refines GW-04; 1 description(s); confirmed: no)  
When the description says the whole product is composed of several subcomponents, each produced and checked individually, and the whole is assembled only after all of them are finished: Model a parallel gateway that splits into one concurrent branch per subcomponent, each branch carrying its own production and verification steps. Join all of these branches with a parallel gateway before the shared assembly step, so that assembly waits for every subcomponent. Keep the outcome of each verification as an exclusive decision inside its branch, and do not use a parallel gateway for the alternative outcomes of a single check.

**EXS-082** (T5; new; 1 description(s); confirmed: yes)  
When the description says the customer chooses one option from several alternatives (for example, a set of attribute values), and each chosen option is manufactured or handled by its own named party, so only the party for the chosen option must receive a request: Model an exclusive decision gateway right after the customer's choice is known and before any request is sent. Give each alternative its own outgoing sequence flow to a separate send task whose label names the party that handles that alternative, using the description's wording. Do not send one generic request covering all alternatives, and do not use a parallel gateway, because only the party for the chosen option is contacted. Join the branches again with an exclusive merge gateway before the next step.

**EXS-083** (T5; refines GW-02; 1 description(s); confirmed: no)  
When the description states that a subject may optionally request extra options, with words such as 'likes to' or 'may', that some parties must act on before shared steps continue, while the remaining steps apply to every case: Place an exclusive decision gateway after the point where the optional requests are known and before the shared steps. One outgoing flow runs the task that passes the chosen options to the parties that must act on them, then continues to the shared step. The other outgoing flow skips these tasks and goes directly to the shared step. Label the flows with the condition. Rejoin the branches with an exclusive merge gateway before the shared step. Add no gateway when every case receives the same steps.

**EXS-084** (T6; new; 1 description(s); confirmed: no)  
When the description says that a producer, after collecting a customer's chosen features, sends requirements to several different named teams, each of which manufactures a different part, and every one of these teams is contacted: Model a parallel gateway that splits the flow, then one separate send task for each receiving team, labeled with that team's name and the requirements it receives, as the description words them. Each send task gets its own branch. Rejoin the branches with a parallel gateway before the next step. Do not use one generic send task that covers all teams and all parts, and do not use an exclusive gateway, because every team is contacted.

**EXS-094** (T5; new; 1 description(s); confirmed: no)  
When the description says that the user may reach out to other people to borrow or buy an item cheaply from them, while the remaining items are bought instead: Model the sourcing choice as an exclusive decision. On the branch where the item can be obtained cheaply from another person, add a user task for reaching out to that person, followed by a separate user task for obtaining the item from them. On the other branch, model the purchase of the item. Join both branches before the next step. Do not omit the reach-out and obtaining tasks, and do not merge them into the purchase task.

**EXS-095** (T3; refines PROC-04; 1 description(s); confirmed: yes)  
When the description states that a condition ends the operation, such as a measured efficiency figure falling under a set limit or a connected resource being lost, and that otherwise the operation keeps running: Model each such ending condition as a branch of an exclusive gateway that leads to its own explicit end event. Before that end event, model any action the description assigns to that branch, such as shutting down equipment or notifying a person. Ensure the process has at least one explicit end event, and do not leave any ending branch without a successor.

**EXS-096** (T5; refines ACT-05; 1 description(s); confirmed: no)  
When the description states that a person physically performs an action on equipment (for example, restarting or repairing it) as a step the process depends on, and the steps that follow continue from that action: Model the physical action as a manual task placed at the point where it is performed, and connect it to the subsequent steps with a sequence flow. Use an intermediate catch event only for an occurrence that the process detects or receives as a signal or notification, not for an action a person carries out.

**EXS-103** (T5; new; 1 description(s); confirmed: no)  
When the description states that a person enters or records a result, status, or date into the system as the closing action of a branch or process segment, such as the outcome of a completed piece of work or the next scheduled due date, and that person performs the work with software support: Model each such closing recording step as a bpmn:userTask performed by that person, placed after the work it records and before the branch ends or the next stage begins. Do not omit the step or replace it with a serviceTask, sendTask, or gateway.

**EXS-125** (T5; new; 1 description(s); confirmed: yes)  
When the description says an actor examines or checks a request or input, and then gives a reply whose content depends on the result of that examination, where the possible replies are listed after the examination as alternative forms of that one reply (for example, transmitting something or rejecting it): Model the examination as its own task performed by that actor. Model the reply as a single task performed by the same actor, placed after the examination task and before the end event. Do not create a separate send task or a separate end event for each listed form of the reply, and do not connect the examination task directly to an end event.

**EXS-126** (T6; refines ACT-04; 1 description(s); confirmed: yes)  
When the description says a participant examines a request it received from another participant, and then replies to that request with either the requested data or a refusal, depending on the examination outcome: Model the examination as a task of the examining participant. Then model the reply as its own task performed by that same participant, placed after the examination task. Branch from the reply task into the possible outcomes, such as sending the requested data or refusing. Do not omit the reply task, and do not replace it with the requesting participant's own send or waiting elements or with a single send task that skips the decision on the reply.
